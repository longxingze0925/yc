# 供应链与客户端防伪设计

## 1. 目标

远控客户端具有高权限和敏感能力，发布链路必须从第一版开始设计可信验证，避免用户安装伪造客户端、篡改更新包或错误连接到非官方服务。

目标：

- 安装包签名。
- 更新 manifest 签名。
- 制品 hash 校验。
- SBOM 输出。
- 发布审计。
- 私有化部署的客户端渠道隔离。
- 客户端能识别官方服务和私有化服务。

## 2. 范围

`V1 Core` 必须实现或冻结：

- Windows 安装包签名策略。
- Ubuntu `.deb` 仓库或包签名策略。
- iOS App Store / TestFlight 签名边界。
- 发布 manifest Ed25519 签名。
- 客户端内置 release public key。
- 每个制品的 SHA-256。
- SBOM 生成和漏洞扫描门禁。
- 官方下载域名和更新 API。

`V1 Commercial/M8` 必须支持：

- 私有化部署客户端配置服务地址。
- 私有化 release channel。
- 企业自有签名证书或官方代签策略。
- 私有化包名、品牌和服务端公钥配置边界。

后置可选：

- 完全可复现构建。
- 硬件签名设备。
- 多签发布审批。

## 3. 发布制品

首版制品：

- Windows `.msi` 或 `.exe`。
- Ubuntu `.deb`。
- iOS TestFlight / App Store build。
- update manifest。
- SBOM。
- checksums 文件。

签名要求：

- Windows 使用 Authenticode 签名。
- Ubuntu 使用仓库 GPG 签名或包签名，并提供 SHA-256。
- iOS 使用 Apple 签名和 TestFlight/App Store 渠道。
- update manifest 使用独立 Ed25519 release key 签名。
- release private key 不得进入客户端、服务端仓库或 CI 明文变量。

## 4. 更新 Manifest

manifest 必须包含：

- `manifest_version`
- `channel`
- `version`
- `build_number`
- `platform`
- `arch`
- `artifact_url`
- `storage_location_id`
- `artifact_sha256`
- `artifact_size_bytes`
- `min_supported_version`
- `rollout_percent`
- `mandatory`
- `release_notes_url`
- `published_at_epoch_millis`
- `expires_at_epoch_millis`

签名：

```text
manifest_signature = Sign(release_private_key, SHA256(canonical_manifest))
```

规则：

- 客户端必须先验证 manifest 签名，再下载制品。
- 下载后必须校验 `artifact_sha256`。
- 平台安装器签名必须通过系统校验。
- manifest 过期或签名失败时不得更新。
- 降级安装默认禁止，除非 manifest 明确声明安全回滚。
- 强制更新不得绕过用户可见提示和系统安装权限。

## 5. 客户端防伪

客户端必须具备：

- 内置官方 release public key。
- 官方服务端地址默认配置。
- 私有化部署时显式展示服务地址和组织标识。
- 更新检查结果展示渠道、版本和签名状态。
- 安装包来源异常时提示风险。

不得：

- 从未签名 manifest 更新。
- 从非 HTTPS 地址下载官方更新。
- 忽略 hash mismatch。
- 静默替换服务地址。
- 在日志输出 release private key、签名密钥或完整 token。

服务端识别：

- 官方 SaaS 使用固定 HTTPS/WSS 证书链。
- 私有化部署允许企业配置服务端地址，但必须在客户端明显展示当前连接的是私有化服务。
- 私有化配置不能伪装成官方 SaaS。

## 6. 数据模型

需要纳入 Schema Freeze 的逻辑表：

- `client_release_channels`
- `client_release_artifacts`
- `client_update_checks`

`client_release_channels` 关键字段：

- `release_channel_id`
- `channel`
- `scope_type`
- `scope_id`
- `status`
- `release_public_key_id`
- `created_at_epoch_millis`
- `updated_at_epoch_millis`

`client_release_artifacts` 关键字段：

- `artifact_id`
- `release_channel_id`
- `version`
- `build_number`
- `platform`
- `arch`
- `artifact_url`
- `storage_location_id`
- `artifact_sha256`
- `artifact_size_bytes`
- `manifest_version`
- `min_supported_version`
- `rollout_percent`
- `mandatory`
- `release_notes_url`
- `manifest_expires_at_epoch_millis`
- `manifest_signature`
- `sbom_url`
- `status`
- `published_by_actor_type`
- `published_by_account_id`
- `published_by_service`
- `published_at_epoch_millis`
- `revoked_at_epoch_millis`

规则：

- `client_release_channels.scope_type` 首版固定集合为 `official`、`organization`；官方 channel 必须使用 `scope_type = official` 且 `scope_id` 为空，私有化 channel 必须使用 `scope_type = organization` 且 `scope_id` 非空。
- `client_release_channels.status` 首版固定集合为 `active`、`disabled`。
- `client_release_artifacts.status` 首版固定集合为 `draft`、`published`、`revoked`。
- `client_release_artifacts` 是生成 update manifest 的权威元数据来源；manifest canonical 输入必须来自本表字段和 `client_release_channels.channel`，不能由发布脚本临时拼接未落库字段。
- `rollout_percent` 范围固定为 `0..100`；`mandatory = true` 只表示客户端必须提示升级，不能绕过系统安装权限。
- `published_by_actor_type` 取值固定为 `account | service`；M8/Admin 人工发布使用 `published_by_account_id`，CI 受控发布使用 `published_by_service`，二者不得同时为空。
- M8 私有化 release channel 启用数据驻留时，`storage_location_id` 必须指向该组织允许的对象存储位置。
- 官方 channel 和私有化 channel 不得共享未授权制品存储位置。
- V1 Core 中 `storage_location_id` 可以为空或指向默认官方对象存储；指向 `object_storage_locations` 的强 FK 只在 M8 Schema Freeze 建立。

`client_update_checks` 关键字段：

- `update_check_id`
- `account_id`
- `device_id`
- `platform`
- `arch`
- `current_version`
- `channel`
- `event_type`
- `result`
- `artifact_id`
- `manifest_signature_valid`
- `artifact_hash_valid`
- `platform_signature_valid`
- `failure_reason`
- `checked_at_epoch_millis`
- `downloaded_at_epoch_millis`
- `verified_at_epoch_millis`
- `failed_at_epoch_millis`
- `created_at_epoch_millis`

规则：

- 制品撤销后不得再作为更新目标。
- 发布记录必须可追溯到操作者。
- 私有化 channel 必须有明确 `scope_type/scope_id`，不能混入官方 channel。
- `POST /v1/client/update-checks` 是客户端更新全阶段裁剪事件上报入口，`event_type` 固定为 `checked | downloaded | verified | failed`，分别映射审计动作 `client_update_checked/client_update_downloaded/client_update_verified/client_update_failed`。
- `event_type = verified` 时必须上报 manifest 签名、artifact hash 和平台签名校验结果；任一为 false 必须改为 `failed` 并写 `failure_reason`。
- `client_release_artifacts.platform` 首版固定集合为 `windows | ubuntu | ios`；`arch` 首版固定集合为 `x86_64 | aarch64`；Schema Freeze 必须加 CHECK。
- `client_update_checks.platform/arch` 沿用上述固定集合；未知平台或架构必须拒绝并写审计。
- 上报不得包含下载 token、release private key、完整本地路径或安装日志明文。

## 7. API 设计

客户端更新：

```text
GET /v1/client/releases/latest
POST /v1/client/update-checks
```

M8/Admin 或 CI 受控发布管理：

```text
POST /v1/client/release-artifacts
PATCH /v1/client/release-artifacts/{artifact_id}
POST /v1/client/release-artifacts/{artifact_id}/revoke
```

规则：

- `GET /v1/client/releases/latest` 只返回当前平台、架构、渠道可用的 manifest。
- V1 Core/M7 只要求只读更新 API、更新检查记录和 release-check 工具生成签名 manifest、checksums、SBOM、撤销清单及发布证据；不要求对普通客户端开放发布管理写接口。
- 发布管理写接口必须要求管理员权限和 MFA step-up，或作为 CI 受控内部入口执行同等签名、审批和审计门禁。
- 发布、撤销、灰度比例变化必须写审计。
- `GET /v1/client/releases/latest` 返回的 manifest 必须由 `client_release_artifacts` 的权威字段生成并验证 `manifest_signature`；服务端不得返回未落库字段拼出的 manifest。
- `POST /v1/client/update-checks` 必须校验设备签名并按 `event_type` 写固定审计动作；失败原因只能使用固定错误码。
- 客户端不得只依赖 HTTPS 成功就安装更新，必须同时校验 manifest 签名、artifact hash 和平台签名。

## 8. CI 和发布门禁

发布前必须生成：

- 格式化和 lint 结果。
- 测试结果。
- 安装包。
- checksums。
- SBOM。
- 漏洞扫描报告。
- manifest。
- manifest 签名。
- 安装、升级、卸载冒烟证据。

发布阻断：

- 安装包未签名。
- manifest 未签名。
- hash 不匹配。
- SBOM 缺失。
- 高危漏洞未处理或未登记豁免。
- 私有化包混用官方 channel。
- release private key 出现在仓库、日志或 CI 明文变量。

## 9. 审计

必须新增或支持审计动作：

- `client_update_checked`
- `client_update_downloaded`
- `client_update_verified`
- `client_update_failed`
- `client_release_published`
- `client_release_revoked`
- `client_release_rollout_updated`

审计 metadata 允许记录：

- `channel`
- `version`
- `build_number`
- `platform`
- `arch`
- `artifact_sha256`
- `artifact_id`
- `failure_reason`

禁止记录：

- release private key。
- 完整签名密钥材料。
- 完整 access token 或 refresh token。

## 10. 测试要求

必须验证：

- Windows 安装包签名可被系统识别。
- Ubuntu `.deb` 或仓库签名可验证。
- iOS TestFlight/App Store 构建签名链正确。
- manifest 签名正确时客户端接受。
- manifest 签名错误时客户端拒绝。
- artifact hash 不匹配时客户端拒绝。
- manifest 过期时客户端拒绝。
- 被撤销 artifact 不再下发。
- 私有化 channel 不返回官方 channel 制品。
- 更新检查、下载、校验、失败和发布撤销写审计。
- SBOM 存在且与发布版本关联。
- release private key 不出现在仓库、构建日志或发布证据包。
