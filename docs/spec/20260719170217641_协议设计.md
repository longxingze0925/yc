# 协议设计

## 1. 协议目标

协议需要支持：

- 账号登录后的信令协商。
- 设备注册和在线状态。
- 会话邀请、确认、拒绝。
- 连接候选地址交换。
- P2P/Relay 链路选择。
- 视频、输入、剪贴板、文件传输。
- 断线重连和错误上报。

## 2. 协议分层

```text
Signaling Protocol
  HTTP + WebSocket JSON

Session Protocol
  会话身份、权限、密钥、状态机

Transport Protocol
  QUIC UDP
  QUIC Relay
  TLS 443 Relay

Media Protocol
  能力协商、H.264 帧元信息、帧数据和质量控制
  V1 Core 不包含系统音频

Control Protocol
  鼠标、键盘、IME、组合键、滚轮、触控手势、远程重启请求

Data Protocol
  剪贴板、文件、统计、配置
```

## 3. 版本策略

当前协议版本：

```text
PROTOCOL_VERSION = 1
```

规则：

- 所有信令握手必须返回协议版本。
- 主控端和被控端版本不兼容时，服务端拒绝会话并返回错误码。
- 客户端发起 `/ws` Upgrade 时必须提交 `client_supported_protocol_versions` 和 `client_min_protocol_version`；服务端只能从客户端声明集合和服务端受支持集合的交集里选择 `protocol_version`。
- `protocol_version` 必须位于服务端维护的受支持版本集合内，且不得低于客户端声明的 `client_min_protocol_version`；无交集、不支持或低于最低版本时 `/ws` hello 必须失败并返回 `unsupported_version`。
- `client_supported_protocol_versions_hash` 必须被设备上线签名覆盖，防止握手中途被替换或静默降级。
- signed key exchange 时双方必须再次校验 `protocol_version` 与 `session_context_hash` 一致；版本不一致不得继续 `key_confirm`。
- 新增字段必须默认向后兼容。
- 删除或重命名字段必须升级主版本。

WebSocket Upgrade 版本协商字段：

- `/ws` Upgrade 请求必须使用 HTTP Header `X-Rctl-Protocol-Versions` 携带客户端支持版本集合，格式为逗号分隔的十进制 `u16`，例如 `1,2`。
- `/ws` Upgrade 请求必须使用 HTTP Header `X-Rctl-Min-Protocol-Version` 携带客户端最低可接受版本，格式为单个十进制 `u16`。
- Header 名大小写不敏感；版本集合解析后必须去重、升序排序，最大 16 项，且 `client_min_protocol_version` 必须出现在集合中。
- `client_supported_protocol_versions_hash = SHA256(canonical("rctl-protocol-versions-v1", sorted_unique_client_supported_protocol_versions, client_min_protocol_version))`。
- Header 缺失、格式非法、集合为空、版本超出 `u16` 或最低版本不在集合中时，Upgrade 前返回 HTTP 400，JSON body 的 `code = invalid_protocol_version_header`。
- 无版本交集、选中版本低于客户端最低版本或服务端不支持时，Upgrade 前返回 HTTP 426，JSON body 的 `code = unsupported_version`，并包含 `server_supported_protocol_versions`。
- Upgrade 成功后，如果 `hello_response` 中的版本集合、最低版本或 hash 与 Upgrade Header 不一致，Signal 必须发送 WebSocket `error.code = unsupported_version` 并以策略错误关闭连接。

## 4. 标识符

账号：

- `account_id`：服务端生成，不暴露递增 ID。

设备：

- `device_id`：设备生成或服务端分配，稳定不频繁变化。
- `public_key`：设备长期公钥。

会话：

- `session_id`：全局唯一，贯穿 API、Signal、Relay、审计日志。
- `session_id` 逻辑类型为 UUID v4。
- JSON、日志和 API 路径中统一使用 lowercase UUID string。
- 二进制头、签名、HKDF、候选 ID 和 digest 计算中统一使用 16-byte UUID bytes，按 RFC 4122 字节顺序编码。
- 不得在同一个 hash 或签名上下文里混用 UUID 字符串和 16-byte bytes。

消息：

- `sequence`：按 `direction + channel_id` 单调递增，用于排序、排查和重放保护。
- 二进制头中 `sequence` 使用 `u64` 编码；首版业务加密消息有效范围为 `0..2^48-1`，超过该范围必须拒绝并重新协商会话密钥。

安全细节：

- 设备上线签名、会话密钥交换、HKDF 输入、应用层加密和重放保护以 `docs/spec/20260719171718533_安全与密钥协议设计.md` 为准。

## 5. 信令协议

传输：

```text
开发环境：ws://host/ws
生产环境：wss://host/ws
```

/ws 鉴权握手：

```text
1. 客户端发起 WebSocket Upgrade，请求头携带 Authorization: Bearer <access_token>、`X-Rctl-Protocol-Versions` 和 `X-Rctl-Min-Protocol-Version`。
2. 服务端校验 access token，失败直接拒绝或关闭连接；服务端根据客户端和服务端版本交集选择 `protocol_version`，无可用版本时返回 `unsupported_version`。
3. 服务端从 access token 中解析并校验 `account_id`，发送 hello_challenge，包含 `account_id`、`protocol_version`、`server_nonce`、`expires_at_epoch_millis` 和 `server_supported_protocol_versions`。
4. 客户端回复 hello_response，包含 `account_id`、`device_id`、`client_nonce`、`timestamp`、`client_supported_protocol_versions`、`client_min_protocol_version`、`client_supported_protocol_versions_hash`、`client_capabilities`、`client_capabilities_hash`、`device_signature`。
5. `client_capabilities_hash = SHA256(canonical("rctl-client-capabilities-v1", client_capabilities))`，`client_supported_protocol_versions_hash = SHA256(canonical("rctl-protocol-versions-v1", sorted_unique_client_supported_protocol_versions, client_min_protocol_version))`。
6. device_signature = Sign(device_private_key, SHA256(canonical("rctl-ws-hello-v1", server_nonce, client_nonce, account_id, device_id, protocol_version, timestamp, client_supported_protocol_versions_hash, client_capabilities_hash)))。
7. 服务端校验 hello_response 中的 `account_id` 与 access token 一致，校验 `protocol_version` 位于客户端声明集合且不低于 `client_min_protocol_version`；服务端必须独立用 `rctl-client-capabilities-v1` canonical 重算 `client_capabilities_hash`，用 Upgrade Header 和最低版本重算 `client_supported_protocol_versions_hash`，与 `hello_response` 提交字段一致后，才校验设备归属、公钥、nonce、timestamp 和设备签名。
8. 校验通过后服务端写入在线状态，返回 hello_ok。
9. 校验失败返回 auth_failed 并关闭连接。
```

`hello_ok` 必须包含：

- `account_id`
- `device_id`
- `protocol_version`
- `connection_id`
- `client_supported_protocol_versions_hash`
- `client_capabilities_hash`
- `server_supported_protocol_versions`
- `server_time_epoch_millis`

`hello_ok.protocol_version` 必须等于 `hello_challenge.protocol_version`，且已被 `hello_response.device_signature` 覆盖；`hello_ok.client_supported_protocol_versions_hash` 和 `hello_ok.client_capabilities_hash` 必须等于 `hello_response` 中被设备签名覆盖的值。客户端收到不一致版本、hash 或服务端支持版本与 Upgrade 协商结果不一致时，必须关闭连接并清理在线恢复状态。

`client_capabilities` schema 必须覆盖平台、版本、输入、媒体、显示、编解码和传输能力；媒体字段以 `docs/spec/20260719193000004_媒体质量控制与能力协商设计.md` 为准，输入字段以 `docs/spec/20260719193000003_键盘IME与快捷键输入设计.md` 为准。

能力声明规则：

- `client_capabilities_hash` 必须被设备签名覆盖；hash 不一致或签名无效时 WebSocket 握手失败。
- Signal/API 只能把 `client_capabilities` 用于在线状态、粗粒度调度和诊断，不得用未签名或已过期的能力声明决定业务通道安全参数。
- 真实媒体、显示和输入能力协商必须在会话建立后通过应用层端到端加密业务通道完成，并与会话权限校验绑定。

重连规则：

- 每次 WebSocket 重连都必须重新执行账号 token 和设备签名握手。
- 客户端可以在 `hello_response` 中附带待恢复的 `session_id` 列表。
- 服务端恢复会话前必须重新校验账号、设备、权限、会话状态和过期时间。
- access token 过期时客户端必须先通过 API refresh 获取新 token，再重新连接 WebSocket。

设备注册边界：

- 设备首次绑定和公钥上传只走 `POST /v1/devices`。
- WebSocket 不提供 `register_device` 业务入口。
- 未通过 `/ws` 鉴权握手的连接不得发送会话、候选或密钥交换消息。

核心信令方向：

```text
session_invite: signal -> controlled
session_accept_ack: signal -> controller/controlled
session_reject_ack: signal -> controller/controlled
session_cancel_ack: signal -> controller/controlled
session_close_ack: signal -> controller/controlled
connection_candidate: controller <-> signal <-> controlled
connection_state: signal -> controller/controlled
relay_allocated: signal -> controller/controlled
request_observe_token: controller/controlled -> signal
observe_token_issued: signal -> controller/controlled
request_candidate_token: controller/controlled -> signal
candidate_token_issued: signal -> controller/controlled
key_exchange_message: controller <-> signal <-> controlled
key_confirm: controller <-> signal <-> controlled
```

会话权威边界：

- 会话创建、验证码/无人值守 proof 校验、接受、拒绝、取消和关闭只能通过 API 完成。
- Signal 不提供会话创建、验证码/无人值守 proof 校验、接受、拒绝、取消或关闭的写入入口，只根据 API 已持久化的状态推送 `session_invite`、`session_accept_ack`、`session_reject_ack`、`session_cancel_ack`、`session_close_ack` 等通知。
- `connection_state` 是 Signal 向双方推送的非权威状态通知，状态事实源仍是 API 持久化后的 `sessions`、`session_events` 和 `audit_logs`；设备或服务上报连接状态必须走 `POST /v1/sessions/{session_id}/connection-state`。
- `session_cancel_ack` 用于业务通道建立前主控端主动取消通知；`session_close_ack` 用于已接受或已建立业务通道后的关闭通知。两者都必须携带 `session_id`、最终 `status`、`actor_type`、`reason` 和 `event_id`；`actor_type = device` 时必须携带 `actor_device_id` 和 `actor_role`，`actor_type = service` 时必须携带 `actor_service`，`actor_type = system` 时 `actor_device_id`、`actor_role` 和 `actor_service` 必须为空。
- Signal 收到候选或密钥交换消息前，必须确认该 `session_id` 已由 API 创建，且发送设备属于该会话角色；Signal 不接受客户端通过 WebSocket 写入 `connected/degraded/reconnecting/failed` 等会话状态。
- 未达到 API 定义的可建链状态不得通过 Signal 进入候选交换、密钥交换或业务传输阶段：`temporary_code` 必须先 `code_verified` 再由被控端 `accepted`；`account_prompt` 必须先 `waiting_approval` 再由被控端 `accepted`；`unattended` 在 `require_prompt = false` 时必须达到 `unattended_verified`，在 `require_prompt = true` 时必须先完成 proof、进入 `waiting_approval`，再由被控端 `accepted`。

`key_exchange_message` 外层必须包含：

- `session_id`
- `device_id`
- `role`
- `signed_key_exchange_payload`
- `key_exchange_signature`

`signed_key_exchange_payload` 必须包含：

- `session_id`
- `device_id`
- `role`
- `session_context_hash`
- `permissions_digest`
- `session_expires_at_epoch_millis`
- `ephemeral_public_key`
- `key_exchange_nonce`
- `selected_transport_path`
- `selected_candidate_pair_id`
- `relay_node_id`
- `timestamp`

确定性哈希规则：

- `session_context_hash` 和 `key_exchange_transcript_hash` 均使用 SHA-256。
- 哈希输入必须使用固定字段顺序和长度前缀编码：`field_name_len || field_name || value_len || value`。
- 字符串使用 UTF-8，整数使用 big-endian，空值用长度 0 表示。
- `signed_key_exchange_canonical_bytes = canonical("rctl-signed-key-exchange-v1", signed_key_exchange_payload_fields)`；该 exact bytes 同时用于签名校验和 transcript，不得再使用不带域分离标签的 payload bytes。
- `key_exchange_signature = Sign(device_private_key, SHA256(signed_key_exchange_canonical_bytes))`，签名值固定为原始 64-byte Ed25519 signature bytes。
- `key_exchange_transcript_hash` 不得放入 `signed_key_exchange_payload`，避免自引用。
- `key_exchange_transcript_hash = SHA256(controller_signed_key_exchange_canonical_bytes || controller_key_exchange_signature || controlled_signed_key_exchange_canonical_bytes || controlled_key_exchange_signature)`，按 `controller`、`controlled` 顺序拼接带域分离标签的 exact canonical bytes 和原始 64-byte 签名。
- 双方收到对端消息后，必须根据本地会话、权限和候选选择结果重新计算 `session_context_hash` 和 canonical payload，再校验设备签名。
- `account_id` 不直接放入 `signed_key_exchange_payload`，只能通过 `session_context_hash` 覆盖；HKDF `info_base` 必须显式包含 `account_id`。实现不得擅自把 `account_id` 加入 payload 或从 HKDF 中删除。
- HKDF 只能使用双方都验证通过后的 `key_exchange_transcript_hash`。

`key_confirm` 必须包含：

- `session_id`
- `device_id`
- `role`
- `key_exchange_transcript_hash`
- `confirm_mac`
- `timestamp`

规则：

- `confirm_mac = HMAC(key_confirmation_<direction>, canonical("rctl-key-confirm-v1", session_id, device_id, role, key_exchange_transcript_hash, timestamp))`。
- `direction` 不由消息体直接信任，必须由 `role` 推导：`role=controller` 对应 `controller_to_controlled`，`role=controlled` 对应 `controlled_to_controller`。
- `device_id` 必须等于该 `role` 在会话中的设备 ID。
- `timestamp` 必须落在双方客户端约定的短窗口内；首版窗口为接收端本地时间前后各 30 秒。同一 `role + key_exchange_transcript_hash + timestamp + confirm_mac` 不得重复接受。
- 双方必须收发并验证 `key_confirm` 后，才能开始视频、输入、剪贴板和文件传输。
- `key_confirm` 失败必须关闭本次安全会话并写 `key_exchange_failed` 或等价会话事件。

`request_observe_token` 必须包含：

- `session_id`
- `device_id`
- `role`
- `local_socket_nonce`
- `requested_ttl_millis`

`observe_token_issued` 必须包含：

- `session_id`
- `device_id`
- `role`
- `local_socket_nonce`
- `observe_token`
- `observe_token_binding_hash`
- `expires_at_epoch_millis`

observe token 规则：

- `observe_token` 只用于 UDP observe 授权，不得用于 P2P 探测。
- `observe_token_binding_hash = SHA256(canonical("rctl-observe-token-binding-v1", session_id, device_id, role, local_socket_nonce, expires_at_epoch_millis))`。
- 客户端只能提交 `requested_ttl_millis`，最终 `expires_at_epoch_millis` 必须由 signal-server 生成。
- signal-server 必须设置服务端上限；首版 observe token 最大有效期 30 秒。
- UDP observe 服务必须校验 token 签名/HMAC、绑定字段、过期时间和设备角色。
- UDP observe 服务校验通过后必须生成短期 `observe_result_id`，把 `session_id`、`device_id`、`role`、`local_socket_nonce`、`observed_endpoint`、`source = udp_observed`、`expires_at_epoch_millis` 和 `observe_result_binding_hash` 写入 Redis 短期记录。
- UDP observe 响应必须返回 `observed_endpoint`、`observe_result_id`、`observe_result_binding_hash` 和 `expires_at_epoch_millis`；客户端只能用该结果为最终 `udp_p2p` 候选请求 `candidate_token`。
- `observe_result_binding_hash = SHA256(canonical("rctl-observe-result-binding-v1", session_id, device_id, role, local_socket_nonce, observed_endpoint, source, expires_at_epoch_millis, observe_result_id))`。
- `observe_token` 不得落库，不得写日志；日志只允许记录 `observe_token_binding_hash` 前 8 字节和错误码。

`request_candidate_token` 必须包含：

- `session_id`
- `device_id`
- `role`
- `candidate_id`
- `kind`
- `endpoint`
- `source`
- `relay_node_id`，LAN Direct 和 UDP P2P 必须为空；Relay 候选不请求 `candidate_token`
- `observe_result_id`，仅 `source = udp_observed` 时必填，其他来源为空
- `observe_result_binding_hash`，仅 `source = udp_observed` 时必填，其他来源为空
- `local_interface_claim_hash`，仅 `source = local_interface` 时必填，其他来源为空
- `local_interface_signature`，仅 `source = local_interface` 时必填，其他来源为空
- `interface_name_hash`，仅 `source = local_interface` 时必填，其他来源为空
- `interface_index_hash`，仅 `source = local_interface` 时必填，其他来源为空
- `local_socket_nonce`，仅 `source = local_interface` 时必填，其他来源为空
- `timestamp_epoch_millis`，仅 `source = local_interface` 时必填，其他来源为空
- `requested_ttl_millis`

`candidate_token_issued` 必须包含：

- `session_id`
- `device_id`
- `role`
- `candidate_id`
- `candidate_token`
- `candidate_token_binding_hash`
- `expires_at_epoch_millis`

`candidate_token_issued` 是探测授权响应，不是持久化候选记录；`candidate_token`、`candidate_token_binding_hash` 和 `expires_at_epoch_millis` 是探测用临时附加物，不得落库、不得写日志、不得跨会话复用。

候选 token 规则：

- `candidate_token` 是短有效期不透明 token，由 signal-server 签发，只用于最终候选的 P2P 探测授权。
- `candidate_token_binding_hash = SHA256(canonical("rctl-candidate-token-binding-v1", session_id, device_id, role, candidate_id, kind, endpoint, source, observe_result_id, expires_at_epoch_millis))`。
- signal-server 签发 token 前必须校验会话、设备、角色和候选字段；`source = udp_observed` 时必须校验 Redis 中的 `observe_result_id`、`observe_result_binding_hash`、`endpoint`、角色和过期时间一致，否则拒绝签发。
- 客户端只能提交 `requested_ttl_millis`，最终 `expires_at_epoch_millis` 必须由 signal-server 生成。
- signal-server 必须设置服务端上限；首版 candidate token 最大有效期 60 秒。
- UDP observe 不得接收 `candidate_token`，必须使用 `observe_token`。
- P2P 探测时，候选拥有方通过 signal-server 把 `candidate_token` 发给对端；对端探测该候选时必须原样带回。
- LAN Direct 候选不需要 UDP observe，但仍必须为最终 P2P 探测请求 `candidate_token`；LAN Direct 固定使用 `kind = lan_direct`、`source = local_interface`，`observe_result_id` 为空。
- LAN Direct 候选必须由候选拥有方设备签名声明本机接口快照，`local_interface_claim_hash = SHA256(canonical("rctl-local-interface-claim-v1", session_id, device_id, role, candidate_id, endpoint, interface_name_hash, interface_index_hash, local_socket_nonce, timestamp_epoch_millis))`，`local_interface_signature = Sign(device_private_key, local_interface_claim_hash)`。
- Signal 必须按候选 ID 公式使用 `session_id/device_id/role/kind/endpoint/source/relay_node_id` 重新计算 `candidate_id`；LAN Direct 和 UDP P2P 的 `relay_node_id` 必须按 0 长度空值参与计算。Signal 还必须用 LAN 专用字段重新计算 `local_interface_claim_hash`，再校验 `local_interface_signature`；只在签名有效、设备属于会话且候选数量未超限时签发 token，不得只信任客户端提交的 hash。
- LAN Direct `timestamp_epoch_millis` 与服务端时间偏差首版不得超过 30 秒；同一 `device_id + session_id + local_socket_nonce + candidate_id` 不得重复接受。
- LAN Direct 的 `endpoint` 只能使用本机接口单播地址和高位临时 UDP 端口；首版禁止 `unspecified`、loopback、multicast、broadcast、documentation/test-net、link-local 和公网地址作为 `lan_direct` 候选。
- 每个设备每个会话首版最多 8 个 LAN Direct 候选；P2P 探测必须限速，只发送携带 `candidate_token` 的最小探测包，不得把 LAN Direct 机制变成任意内网端口扫描。
- 探测方本地必须再次判断远端 LAN Direct 地址是否在本机可路由的局域网接口范围内；不在本机局域网范围内的 LAN Direct 候选必须跳过，不能退化为公网或任意私网探测。
- UDP P2P 候选固定使用 `kind = udp_p2p`、`source = udp_observed`；Relay 候选固定使用 `kind = quic_relay | tls_443_relay`、`source = relay_allocated`。
- `candidate_id` 必须由候选拥有方、signal-server 和探测方分别用相同字段集合独立重算，不能从信令消息中直接照抄作为信任来源；非 Relay 候选的 `relay_node_id` 必须按 0 长度空值参与计算。
- P2P 探测接收端不需要持有服务端密钥，只校验收到的 token 是否等于本地候选记录中的 token，并校验 `candidate_token_binding_hash` 和 probe nonce；同一 `session_id + candidate_id + role + probe_nonce` 重放必须在 candidate token 有效期内被拒绝。
- `candidate_token` 不得落库，不得写日志；日志只允许记录 `candidate_token_binding_hash` 前 8 字节和错误码。

`relay_allocated` 必须包含：

- `session_id`
- `device_id`
- `role`
- `controller_device_id`
- `controlled_device_id`
- `relay_node_id`
- `transport`
- `public_endpoint`
- `permissions_digest`
- `relay_token_epoch`
- `issued_at_epoch_millis`
- `expires_at_epoch_millis`
- `relay_token_id`
- `session_relay_token`
- `token_binding_hash`

Relay 建连认证：

- 客户端连接 QUIC Relay 或 TLS 443 Relay 后，第一条控制消息必须是 `relay_open`。
- `session_relay_token` 是角色级 token；Signal/API 必须分别给主控端和被控端签发不同 token。
- `relay_allocated` 必须按角色分别下发给主控端和被控端；客户端构造 `relay_open` 时必须使用 `relay_allocated` 明文字段，不得依赖解析 `session_relay_token` 获得绑定字段。
- `relay_token_binding = canonical("rctl-relay-token-binding-v1", session_id, device_id, role, controller_device_id, controlled_device_id, relay_node_id, transport, permissions_digest, relay_token_epoch, issued_at_epoch_millis, expires_at_epoch_millis, relay_token_id)`。
- `token_binding_hash = SHA256(relay_token_binding)`。
- `session_relay_token` 必须是结构化签名 token 或等价可验证令牌，payload 至少包含 `session_id`、`device_id`、`role`、`controller_device_id`、`controlled_device_id`、`relay_node_id`、`transport`、`permissions_digest`、`relay_token_epoch`、`issued_at_epoch_millis`、`expires_at_epoch_millis` 和 `relay_token_id`。
- `relay_open` 必须包含 `session_id`、`device_id`、`role`、`controller_device_id`、`controlled_device_id`、`relay_node_id`、`transport`、`permissions_digest`、`relay_token_epoch`、`issued_at_epoch_millis`、`expires_at_epoch_millis`、`relay_token_id`、`relay_open_nonce`、`session_relay_token`、`token_binding_hash`、`device_signature`。
- `device_signature = Sign(device_private_key, SHA256(canonical("rctl-relay-open-v1", relay_open_without_signature)))`。
- `relay_open_without_signature` 字段顺序固定：`session_id`、`device_id`、`role`、`controller_device_id`、`controlled_device_id`、`relay_node_id`、`transport`、`permissions_digest`、`relay_token_epoch`、`issued_at_epoch_millis`、`expires_at_epoch_millis`、`relay_token_id`、`relay_open_nonce`、`session_relay_token`、`token_binding_hash`。该顺序与 `rctl-relay-token-binding-v1` 一致；不包含 `device_signature`本身，也不包含 `relay_open_payload 中可变扩展字段`。canonical 编码与协议附录定义的长度前缀字段编码一致；字符串 UTF-8、整数 big-endian、UUID 16 字节、空 `relay_node_id` 使用 0 长度 null 字段参与计算。跨实现不同字段顺序、重复签名 `device_signature`、直接签名未 hash 的 canonical bytes 或重复使用子集 binding hash 必须拒绝。
- Relay 必须从 `relay_open` 和 token payload 中重新计算 `token_binding_hash`，并校验 `session_relay_token`、设备签名、设备角色、Relay 节点、transport、过期时间和 nonce 未重放。
- Relay 校验设备签名时，设备公钥、key version 和撤销状态必须来自 `relay:session:{session_id}:authorization` 或等价服务端 introspection；不得只信任 token payload 或客户端自带公钥。
- token 重放判定按 `relay_token_id + role + relay_open_nonce` 记录；同一角色同一 nonce 不得重复接受，不得把主控端 token 用于被控端，短断重连必须使用新的 `relay_open_nonce`。首版 `relay_open_nonce` 去重记录保存到 token 过期后至少 60 秒。
- `session_relay_token` 首版最大 TTL 为 60 秒；跨区策略或弱网策略需要更短 TTL 时以更严格值为准。
- Relay 接受 `relay_open` 前必须读取服务端签发的短期会话授权状态，确认 `session_id` 仍处于可建链或已连接状态、`allow_relay = true`、`permissions_digest` 未变化、`relay_token_epoch` 未被撤销、`relay_node_id` 仍允许，且对应设备公钥版本未撤销。
- 会话关闭、权限变化、`allow_relay` 变为 false、策略关闭会话或 Relay 节点被禁用时，api-server/signal-server 必须提升或撤销 `relay_token_epoch` 并写入短期撤销状态；旧 token 即使未过期也必须被 Relay 拒绝。
- Relay 节点被禁用后，撤销状态对所有新 `relay_open` 请求的生效 SLO 为 2 秒内；超过 SLO 仍接受新请求必须视为发布阻断问题。
- Relay 校验通过前不得转发任何业务密文。
- `session_relay_token` 不得写入日志；日志只允许记录 token hash 前 8 字节或错误码。

错误响应：

```json
{
  "type": "error",
  "code": "invalid_payload",
  "message": "invalid signaling json"
}
```

## 6. 二进制消息头

当前二进制消息头长度：

```text
40 bytes
```

结构：

```text
magic: 4 bytes = RCTL
version: u16
kind: u16
flags: u16
channel_id: u16
session_id: u128
sequence: u64
payload_len: u32
```

用途：

- QUIC 数据通道上的业务消息。
- 视频帧元信息。
- 输入事件。
- 文件分片。
- 统计和错误上报。

`device_online`、会话邀请/接受/拒绝/取消/关闭、候选交换和连接状态属于 API/Signal 控制面 JSON 消息，不得作为业务数据面 kind 发送。

`channel_id` 固定表：

| channel_id | 名称 | 可靠性和优先级 |
| --- | --- | --- |
| 0 | `secure_control` | 可靠有序，最高优先级 |
| 1 | `input_reliable` | 可靠有序，高优先级 |
| 2 | `input_realtime` | QUIC DATAGRAM，可丢弃，仅鼠标移动 |
| 3 | `media_control` | 可靠有序，高于视频 |
| 4 | `video` | 可靠独立帧流，允许丢弃过期帧 |
| 5 | `clipboard` | 可靠有序，默认关闭 |
| 6 | `file_transfer` | 可靠有序，最低业务优先级 |
| 7 | `device_control` | 可靠有序，高优先级 |
| 8 | `telemetry` | QUIC DATAGRAM，可丢弃 |

QUIC 映射规则：

- 每个远控会话使用一条已认证 QUIC connection；channel 0、1、3、5、6、7 各使用独立的长期双向 stream。
- channel 4 每个视频帧使用独立单向 stream，`video_frame_info` 后紧跟同一帧的一个或多个 `video_frame_data`；接收端可以取消过期帧 stream，不能让旧帧阻塞输入。
- channel 2 和 8 使用 QUIC DATAGRAM。对端不支持 DATAGRAM 时，鼠标移动合并为最新事件后走 channel 1；统计走 channel 0 的低优先级可靠消息。
- 鼠标按键、滚轮、物理键、文本、IME、快捷键和 `release_all_keys` 必须走 channel 1，不得使用可丢弃 DATAGRAM。
- 所有数据面消息，包括 DATAGRAM，仍必须携带 40-byte header 并经过应用层 E2EE；Relay 只按外层长度和会话路由转发密文。
- TLS 443 fallback 在单条 TLS 连接上按 40-byte header 逻辑复用 channel；发送调度顺序固定为 0/1/7、3、4、5、6、8，并对 channel 2 只保留最新鼠标移动。
- 未知 kind 或 kind/channel 不匹配必须返回 `unsupported_message_kind` 或 `invalid_channel` 并关闭对应业务通道；不得静默降级解析。

## 8. 业务 payload 最小结构

`video_frame_info`：

- `session_id`
- `display_id`
- `frame_id`
- `codec`
- `width`
- `height`
- `stride`
- `pixel_format`
- `color_space`
- `rotation`
- `is_keyframe`
- `pts_millis`
- `frame_bytes_len`

规则：

- `codec` 首版固定支持 `h264`。
- `frame_id` 在单显示器单方向内递增。
- `video_frame_data` 必须引用同一 `frame_id`。
- 媒体能力协商、质量档位、动态码率、关键帧请求和硬件编解码 fallback 以 `docs/spec/20260719193000004_媒体质量控制与能力协商设计.md` 为准。

媒体控制消息：

- `media_capabilities`：`session_id`、`role`、`codec_capabilities`、`display_capabilities`、`input_capabilities`。
- `media_config_request`：`session_id`、`display_id`、`preferred_codec`、`max_width`、`max_height`、`max_fps`、`max_bitrate_kbps`、`quality_profile`、`color_mode`、`timestamp_epoch_millis`。
- `media_config_state`：`session_id`、`display_id`、`codec`、`width`、`height`、`fps`、`bitrate_kbps`、`profile`、`pixel_format`、`color_mode`、`hardware_acceleration`、`state`、`reason`、`timestamp_epoch_millis`。
- `media_quality_request`：`session_id`、`display_id`、`quality_profile`、`reason`、`timestamp_epoch_millis`。
- `media_quality_state`：`session_id`、`display_id`、`rtt_ms`、`loss_ppm`、`jitter_ms`、`bitrate_kbps`、`fps`、`dropped_frames`、`encode_ms`、`decode_ms`、`cpu_percent`、`memory_mb`、`timestamp_epoch_millis`。
- `keyframe_request`：`session_id`、`display_id`、`reason`、`last_received_frame_id`、`timestamp_epoch_millis`。

规则：

- V1 媒体控制消息必须走应用层端到端加密业务通道。
- 服务端可保存的能力摘要仅限 `/ws` hello 中已由设备签名覆盖的粗粒度 `client_capabilities`；会话内 `media_capabilities` payload 不得被 Signal/API 明文保存或解析。
- `keyframe_request` 必须限流。
- H.265、AV1、4:4:4 和 HDR 只预留，不作为 V1 Core 验收能力。
- 系统音频采集、传输和远端播放只预留，不作为 V1 Core 验收能力。
- 除 Relay/Signal 转发所需外层元数据和聚合统计外，`media_capabilities`、`display_list`、`display_select`、`display_changed`、`input_event`、剪贴板、文件传输、隐私屏、本地输入保护和远程重启 payload 都必须走应用层端到端加密业务通道。

`input_event`：

- `session_id`
- `event_id`
- `display_id`
- `input_kind`
- `key_event_kind`
- `physical_code`
- `scan_code`
- `virtual_key`
- `logical_key`
- `x_norm`
- `y_norm`
- `button`
- `key_code`
- `modifiers`
- `wheel_delta_x`
- `wheel_delta_y`
- `text`
- `composition_text`
- `composition_state`
- `keyboard_layout`
- `is_auto_repeat`
- `timestamp_epoch_millis`

规则：

- `input_kind` 首版支持 `mouse_move`、`mouse_button`、`mouse_wheel`、`physical_key`、`text_commit`、`ime_composition`、`shortcut`、`touch_gesture`、`release_all_keys`。
- `key_event_kind` 支持 `down`、`up`、`repeat`、`tap`。
- 坐标使用 `0.0..1.0` 归一化坐标，按当前 `display_id` 映射到被控端显示器。
- 普通文本输入优先使用 `text_commit`；快捷键、功能键和修饰键优先使用 `physical_key` 或 `shortcut`。
- `text` 和 `composition_text` 只用于输入事件，不得写入日志、审计或服务端明细。
- 断开、重连超时、焦点丢失和会话关闭时必须执行 `release_all_keys`。
- 没有 `input_control` 权限时必须拒绝 `input_event`。
- 键盘布局、中文 IME、组合键和平台 unsupported 规则以 `docs/spec/20260719193000003_键盘IME与快捷键输入设计.md` 为准。

多显示器消息：

- `display_list`：`session_id`、`displays[]`。
- `display_select`：`session_id`、`display_id`。
- `display_changed`：`session_id`、`reason`、`displays[]`。
- `displays[]` 元素必须包含 `display_id`、`name`、`width`、`height`、`scale_factor`、`is_primary`。

剪贴板消息：

- `clipboard_permission_request`：`session_id`、`request_id`、`direction`、`reason`、`timestamp_epoch_millis`。
- `clipboard_permission_state`：`session_id`、`request_id`、`enabled`、`accepted`、`confirmed_by_device_id`、`reason`、`timestamp_epoch_millis`。
- `clipboard_text`：`session_id`、`direction`、`content_len`、`text_utf8`、`timestamp_epoch_millis`。
- 没有 `clipboard` 权限时必须拒绝。
- 临时协助或反诈策略要求二次提示时，`clipboard_text` 只能在被控端通过 `clipboard_permission_state.accepted = true` 后发送；`confirmed_by_device_id` 必须等于会话被控端设备，授权状态通过设备签名的裁剪元数据上报写审计，不得上报剪贴板内容。
- `text_utf8` 不得写入日志或审计明细。

文件传输消息：

- `file_transfer_request`：`file_transfer_id`、`session_id`、`direction`、`file_name`、`file_size_bytes`、`sha256`。
- `file_transfer_ack`：`file_transfer_id`、`accepted`、`reason`、`confirmed_by_controlled`、`confirmed_by_device_id`、`timestamp_epoch_millis`。
- `file_chunk`：`file_transfer_id`、`chunk_index`、`offset`、`bytes_len`、`chunk_sha256`、`data`。
- `file_transfer_cancel`：`file_transfer_id`、`cancelled_by_device_id`、`reason`、`timestamp_epoch_millis`。
- 没有 `file_transfer` 权限时不得创建传输任务。
- 临时协助或反诈策略要求二次提示时，`file_transfer_ack.accepted = true` 必须表示被控端本地显式确认，不能只表示协议层收到请求；`confirmed_by_device_id` 必须等于会话被控端设备。
- 文件传输请求、确认、拒绝、取消和完成必须写审计，但审计不得保存文件内容。
- 文件通道必须独立限速，不能阻塞控制通道。
- `file_name` 只作为展示名和建议名，不得包含路径语义；接收端必须拒绝路径穿越、绝对路径、空名、控制字符、保留设备名和平台非法字符。
- 接收端保存文件必须先写同目录临时文件，完成 `sha256` 校验后原子落盘；取消、失败、hash 不匹配或磁盘不足时必须清理临时文件。
- 默认不覆盖同名文件；覆盖必须由接收端显式确认并写裁剪审计。

隐私屏和本地输入保护消息：

- `privacy_mode_request`：`session_id`、`request_id`、`mode`、`enabled`、`reason`、`timestamp_epoch_millis`。
- `privacy_mode_state`：`session_id`、`mode`、`state`、`platform_status`、`error_code`、`timestamp_epoch_millis`。
- `privacy_mode_restore`：`session_id`、`mode`、`reason`、`timestamp_epoch_millis`。

规则：

- `mode` 只能是 `privacy_screen` 或 `block_local_input`。
- 没有 `privacy_screen` 权限时必须拒绝隐私屏请求。
- 没有 `block_local_input` 权限时必须拒绝本地输入保护请求。
- 首版 step-up 在会话创建、权限授予或本地安全设置变更前完成，并进入 `permissions_digest` 或策略评估结果；运行时 `privacy_mode_request` 走应用层端到端加密业务通道，不再额外调用服务端 step-up API。
- 如果后续要对每次运行时开关单独 step-up，必须另行设计类似远程重启的 API 请求、canonical hash 和端点校验流程。
- 运行时状态必须由被控端上报，主控端不得自行标记成功。
- 会话断开、重连超时或权限变化时，被控端必须恢复显示和输入状态。
- 隐私屏和本地输入保护具体约束以 `docs/spec/20260719190000003_隐私屏与本地输入保护设计.md` 为准。

远程重启消息：

- `reboot_request`：`session_id`、`reboot_request_id`、`mode`、`reason`、`countdown_seconds`、`reconnect_after_reboot`、`api_request_hash`、`timestamp_epoch_millis`。
- `reboot_state`：`session_id`、`reboot_request_id`、`state`、`error_code`、`auto_resume_consent`、`local_consent_token_hash`、`timestamp_epoch_millis`。
- `reboot_cancel`：`session_id`、`reboot_request_id`、`reason`、`timestamp_epoch_millis`。
- `reboot_resume_hint`：`old_session_id`、`reboot_request_id`、`controlled_device_id`、`resume_expires_at_epoch_millis`、`controlled_device_signature`。

规则：

- 远程重启消息必须走应用层端到端加密业务通道；Signal/API/Relay 不得解密或校验业务明文。
- `reboot_request.mode` 固定枚举为 `normal | safe_mode_reserved`；`safe_mode_reserved` 首版只保留，不实现。
- `reboot_resume_hint` 必须由被控端设备长期私钥签名：`controlled_device_signature = Sign(controlled_device_private_key, SHA256(canonical("rctl-reboot-resume-hint-v1", old_session_id, reboot_request_id, controlled_device_id, resume_expires_at_epoch_millis)))`。主控端解密后必须校验签名、设备 ID、旧会话、恢复窗口和 `reboot_request_id` 后才能调用 `/resume`。
- 被控端执行前必须确认 API 已创建有效 `reboot_request_id`，并验证 `api_request_hash`。
- `api_request_hash` 固定为 `reboot_api_request_hash = SHA256(canonical("rctl-reboot-api-request-v1", session_id, reboot_request_id, controller_account_id, controller_device_id, controlled_device_id, mode, reason_hash, countdown_seconds, reconnect_after_reboot, allow_remote_reboot, allow_remote_reboot_last_changed_at_epoch_millis, step_up_challenge_id, step_up_verified_at_epoch_millis, step_up_expires_at_epoch_millis, idempotency_key_hash, policy_evaluation_id, policy_evaluated_at_epoch_millis, permissions_digest, permissions_digest_last_changed_at_epoch_millis, request_status, created_at_epoch_millis, expires_at_epoch_millis))`。
- `request_status` 是生成 `api_request_hash` 时的不可变状态快照，固定枚举为 `pending | accepted`；V1 当前请求状态必须由被控端在线调用 API 单独确认，不提供离线签名状态回执替代路径。
- 原始 reason 只允许出现在应用层端到端加密的 `reboot_request` 业务消息中；API、Signal、Relay、数据库和审计 metadata 只能保存 `reason_hash`，不得保存或解析 reason 自由文本。
- `reason_hash = SHA256(reason_utf8)`，`idempotency_key_hash = SHA256(idempotency_key)`；被控端执行前必须用 E2EE 消息中的 `reason` 重新计算 `reason_hash` 并确认其与 `api_request_hash` 输入一致；原始 reason 和幂等键不得进入日志或 Relay。
- 被控端执行前必须确认 step-up 未过期，且 `step_up_verified_at_epoch_millis` 不早于 `permissions_digest_last_changed_at_epoch_millis`、`allow_remote_reboot_last_changed_at_epoch_millis` 和 `policy_evaluated_at_epoch_millis` 三者最大值。
- `reboot_state` 中的本地同意状态只能由被控端设备签名上报；自动恢复一次必须绑定 `local_consent_token_hash` 且只能消费一次。
- 被控端校验 `api_request_hash` 时必须通过 `GET /v1/reboot-requests/{reboot_request_id}` 在线确认当前 `status` 仍为 `pending/accepted` 范围内的有效状态，且 `session_id`、主控设备、被控设备、`permissions_digest` 和过期时间一致；V1 不接受离线或 Signal 转发的签名状态回执。
- 旧会话关闭后不得继续投递业务消息；重启后恢复必须创建新会话并重新完成权限评估、候选交换、signed key exchange 和 `key_confirm`。
- 远程重启进入 `accepted/executing/device_offline/resume_ready/resumed` 任一状态、收到有效 `reboot_resume_hint`、系统重启、被控端服务重启超过短断窗口或旧会话关闭后，必须立即关闭旧会话的 30 秒短断密钥复用窗口；恢复窗口 10 分钟只适用于 `reboot_resume_token` 换取新会话，不允许复用旧会话密钥。
- 远程重启边界以 `docs/spec/20260719193000002_远程重启与会话恢复设计.md` 为准。

## 9. 通道优先级

控制通道：

- 最高优先级。
- 可靠、有序。
- 鼠标键盘不能被视频和文件传输阻塞。

视频通道：

- 低延迟优先。
- 允许丢弃过期帧。
- 不允许旧帧堆积造成画面延迟扩大。

文件通道：

- 可靠。
- 独立限速。
- 不抢占控制通道。

统计通道：

- 周期上报。
- 允许低优先级。

## 10. 连接候选

候选类型：

- `lan_direct`
- `udp_p2p`
- `quic_relay`
- `tls_443_relay`

候选字段（仅作为协议附录的说明，不是持久化候选记录的字段）：

- 持久候选字段：`candidate_id`、`session_id`、`device_id`、`role`、`kind`、`endpoint`、`source`、`observe_result_id`、`priority`、`rtt_ms`、`loss_ppm`、`jitter_ms`、`relay_node_id`。这些是 `connection_candidates` 表只保存的字段。
- 探测授权临时附加物（不入库、不写日志）：`candidate_token`、`candidate_token_binding_hash`、`expires_at_epoch_millis`。这些只允许在内存、Redis 短期 key 和探测包往返过程中持有，不是 `connection_candidates` 表字段。

候选 ID：

```text
candidate_id = first_128_bits(SHA256(canonical("rctl-candidate-id-v1", session_id, device_id, role, kind, endpoint, source, relay_node_id)))
candidate_pair_id = first_128_bits(SHA256(canonical("rctl-candidate-pair-id-v1", session_id, controller_candidate_id, controlled_candidate_id, selected_transport_path, relay_node_id)))
```

规则：

- `canonical(...)` 必须使用安全文档定义的 length-prefixed 字段编码；字符串按 UTF-8，整数按 big-endian，UUID 按 16 字节，空 `relay_node_id` 用 0 长度 null 字段参与计算。
- `candidate_id` 是候选自身的稳定 ID，不得包含 `candidate_token`、`candidate_token_binding_hash` 或服务端最终生成的 `expires_at_epoch_millis`，避免 token 签发前后 ID 不一致。
- `observe_result_id` 不参与 `candidate_id`，只参与 `candidate_token_binding_hash` 和 `source = udp_observed` 的来源校验。
- 双方必须使用同一候选字段计算 `candidate_id` 和 `candidate_pair_id`。
- Relay 路径下 `relay_node_id` 必须参与 `candidate_pair_id`。
- 非 Relay 路径下 `relay_node_id` 必须为空值参与计算。

选择原则：

- 先按路径优先级排序。
- 同路径内选 RTT、丢包、抖动综合最优。
- 连接中可切换到更稳定路径，但只要 `candidate_pair_id` 或 Relay 节点变化，就必须重新 signed key exchange。
- 候选采集、UDP 打洞、Relay 分配和超时策略以 `docs/spec/20260719171718533_NAT穿透与连接状态机设计.md` 为准。

## 11. 断线重连

必须支持：

- 网络短断恢复。
- Wi-Fi/热点切换。
- Relay 节点失败后重新分配。
- 会话恢复时重新校验权限。
- 远程重启后新会话恢复。

限制：

- 断线超过服务端配置超时时间后，会话关闭。
- 被控端主动断开后不得自动重连。
- 远程重启关闭旧会话，重启后不得复用旧会话密钥。

## 12. 协议安全

禁止：

- 明文传输验证码、无人值守密码、私钥。
- 日志记录剪贴板内容和文件内容。
- 未经授权的输入事件投递。

必须：

- 信令层校验账号和设备权限。
- 会话层校验权限位。
- 传输层绑定 `session_id`。
- 密钥交换消息必须携带设备签名，且绑定账号、会话、设备、权限、传输路径和候选对。
- 所有敏感操作写审计。
- 验证码和无人值守凭据流程以 `docs/spec/20260719171718533_认证与无人值守凭据设计.md` 为准。
- 账号 MFA、反诈与滥用、条件访问、隐私屏、本地输入保护、远程重启、键盘/IME、媒体协商、会话录制边界、企业区域驻留和客户端防伪以对应专项文档为准。
