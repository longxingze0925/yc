# 远程重启与会话恢复设计

## 1. 目标

远程重启是远控软件的常见维护能力，但它不是远程命令行。首版只允许在已授权远控会话中发起“重启被控设备并尝试恢复连接”，不提供任意命令执行，不绕过操作系统权限，不复用旧会话密钥。

目标：

- 支持被控设备重启请求、倒计时、取消和状态回传。
- 重启前必须完成权限、策略和高风险 step-up 校验。
- 重启后只能创建新安全会话，不能复用旧业务密钥。
- 临时协助和无人值守场景的恢复授权边界清晰。
- 所有请求、执行、失败、取消和恢复尝试可审计。

## 2. 范围

`V1 Core/M6` 实现：

- 已连接会话内请求重启被控设备。
- 被控端本地提示、倒计时和取消。
- 重启后被控服务自动上线。
- 主控端在短窗口内显示“等待设备重启恢复”并可发起新会话。
- Windows Service 和 Ubuntu systemd 服务自启动恢复。
- 远程重启审计和失败原因。

`V1 Commercial/M8` 增强：

- 企业策略控制哪些角色可以请求远程重启。
- 批准流、维护窗口和重启计划。
- 设备组批量重启可以后置，不进入 V1 Core。

不做：

- 任意远程命令行。
- 静默重启。
- 绕过 UAC、安全桌面、系统更新或关机权限。
- 主控端或被控端主动断开后的无条件自动重连。
- 复用重启前的应用层会话密钥。

## 3. 权限和策略

远程重启使用独立策略字段，不加入 V1 的 9 项 `permissions_digest`：

- `allow_remote_reboot`

原因：

- 远程重启是高风险会话动作，不是业务通道持续能力。
- V1 的 9 项 `permissions_digest` 已作为会话密钥输入冻结；重启授权由 API 和端侧签名请求控制。
- 如果未来要把远程重启做成可持续会话能力，必须先升级权限 canonical 模型和协议主版本。

规则：

- 默认关闭。
- 临时协助默认要求被控端当次确认。
- 无人值守场景也必须有设备本地允许项和账号 step-up。
- 企业策略只能收紧，不能放宽被控端本地关闭项。
- 请求远程重启必须完成高风险 step-up。
- 被控端本地或设备策略中的 `allow_remote_reboot` 从 false 改 true 必须先完成高风险 step-up 并写审计；从 true 改 false 不需要 step-up。
- 创建远程重启请求时必须校验 step-up 未过期，且 `step_up_verified_at_epoch_millis >= max(permissions_digest_last_changed_at_epoch_millis, allow_remote_reboot_last_changed_at_epoch_millis, policy_evaluated_at_epoch_millis)`；权限、远程重启允许项或策略评估在 step-up 后变化时，旧 step-up 不能复用。
- 被控端执行前必须验证 API 已签发的 `reboot_request_id` 和应用层端到端加密的 `reboot_request` 一致。

## 4. 流程

已连接会话中请求重启：

```text
1. 主控端发起远程重启请求。
2. api-server 校验账号、设备签名、会话状态、策略、step-up 和幂等键。
3. api-server 创建 `reboot_request_id`，状态为 `pending`。
4. 主控端通过应用层端到端加密业务通道发送 `reboot_request`。
5. 被控端校验本地策略、API 请求状态、会话 ID、主控设备和 request hash。
6. 被控端显示本地倒计时和取消入口。
7. 倒计时结束且未取消时执行系统重启。
8. 旧会话关闭，原因是 `controlled_reboot_requested`。
9. 被控服务随系统启动后重新上线。
10. 主控端使用恢复意图创建新会话，并重新完成权限评估、候选交换、signed key exchange 和 key_confirm。
```

临时协助恢复：

- 重启前被控端必须明确同意“重启后继续协助”。
- 重启后恢复窗口首版固定最大 10 分钟。
- 恢复时仍必须弹出被控端确认，除非重启前被控端明确选择“本次重启后自动恢复一次”。
- 自动恢复一次必须由被控端本地用户在倒计时提示中显式选择，不能由主控端或服务端远程代选。
- 自动恢复一次只能绑定原主控账号、原主控设备、原被控设备、原 `reboot_request_id` 和本地 `local_consent_token_hash`，且只能消费一次。
- 自动恢复一次不把 `local_consent_token` 明文交给主控端或服务端；被控端重启上线后必须用设备签名提交 `local_consent_proof_hash = SHA256(canonical("rctl-reboot-local-consent-proof-v1", local_consent_token_hash, reboot_request_id, controlled_device_id, resume_challenge_nonce, timestamp_epoch_millis))`，API 校验签名、challenge、hash、设备和一次性消费状态后才允许跳过本次被控端弹窗确认。
- 自动恢复一次被消费、撤销、过期或恢复失败后必须失效，后续恢复必须重新弹出被控端确认。

无人值守恢复：

- 必须重新执行无人值守 proof 或使用短期 `reboot_resume_token` 换取新的 unattended challenge。
- `reboot_resume_token` 只能创建恢复意图或换取新的 unattended challenge，不能直接替代无人值守 proof、被控端确认、权限评估或新会话密钥交换。
- `reboot_resume_token` 必须绑定原 `controller_account_id`、`controller_device_id`、`controlled_device_id`、旧 `session_id`、`reboot_request_id`、`permissions_digest`、过期时间和一次性消费状态；首版最大有效期 10 分钟。
- `reboot_resume_token` 格式固定为 `base64url(reboot_resume_token_id) "." base64url(reboot_resume_token_secret)`。
- `reboot_resume_token_id` 是随机不可枚举查找 ID，至少 128 bit；`reboot_resume_token_secret` 是随机 secret，至少 256 bit。
- 服务端保存 `reboot_resume_token_id` 和 `reboot_resume_token_secret_hash = SHA256(canonical("rctl-reboot-resume-token-secret-v1", reboot_resume_token_secret))`，绑定字段保存为独立不可变列。
- `/resume` 必须先用 `reboot_resume_token_id` 定位记录，再常量时间比较 secret hash，并逐项校验原账号、原主控设备、原被控设备、旧会话、`reboot_request_id`、`permissions_digest`、过期时间、`reboot_resume_token_consumed_at_epoch_millis` 和失效状态。
- `reboot_resume_token` 明文只返回主控端一次；服务端不得保存 token secret 明文。成功恢复后必须写入 `reboot_resume_token_consumed_at_epoch_millis`；过期、取消或恢复失败后必须写入 `reboot_resume_token_invalidated_at_epoch_millis` 和固定 `reboot_resume_token_invalidation_reason`。
- 无人值守已关闭、策略变化或设备本地关闭远程重启时，恢复必须失败。

## 5. 协议消息

新增业务消息类型：

- `reboot_request`
- `reboot_state`
- `reboot_cancel`
- `reboot_resume_hint`

`reboot_resume_hint` 字段固定为：

- `old_session_id`
- `reboot_request_id`
- `controlled_device_id`
- `resume_expires_at_epoch_millis`
- `controlled_device_signature`

`controlled_device_signature = Sign(controlled_device_private_key, SHA256(canonical("rctl-reboot-resume-hint-v1", old_session_id, reboot_request_id, controlled_device_id, resume_expires_at_epoch_millis)))`。该消息仍走应用层端到端加密业务通道，Signal/API/Relay 不得解密或校验业务明文；主控端解密后必须校验被控设备签名和恢复窗口后才能发起 `/resume`。

`reboot_request` 字段：

- `session_id`
- `reboot_request_id`
- `mode`
- `reason`
- `countdown_seconds`
- `reconnect_after_reboot`
- `api_request_hash`
- `timestamp_epoch_millis`

`mode` 取值：

- `normal`
- `safe_mode_reserved`

V1 规则：

- `safe_mode_reserved` 仅保留，不实现。
- `countdown_seconds` 默认不小于 10 秒。
- `reconnect_after_reboot` 只表达恢复意图，不代表自动跳过授权。

`api_request_hash`：

```text
reboot_api_request_hash = SHA256(canonical(
  "rctl-reboot-api-request-v1",
  session_id,
  reboot_request_id,
  controller_account_id,
  controller_device_id,
  controlled_device_id,
  mode,
  reason_hash,
  countdown_seconds,
  reconnect_after_reboot,
  allow_remote_reboot,
  allow_remote_reboot_last_changed_at_epoch_millis,
  step_up_challenge_id,
  step_up_verified_at_epoch_millis,
  step_up_expires_at_epoch_millis,
  idempotency_key_hash,
  policy_evaluation_id,
  policy_evaluated_at_epoch_millis,
  permissions_digest,
  permissions_digest_last_changed_at_epoch_millis,
  request_status,
  created_at_epoch_millis,
  expires_at_epoch_millis
))
```

规则：

- 原始 `reason` 只允许出现在应用层端到端加密的 `reboot_request` 业务消息中，供被控端本地提示展示；API、Signal、Relay、数据库和审计 metadata 不得保存或解析 reason 自由文本。
- `reason_hash = SHA256(reason_utf8)`，`idempotency_key_hash = SHA256(idempotency_key)`；被控端执行前必须用 E2EE 消息中的 `reason` 重新计算 `reason_hash` 并确认其与 `api_request_hash` 输入一致。
- `request_status` 是生成 `api_request_hash` 时的不可变状态快照，固定枚举为 `pending | accepted`；`remote_reboot_requests.status` 是当前状态，两者必须分开保存。
- 被控端执行前必须确认 API 侧 `reboot_request_id` 仍有效，当前 `status` 处于 `pending/accepted` 范围，且本地收到的 `api_request_hash` 等于服务端保存的不可变快照。
- V1 只允许被控端在线调用 `GET /v1/reboot-requests/{reboot_request_id}` 获取 API 权威状态后执行；不提供离线签名状态回执替代路径。未来如需离线签名回执，必须先冻结服务端签名 key、key ID、canonical receipt、过期、撤销和测试向量。
- 被控端执行前必须确认 step-up 未过期，且 `step_up_verified_at_epoch_millis` 不早于 `permissions_digest_last_changed_at_epoch_millis`、`allow_remote_reboot_last_changed_at_epoch_millis` 和 `policy_evaluated_at_epoch_millis` 三者最大值。
- `api_request_hash` 不能替代设备签名、step-up 或被控端本地提示，只用于绑定 API 请求事实和应用层加密业务消息。

`reboot_state` 字段：

- `session_id`
- `reboot_request_id`
- `state`
- `error_code`
- `auto_resume_consent`
- `local_consent_token_hash`
- `timestamp_epoch_millis`

`state` 取值：

- `pending`
- `shown_to_user`
- `accepted`
- `cancelled`
- `executing`
- `device_offline`
- `device_online`
- `resume_ready`
- `resume_failed`

规则：

- `reboot_state.state` 是被控端通过业务消息上报的瞬时状态切片；`remote_reboot_requests.status` 是 API/数据库行的权威状态字段。二者字段名来自不同层级，不要求取值完全相同。
- 状态映射固定为：`shown_to_user` 只更新提示时间并写 `remote_reboot_prompt_shown` 审计，不改变权威 `status`；`device_online` 表示重启后设备重新上线，权威 `status` 仍由后续 `resume_ready/resumed/failed` 推进；`resume_failed` 必须映射为权威 `status = failed` 并写 `failure_reason`。
- 所有 `reboot_*` 业务消息必须走应用层端到端加密。
- API/Signal/Relay 不得伪造被控端本地接受状态。
- `shown_to_user/accepted/cancelled/executing/device_offline/device_online/resume_ready/resume_failed` 的事实源是被控端本地状态机；API 和 Signal 只能保存或转发设备签名后的裁剪状态元数据。
- `auto_resume_consent` 只能由被控端在 `accepted` 状态上报，取值为 `none | once_by_controlled_user`；选择 `once_by_controlled_user` 时必须同时上报本地生成的 `local_consent_token_hash`，明文 token 只保存在被控端本地安全存储中。
- 旧会话关闭后不得继续投递输入、剪贴板、文件或视频消息。

## 6. API 设计

V1 Core API：

```text
POST /v1/sessions/{session_id}/reboot-requests
GET  /v1/reboot-requests/{reboot_request_id}
POST /v1/reboot-requests/{reboot_request_id}/state
POST /v1/reboot-requests/{reboot_request_id}/cancel
POST /v1/reboot-requests/{reboot_request_id}/resume
```

规则：

- 创建请求必须校验账号 token、主控设备签名、会话状态、幂等键和 step-up。
- 创建请求只接收 `reason_hash`，不得接收或保存 reason 自由文本。
- `state` 只能由被控端设备签名调用，用于上报本地提示、接受、取消、执行、离线前准备和自动恢复一次同意的裁剪元数据；不得携带 reason 明文。
- `cancel` 可以由主控端或被控端调用；被控端调用必须带被控设备签名。
- `resume` 只能创建新会话或返回新会话创建所需 challenge，不得恢复旧业务通道；临时协助若未记录 `auto_resume_consent = once_by_controlled_user`、该同意已撤销或该同意已消费，必须进入新的被控端确认流程。
- `reconnect_after_reboot` 只在创建远程重启请求时表达恢复意图；`resume` API 不接收该字段，恢复意图由 `reboot_resume_token`、原请求记录和权限绑定共同校验。`resume` 请求体或 query 携带 `reconnect_after_reboot` 时必须拒绝为 `unexpected_field`，不得把它解释成跳过授权的信号。
- `resume` 调用必须解析 `reboot_resume_token_id` 和 `reboot_resume_token_secret`，按 ID 定位记录，常量时间比较 `reboot_resume_token_secret_hash`，并校验原账号、原主控设备、原被控设备、原 `reboot_request_id`、`permissions_digest`、恢复窗口、`reboot_resume_token_consumed_at_epoch_millis` 和 token 失效状态；任一不匹配都必须拒绝并写审计。
- 临时协助自动恢复一次还必须等待被控端上线后提交设备签名的 `local_consent_proof_hash`；主控端不接触 `local_consent_token`，API 不得要求主控端提交 `local_consent_token` 或其明文等价物。
- API 只保存请求元数据和状态，不保存操作系统命令输出。

## 7. 数据模型

需要纳入 Schema Freeze 的逻辑表：

- `remote_reboot_requests`

`remote_reboot_requests` 关键字段：

- `reboot_request_id`
- `session_id`
- `controller_account_id`
- `controller_device_id`
- `controlled_device_id`
- `status`
- `api_request_hash`
- `api_request_hash_status`
- `mode`
- `reason_hash`
- `countdown_seconds`
- `reconnect_after_reboot`
- `allow_remote_reboot`
- `allow_remote_reboot_last_changed_at_epoch_millis`
- `step_up_challenge_id`
- `step_up_verified_at_epoch_millis`
- `step_up_expires_at_epoch_millis`
- `idempotency_key_hash`
- `policy_evaluation_id`
- `policy_evaluated_at_epoch_millis`
- `permissions_digest`
- `permissions_digest_last_changed_at_epoch_millis`
- `auto_resume_consent`
- `consent_at_epoch_millis`
- `consent_controlled_device_id`
- `consent_local_user_principal_hash`
- `consent_revoked_at_epoch_millis`
- `consent_revoked_by_actor_type`
- `consent_revoked_reason`
- `local_consent_token_hash`
- `auto_resume_consumed_at_epoch_millis`
- `reboot_resume_token_id`
- `reboot_resume_token_secret_hash`
- `reboot_resume_token_consumed_at_epoch_millis`
- `reboot_resume_token_invalidated_at_epoch_millis`
- `reboot_resume_token_invalidation_reason`
- `resume_expires_at_epoch_millis`
- `created_at_epoch_millis`
- `expires_at_epoch_millis`
- `requested_at_epoch_millis`
- `accepted_at_epoch_millis`
- `executed_at_epoch_millis`
- `cancelled_at_epoch_millis`
- `failure_reason`

规则：

- `api_request_hash` 及其输入快照字段在创建后不可修改；状态流转只更新当前 `status` 和对应时间字段，不重算旧 hash。
- `api_request_hash_status` 是数据库列名，对应协议 canonical 输入字段 `request_status`；二者必须保存同一值。T002E 落 SQL 时必须把列注释和 CHECK 指向 `request_status`，CHECK 固定为 `pending | accepted`，不得另建第二套语义。
- API 和数据库不得保存 reason 自由文本；只保存 `reason_hash`。
- `mode` 固定枚举为 `normal | safe_mode_reserved`；`safe_mode_reserved` 首版只保留，不实现。
- `auto_resume_consent` 取值为 `none | once_by_controlled_user`，默认 `none`。
- `consent_local_user_principal_hash` 只保存本地用户主体的 hash 或平台不可逆标识 hash，不保存用户名、邮箱、真实姓名或系统账号明文。
- `consent_revoked_by_actor_type` 固定为 `controlled_device | account | system`；`consent_revoked_reason` 固定为 `controlled_user_revoked | unattended_disabled | device_unbound | mfa_reset | policy_changed | token_invalidated`。撤销只能由被控端签名、本账号高风险操作或系统策略触发，必须写 `remote_reboot_auto_resume_consent_revoked` 审计。
- `local_consent_token_hash` 只能由被控端本地生成并经设备签名上报；明文 token 不得离开被控端本地安全存储。
- `auto_resume_consumed_at_epoch_millis` 非空后不得再次自动恢复。
- `reboot_resume_token` 只返回主控端一次，服务端只保存 `reboot_resume_token_id` 和 `reboot_resume_token_secret_hash`。
- `reboot_resume_token` 和 `reboot_resume_token_secret` 不得写日志或审计 metadata；`reboot_resume_token_id` 可以作为查找 ID 保存，但不得作为授权凭据使用。
- `reboot_resume_token_secret_hash` 只用于校验 token secret；原账号、主控设备、被控设备、旧会话、`reboot_request_id`、`permissions_digest`、过期时间、token 消费时间和 token 失效状态必须保存为独立不可变绑定字段并逐项校验。临时协助自动恢复一次另行校验被控端设备签名的 `local_consent_proof_hash`，不得要求主控端持有 `local_consent_token`。
- `reboot_resume_token_consumed_at_epoch_millis` 和 `reboot_resume_token_invalidated_at_epoch_millis` 任一非空后，`/resume` 必须拒绝；二者不得同时由成功路径写入，冲突写入必须视为数据一致性错误。
- `reboot_resume_token_invalidation_reason` 固定枚举为 `expired | cancelled | resume_failed | policy_changed | permissions_changed | device_key_revoked | manual_revoked`，不得写自由文本。
- `status` 首版固定集合为 `pending`、`accepted`、`cancelled`、`executing`、`device_offline`、`resume_ready`、`resumed`、`failed`、`expired`；`shown_to_user` 和 `device_online` 不进入权威 `status`，仅作为瞬时业务状态和审计事件。

## 8. 审计

必须新增或支持审计动作：

- `remote_reboot_requested`
- `remote_reboot_prompt_shown`
- `remote_reboot_accepted`
- `remote_reboot_cancelled`
- `remote_reboot_started`

- `remote_reboot_device_online`

- `reboot_request_id`

- `reboot_resume_token`

- `reason`

- 密码、验证码、MFA code、无人值守密码或 token 明文。

## 9. 客户端要求

被控端：

- 必须显示重启倒计时、主控端标识、原因、取消按钮和断开按钮。
- “本次重启后自动恢复一次”必须是显式可见选项，默认不选；选中后必须显示原主控账号和设备，并保留取消方式。
- 必须在重启前释放输入保护、隐私屏、采集和编码资源。
- 重启后服务自启动，但不得静默建立旧业务通道。
- 如果平台权限不足，必须明确失败并写审计。

主控端：

- 必须显示高风险 step-up。
- 必须显示重启进度：等待被控端确认、倒计时、设备离线、设备上线、准备新会话。
- 必须允许用户取消等待恢复。
- 新会话失败时必须给出可理解原因。

Windows：

- 使用系统允许的重启 API。
- 不绕过 UAC、安全桌面和系统更新阻塞。
- Service 必须在重启后可上线。

Ubuntu：

- 使用 systemd/logind 或桌面环境允许的重启路径。
- 不绕过系统授权。
- systemd user service 或 system service 必须按安装模式恢复上线。

## 10. 测试要求

必须验证：

- 无 `allow_remote_reboot` 策略时拒绝请求。
- 未完成 step-up 时拒绝请求。
- 临时协助默认展示被控端确认。
- 被控端取消后不重启。
- 被控端接受重启后必须写 `remote_reboot_accepted` 审计，并记录 `accepted_at_epoch_millis`。
- 重启前释放隐私屏、本地输入保护和采集资源。
- 重启后旧会话密钥不能继续发送业务消息。
- 重启后被控端重新上线。
- 恢复窗口过期后不能自动恢复。
- 未选择自动恢复一次时，临时协助恢复必须重新弹出被控端确认。
- 自动恢复一次只能被原主控账号、原主控设备和原被控设备在窗口内消费一次；消费后再次恢复必须失败或重新确认。
- 无人值守关闭后恢复失败。
- Windows 和 Ubuntu 26.04 LTS 均能完成重启后上线冒烟。
- 审计记录覆盖请求、取消、执行、离线、上线、恢复和失败。
