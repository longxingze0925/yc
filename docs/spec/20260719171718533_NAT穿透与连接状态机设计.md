# NAT 穿透与连接状态机设计

## 1. 目标

远控连接必须在多种网络环境下尽量成功：

- 同局域网。
- 家庭 NAT。
- 手机热点。
- 公司网络。
- UDP 受限。
- 只能访问 443 的网络。

连接策略：

```text
LAN Direct -> UDP P2P -> QUIC Relay -> TLS 443 Relay
```

## 2. 组件

`signal-server`：

- 交换候选地址。
- 下发 Relay 节点。
- 转发 API 已持久化后的连接状态通知，不接收客户端状态写入。

`relay-server`：

- QUIC Relay。
- TLS 443 Relay。
- 节点健康和负载上报。

`client-core`：

- 采集候选地址。
- 并发探测链路。
- 选择链路。
- 断线重连。

## 3. 候选地址

候选类型：

- `lan_direct`
- `udp_p2p`
- `quic_relay`
- `tls_443_relay`

候选字段：

- `candidate_id`
- `session_id`
- `device_id`
- `role`
- `kind`
- `endpoint`
- `source`
- `observe_result_id`
- `priority`
- `expires_at_epoch_millis`
- `relay_node_id`
- `rtt_ms`
- `loss_ppm`
- `jitter_ms`

`source` 取值：

- `local_interface`：本机网卡地址。
- `udp_observed`：UDP 外部观测地址。
- `relay_allocated`：Relay 分配地址。

## 4. 外部观测地址来源

首版决策：

- 不依赖第三方公共 STUN 服务作为默认路径。
- `relay-server` 提供轻量 UDP observe 服务，用于返回客户端的 UDP 外部观测地址。
- `signal-server` 负责签发短有效期 `observe_token` 和 `candidate_token`。
- 客户端请求 UDP observe 时必须携带 `observe_token`，不得携带最终候选的 `candidate_token`。
- UDP observe 服务返回 `observed_endpoint`、`observe_result_id`、`observe_result_binding_hash` 和 `expires_at_epoch_millis`；`region` 只作为可选诊断字段，不参与候选 ID 或 token 绑定。
- 客户端应尽量使用后续 P2P 探测相同的本地 UDP socket 或端口复用策略；不能复用时必须降低该候选优先级。
- 不得把 WebSocket/TCP 连接的远端地址当成 UDP P2P 候选地址。

UDP observe 只用于生成 `udp_p2p` 候选，不参与权限决策。权限、会话状态和 Relay 分配仍由 API/Signal 按会话策略处理。

企业区域驻留启用后，权威区域只能来自服务端 Relay 节点配置、组织区域策略和部署配置；不得使用 UDP observe 的诊断 `region` 做合规决策。

`observe_token` 签发规则：

- 客户端先向 signal-server 发送 `request_observe_token`。
- token 必须绑定 `session_id`、`device_id`、`role`、`local_socket_nonce` 和过期时间。
- `observe_token_binding_hash = SHA256(canonical("rctl-observe-token-binding-v1", session_id, device_id, role, local_socket_nonce, expires_at_epoch_millis))`。
- 客户端只能请求 `requested_ttl_millis`，最终过期时间由 signal-server 按服务端上限生成；首版 observe token 最大有效期 30 秒。
- UDP observe 服务必须校验 token 签名/HMAC、绑定字段、设备角色和过期时间。
- UDP observe 成功后，relay-server 必须生成短期 `observe_result_id`，把 `session_id`、`device_id`、`role`、`local_socket_nonce`、`observed_endpoint`、`source = udp_observed`、`expires_at_epoch_millis` 和 `observe_result_binding_hash` 写入 Redis。
- UDP observe 响应返回 `observed_endpoint`、`observe_result_id`、`observe_result_binding_hash` 和 `expires_at_epoch_millis`；客户端用该外部 `endpoint` 生成 `udp_p2p` 候选，再请求 `candidate_token`。
- `observe_result_binding_hash = SHA256(canonical("rctl-observe-result-binding-v1", session_id, device_id, role, local_socket_nonce, observed_endpoint, source, expires_at_epoch_millis, observe_result_id))`。
- `observe_token` 不得落库或写日志，只允许记录 binding hash 前 8 字节和错误码。

`candidate_token` 签发规则：

- 客户端先向 signal-server 发送 `request_candidate_token`。
- token 必须绑定 `session_id`、`device_id`、`role`、`candidate_id`、`kind`、`endpoint`、`source`、`observe_result_id` 和过期时间。
- `source = udp_observed` 时，`request_candidate_token` 必须额外携带 `observe_result_id` 和 `observe_result_binding_hash`；signal-server 必须读取 Redis 短期记录，确认该 `endpoint` 确实来自 UDP observe。
- `candidate_token_binding_hash = SHA256(canonical("rctl-candidate-token-binding-v1", session_id, device_id, role, candidate_id, kind, endpoint, source, observe_result_id, expires_at_epoch_millis))`；非 UDP observe 候选的 `observe_result_id` 使用空值参与计算。
- `candidate_id` 必须在请求 token 前由候选自身字段稳定生成，不得包含 `expires_at_epoch_millis`、`candidate_token` 或 `candidate_token_binding_hash`。
- 客户端只能请求 `requested_ttl_millis`，最终过期时间由 signal-server 按服务端上限生成；首版 candidate token 最大有效期 60 秒。
- `candidate_token` 只用于最终候选的 P2P 探测授权，不得用于 UDP observe。
- LAN Direct 候选不需要 UDP observe，但仍必须为最终 P2P 探测请求 `candidate_token`；LAN Direct 固定使用 `kind = lan_direct`、`source = local_interface`，`observe_result_id` 为空。
- LAN Direct 候选请求必须携带 `interface_name_hash`、`interface_index_hash`、`local_socket_nonce`、`timestamp_epoch_millis`、`local_interface_claim_hash` 和 `local_interface_signature`。
- LAN Direct 候选必须携带设备签名的本机接口声明：`local_interface_claim_hash = SHA256(canonical("rctl-local-interface-claim-v1", session_id, device_id, role, candidate_id, endpoint, interface_name_hash, interface_index_hash, local_socket_nonce, timestamp_epoch_millis))`，`local_interface_signature = Sign(device_private_key, local_interface_claim_hash)`。
- Signal 必须重新计算 `candidate_id` 和 `local_interface_claim_hash`，并校验签名、会话角色、候选数量上限、30 秒时间窗口和 `device_id + session_id + local_socket_nonce + candidate_id` 未重放后才签发 `candidate_token`。
- LAN Direct 的 `endpoint` 只能使用本机接口单播地址和高位临时 UDP 端口；首版禁止 `unspecified`、loopback、multicast、broadcast、documentation/test-net、link-local 和公网地址作为 `lan_direct` 候选。
- 每个设备每个会话首版最多 8 个 LAN Direct 候选，候选交换和 P2P 探测必须限速；探测包只能包含 `session_id`、`candidate_id`、`role`、`candidate_token`、`candidate_token_binding_hash` 和 probe nonce，不得携带业务 payload。
- 探测方必须本地判断远端 LAN Direct 地址是否落在本机可路由的局域网接口范围内，不匹配时跳过该 LAN 候选，不能用 LAN Direct 机制探测任意私网地址。
- UDP P2P 候选固定使用 `kind = udp_p2p`、`source = udp_observed`；Relay 候选固定使用 `kind = quic_relay | tls_443_relay`、`source = relay_allocated`。
- P2P 探测接收端不持有服务端 token 密钥，只校验探测包带回的 token 是否等于本地候选记录中的 token，并校验 `candidate_token_binding_hash` 和 probe nonce；同一 `session_id + candidate_id + role + probe_nonce` 重放必须在 candidate token 有效期内被拒绝。
- `candidate_token` 不得落库或写日志，只允许记录 binding hash 前 8 字节、候选类型和错误码。

## 5. 连接协商流程

```text
1. 主控端请求创建会话。
2. api-server 校验权限。
3. signal-server 推送邀请给被控端。
4. API 状态达到可建链门槛：临时验证码会话必须进入 `accepted`，账号确认会话必须进入 `accepted`，无人值守会话在 `require_prompt = false` 时必须进入 `unattended_verified`，在 `require_prompt = true` 时必须进入 `accepted`。
5. 双方采集本地 LAN 候选。
6. 双方请求外部观测地址。
7. signal-server 分配 Relay 候选。
8. 双方交换候选。
9. 双方并发尝试连接。
10. 选择可用且质量最好的路径。
11. 建立会话密钥。
12. 开始业务数据传输。
```

## 6. UDP P2P 打洞

打洞策略：

- 双方通过 signal-server 获得对端候选。
- 双方同时向对端候选发送探测包。
- 探测包必须带 `session_id`、`candidate_id`、`role`、`candidate_token`、`candidate_token_binding_hash` 和一次性 probe nonce。
- 收到有效探测包后回应确认。
- 双向确认后进入 QUIC 握手。

限制：

- 对称 NAT 下可能失败。
- 企业防火墙可能阻断 UDP。
- 失败不得阻塞 Relay 尝试。

## 7. 链路竞速

必须并发尝试：

- LAN Direct。
- UDP P2P。
- QUIC Relay。

TLS 443 Relay 可延后短时间启动，也可在检测到 UDP 阻断后启动。

选择规则：

```text
路径优先级优先
同路径比较 RTT
RTT 接近时比较丢包和抖动
已连接路径明显劣化时允许切换
```

不得：

- 永远等待 P2P 成功。
- P2P 探测失败后才开始 Relay。
- 文件传输影响链路探测。

## 8. 状态机

```text
Idle
  -> Preparing
  -> GatheringCandidates
  -> ExchangingCandidates
  -> Racing
  -> EstablishingSecureSession
  -> Connected
  -> Degraded
  -> Reconnecting
  -> Closed

任意阶段可进入 Failed
```

状态说明：

- `Preparing`：完成权限和确认。
- `GatheringCandidates`：采集 LAN、P2P、Relay 候选。
- `Racing`：并发尝试候选。
- `EstablishingSecureSession`：进行密钥交换和会话绑定。
- `Connected`：业务数据可传输。
- `Degraded`：链路质量下降但仍可用。
- `Reconnecting`：链路断开，尝试恢复。

## 9. 首版默认超时

首版默认：

- LAN 探测：1 秒。
- UDP P2P 首轮探测：3 秒。
- QUIC Relay 建连：3 秒。
- TLS 443 Relay 建连：5 秒。
- 断线重连窗口：30 秒。
- `key_confirm.timestamp` 允许偏差：接收端本地时间前后各 30 秒。
- `relay_open_nonce` 去重记录：保存到对应 `session_relay_token` 过期后至少 60 秒。

规则：

- 连接探测超时可以按平台网络质量收紧或在灰度中调优，但 `key_confirm.timestamp` 允许偏差和 `relay_open_nonce` 去重窗口属于安全边界，放宽前必须更新协议设计、测试方案和 AI 任务清单。
- 被控端确认等待：60 秒。

断线重连窗口起算点是最后一次成功接收已认证业务帧或心跳的时间。远程重启进入执行或恢复流程后必须立即关闭该窗口，不得把远程重启 10 分钟恢复窗口用于复用旧会话密钥。以上值必须可配置，并在测试中记录实际表现。

## 10. Relay 分配

分配依据：

- 地理区域。
- 当前负载。
- 历史质量。
- 企业策略。
- 是否支持 TLS 443。

Relay 返回：

- `session_id`
- `device_id`
- `role`
- `controller_device_id`
- `controlled_device_id`
- `relay_node_id`
- `public_endpoint`
- `transport`
- `permissions_digest`
- `relay_token_epoch`
- `issued_at_epoch_millis`
- `expires_at_epoch_millis`
- `relay_token_id`
- `session_relay_token`
- `token_binding_hash`

Relay token 绑定：

```text
relay_token_binding = canonical("rctl-relay-token-binding-v1", session_id, device_id, role, controller_device_id, controlled_device_id, relay_node_id, transport, permissions_digest, relay_token_epoch, issued_at_epoch_millis, expires_at_epoch_millis, relay_token_id)
token_binding_hash = SHA256(relay_token_binding)
```

`session_relay_token` 必须是角色级结构化签名 token 或等价可验证令牌，主控端和被控端使用不同 token。payload 至少包含上述绑定字段。Signal/API 必须把这些绑定字段作为 `relay_allocated` 明文字段分别下发给对应角色；客户端发送 `relay_open` 时必须显式携带这些字段，并使用设备长期私钥签名 `SHA256(canonical("rctl-relay-open-v1", relay_open_without_signature))`，即 `device_signature = Sign(device_private_key, SHA256(canonical("rctl-relay-open-v1", relay_open_without_signature)))`。Relay 必须校验 `relay_open` 字段与 token payload 一致。

`relay_open_without_signature` 须按 `session_id`、`device_id`、`role`、`controller_device_id`、`controlled_device_id`、`relay_node_id`、`transport`、`permissions_digest`、`relay_token_epoch`、`issued_at_epoch_millis`、`expires_at_epoch_millis`、`relay_token_id`、`relay_open_nonce`、`session_relay_token`、`token_binding_hash` 顺序参与计算，不包含 `device_signature`本身。该顺序与 `rctl-relay-token-binding-v1` 字段顺序一致，canonical 编码使用协议附录定义的 length-prefixed 字段编码；跨实现不同字段顺序、直接签名未 hash 的 canonical bytes、重复签名 `device_signature` 或复用 `rctl-relay-token-binding-v1` hash 作为该签名输入都必须拒绝。

Relay 校验设备签名时，设备公钥、key version 和撤销状态必须来自 `relay:session:{session_id}:authorization` 或等价服务端 introspection；不得只信任 token payload 或客户端自带公钥。授权缓存缺失、过期、公钥版本不匹配或设备密钥已撤销时必须拒绝建链。

Relay token 新鲜度：

- `session_relay_token` 首版最大 TTL 为 60 秒，策略要求更短时取更严格值。
- Relay 接受 `relay_open` 前必须校验短期会话授权状态：会话仍可建链或已连接、`allow_relay = true`、`permissions_digest` 未变化、`relay_token_epoch` 未撤销、`relay_node_id` 仍允许、双方设备公钥版本未撤销。
- 会话关闭、权限变化、`allow_relay` 变为 false、策略关闭会话或 Relay 节点被禁用时，api-server/signal-server 必须提升或撤销 `relay_token_epoch`；旧 token 即使未过期也必须拒绝。
- Relay 节点被禁用后，撤销状态对所有新 `relay_open` 请求的生效 SLO 为 2 秒内；超过 SLO 仍接受新请求必须阻断发布。

Relay 必须校验：

- `session_id`
- `controller_device_id`
- `controlled_device_id`
- `device_id`
- `role`
- `session_relay_token`
- `token_binding_hash`
- `permissions_digest`
- `relay_token_epoch`
- `issued_at_epoch_millis`
- `expires_at_epoch_millis`
- `relay_token_id`
- `relay_open_nonce`
- `device_signature`
- token 过期时间。
- 设备公钥或 `device_public_key_id/key_version` 来自服务端授权状态。
- 设备密钥未撤销。
- 主控设备和被控设备。
- Relay 节点 ID。
- transport 类型。
- `relay_open` 中的 token 绑定字段必须与 signal-server 分配结果一致。
- 重放缓存键为 `relay_token_id + role + relay_open_nonce`；同一角色同一 nonce 不得重复接受，另一端或短断重连必须使用独立 nonce。
- M8 企业区域策略启用时，Relay 分配前必须过滤不合规区域；无合规节点且策略 fail-closed 时必须拒绝分配，不得跨区兜底。

## 11. 断线重连

重连触发：

- 心跳超时。
- QUIC 连接关闭。
- RTT 持续过高。
- 丢包持续过高。
- 网络接口切换。

重连规则：

- 被控端主动断开后不得自动重连。
- 主控端主动断开后不得自动重连。
- 网络异常可在重连窗口内恢复。
- 候选对、传输路径或 Relay 节点变化时，必须重新 signed key exchange 后才能恢复业务数据。
- 远程重启关闭旧会话，设备重启后必须创建新会话并重新完成候选交换和 signed key exchange。
- 重连成功后必须记录会话事件。

## 12. 验收

必须验证：

- 同局域网走 LAN Direct。
- UDP 可用时优先 P2P。
- UDP 外部观测地址来自 UDP observe，不来自 WebSocket/TCP 远端地址。
- LAN Direct 候选拒绝 loopback、multicast、link-local、公网地址、非本机会话角色签名和超数量候选；探测方跳过不在本机局域网范围内的 LAN 候选。
- UDP P2P 失败时自动走 QUIC Relay。
- UDP 被阻断时走 TLS 443 Relay。
- Relay 节点中断后可重新分配。
- 断线 5 秒内恢复。
- 被控端断开后不会自动重连。
