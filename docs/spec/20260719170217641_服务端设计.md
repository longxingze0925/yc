- API Server

- Admin Web

## 2. API Server

职责：

- 账号注册和登录。
- MFA、风险验证和受信任主控设备。
- 设备管理。
- 会话创建。
- 权限校验。
- 条件访问策略评估。
- 反诈、限流、举报和处置评估。
- 审计查询。
- 客户端配置下发。
- 客户端发布和更新 manifest 下发。

技术：

- Rust
- axum
- PostgreSQL
- Redis
- tracing

认证要求：

- access token / refresh token 策略以 `docs/spec/20260719171718533_认证与无人值守凭据设计.md` 为准。
- 密码必须使用 Argon2id hash。
- refresh token 服务端只保存 hash。
- PostgreSQL 是登录/step-up challenge 发行、`required_methods`、状态和消费、account session、设备注册 grant 消费、trusted-device 和恢复码 delivery 幂等结果的唯一事实源；Redis 只尽力承担短期缓存、nonce、防重放、限流和租约，缺失、超时或不一致时必须回读 PostgreSQL。

API 规则：

- `POST /v1/auth/register` 是首版账号注册入口；如果未来改为邀请注册，必须先更新产品规格和任务清单。
- `POST /v1/auth/login` 必须接收 `email/password/device_id/device_public_key/public_key_id/public_key_version/client_nonce/protocol_version`。密码正确后把设备判定为 `registered | pending_enrollment | conflict`；非 conflict 只返回 `login_challenge_required`、账号/challenge ID、登录请求和 challenge binding hash、`server_nonce`、设备状态、所需因子、过期时间和剩余次数，不得签发 token。
- `POST /v1/auth/login/finish` 必须接收 `login_challenge_id/login_request_binding_hash/login_challenge_binding_hash/client_nonce/server_nonce/factor/code/protocol_version`，并校验 `X-Request-ID/X-Rctl-Device-ID/X-Rctl-Timestamp/X-Rctl-Api-Nonce/X-Rctl-Device-Signature`。`registered` 只使用 `devices` 当前未撤销公钥验签，`pending_enrollment` 只使用第一段绑定的拟注册公钥验签。
- 登录第一段读取的 `accounts.updated_at_epoch_millis` 必须作为 `login_account_updated_at_epoch_millis` 保存并纳入 challenge binding；创建和 finish 事务锁定账号并要求当前值与快照严格相等。安全版本变化后旧未消费 challenge 固定以 `account_security_changed` 拒绝，不得签发 token、session 或 grant；该规则不能依赖墙钟先后比较。
- 持久化 `purpose = login_mfa` challenge 时，`pending_enrollment` 必须写 `device_id = NULL`，并把客户端真实拟注册 ID 写入 `login_device_id`；`registered` 必须写入相等且非空的 `device_id/login_device_id`。不得让未注册 ID 触发 `devices` 外键，也不得在恢复路径用空值或请求自报 ID 替代 `login_device_id`。
- 新增设备唯一授权路径固定为 `/v1/auth/login` 两段式 challenge 加 enrollment grant。`purpose = new_controller_device` 保留在固定枚举中仅用于兼容既有记录和审计语义；V1 通用 `/v1/auth/risk-challenge` 遇到未知 `device_id` 必须拒绝且不得落 challenge。未知设备必须走 `login_mfa + pending_enrollment`，写入 `device_id = NULL` 并在 `login_device_id` 保存真实拟注册 ID。
- 登录 challenge 必须绑定账号、请求 ID、设备 ID/状态、公钥 fingerprint、双 nonce、服务端观测 IP、裁剪后 User-Agent、风险决策、因子集合、协议版本、签发/过期时间和次数上限；最大 5 分钟、5 次。finish 必须在 PostgreSQL 事务中锁定并消费 challenge、TOTP counter 或 recovery code，建立 account session 和可选 enrollment grant，提交后才返回 token。
- `login_mfa` 的完整设备公钥与 binding 上下文必须和 challenge 状态一起持久化到 PostgreSQL；Redis 只保存带尝试租约的短期副本。Redis 记录丢失时，finish 只能从 PostgreSQL 权威行重建副本，重建后仍必须执行原子消费和设备私钥证明。
- 登录 finish 和 refresh 成功响应必须包含 `account_id`、access token、refresh token 或 refresh token 轮换结果、token 过期时间；未注册设备 finish 还返回一次性 `device_enrollment_grant` 和过期时间。WebSocket 设备签名使用的 `account_id` 必须与 access token 解析结果一致。
- 登录 finish 建立 `account_sessions` 时必须显式持久化非空 `mfa_verified`：直接完成 TOTP/recovery code 或命中当前有效 trusted-device 时为 true，无 MFA 且未命中有效 trust 时为 false。该值是 session 认证强度快照，不能替代高风险 step-up。
- refresh 必须先锁账号，并在单个 PostgreSQL 事务中完成旧 refresh session 消费、替代 session 插入和刷新审计。替代 session 必须从旧 PostgreSQL 行读取并原样复制 `mfa_verified`，禁止根据账号当前 MFA 状态、Redis/内存状态、请求字段或代码默认值重新计算；服务重启或 Repository 重建不能降级或提升该值。密码修改/MFA 状态事务撤销完成后，任何基于撤销前快照的 refresh 都必须失败，不得在独立事务中复活 session；同一 refresh token 并发轮换只能一个成功。
- challenge、设备证明、MFA 或协议版本任一失败时不得签发 access token、refresh token 或 enrollment grant。旧 `/v1/auth/mfa/verify` 不得继续签发 token，迁移期只能返回升级错误。
- 高风险 API 必须支持 step-up 验证，包括修改密码、禁用 MFA、重新生成恢复码、替换设备公钥、设备重绑定或设备密钥恢复、开启或轮换无人值守、关闭 `require_prompt`、授予或本地允许 `privacy_screen`、授予或本地允许 `block_local_input`、请求远程重启、放宽策略、发布客户端制品和修改区域驻留策略。
- step-up challenge 的 `required_methods` 是 challenge 创建时从已锁定账号/MFA 状态得出并持久化的事务级条件，不是客户端可选参数或 Redis 派生值。MFA active 时固定为 `totp | recovery_code` 二选一；无 MFA 时仅 `password_change` 可固定为 `password`，其他高风险 purpose 必须返回 `mfa_enrollment_required` 且不创建 challenge。
- Memory 与 PostgreSQL 的 login finish 必须共用 grant/trust/审计集合 authority 校验，拒绝跨 challenge、跨账号/设备/session、fingerprint、TTL、trust 决策和重复审计 ID 不一致。
- `PATCH /v1/me/password` 只接受 `{current_password,new_password}`，并必须验证与当前 PATCH 完整操作 binding 一致的 `password_change` step-up。MFA active 时 TOTP/recovery step-up 不替代 `current_password` 校验；无 MFA 时完成 password reauthentication 后仍必须在 PATCH 中再校验 `current_password`。
- 密码修改的最终 PostgreSQL 事务必须锁定账号和 challenge，确认已验证旧密码的 hash 仍是当前值，原子消费 challenge、写入新 Argon2id hash、以 `password_changed` 撤销账号全部 `account_sessions`（包含当前 session）和全部 active trust，并写入 `password_changed` 及必要撤销审计。成功固定返回 `204 No Content`，不签发替代 access/refresh/step-up token，客户端必须使用新密码重新登录。
- 删除或禁用任何 MFA 因子都属于高风险操作；禁用最后一个有效因子会让账号进入无 MFA 状态，必须 step-up、写审计并提示风险。
- 高风险 API 校验 step-up 时必须重新计算 `operation_binding_hash`，确认账号、设备、目的、method、path、body hash、request_id 和过期时间一致；已消费或过期的 challenge 不得复用。
- risk challenge 验证必须锁定 PostgreSQL 权威行并以行内 `required_methods` 为条件。客户端在 PostgreSQL 已提交 `verified`、但 token 签发/响应或 Redis finalize 失败后重试时，只有 challenge 仍未过期、`consumed_at_epoch_millis IS NULL` 且账号/设备/purpose/binding 完全相同才可确定性重签同语义 token，不得重复消费 TOTP/recovery code 或写成功审计。
- challenge 发行与发行审计、因子消费/尝试次数/状态更新与成功或失败审计、高风险业务写入/challenge 消费与业务审计，必须分别在同一 PostgreSQL 事务中闭合；任一审计或状态写入失败都必须整体回滚。
- challenge 转为 `cancelled` 时，仓储必须在同一 PostgreSQL 事务内锁定权威行、写入 cancelled 状态并插入现有动作 `risk_challenge_failed` 的审计，审计字段固定为 `result = failure`、`reason = cancelled`。状态或审计任一写入失败必须全部回滚；不得新增 cancel 专用 audit action，也不得先改状态后异步补审计。
- TOTP secret、TOTP code、恢复码明文和 step-up token 明文不得写入日志、审计 metadata 或数据库。
- `POST /v1/me/mfa/totp/start` 必须接收客户端临时 X25519 `recovery_delivery_public_key`；finish 必须要求 `Idempotency-Key`，在成功事务中保存恢复码 hash 和客户端可解密的 delivery ciphertext，不保存恢复码明文或服务端临时私钥。
- TOTP finish 首次响应和精确幂等重试必须返回同一 `delivery_id/server_ephemeral_public_key/nonce/ciphertext/created_at_epoch_millis/expires_at_epoch_millis/recovery_code_count`；`created_at_epoch_millis` 和过期时间都参与 HKDF/AAD，客户端不得使用本地推测时间。当前 session 因 `mfa_enabled` 被撤销后，只允许原 token 在原过期时间与 delivery TTL 较小窗口内读取同一已提交 ciphertext，不得重新校验 TOTP、生成恢复码或访问其他 API。
- 启用 MFA、禁用 MFA 和修改密码必须在各自安全状态事务中撤销账号全部 `account_sessions`（含当前）和全部 active `trusted_controller_devices`，写明 `revoked_reason` 和审计后提交；`authenticate` 每次请求必须查询 session authority，不能只验证 access token 签名。
- trusted-device 命中必须同时校验账号、设备、当前公钥 fingerprint、active 状态和 TTL；普通登录和 refresh 只更新 `last_used_at_epoch_millis`，不得延长 `expires_at_epoch_millis`。TOTP trust 最长 30 天，recovery-code trust 默认 24 小时且固定要求高风险 step-up。
- `POST /v1/devices` 必须增加 `device_enrollment_grant`，并在单个 PostgreSQL 事务中锁定 grant、校验 secret hash/TTL/账号/设备/公钥 fingerprint/challenge binding/协议版本/原 account session、再次验证拟注册私钥签名、插入 `devices`、消费 grant 和写审计；`establish_trust = true` 时再原子插入 trusted-device。只有 access token 或新公钥自签必须返回 `device_enrollment_grant_required`。
- grant 默认和最大 TTL 均为 5 分钟，secret 只保存 hash；跨账号、设备 ID、公钥、challenge 或协议版本，已消费、过期或 secret 错误均拒绝。无 MFA 登录签发的 grant 固定 `establish_trust = false`，客户端不得覆盖 trust 决策字段。
- grant 消费必须持久化稳定的注册业务 binding、首次 `public_key_id` 和可选首次 trusted-device ID；binding 排除 API nonce、签名时间戳、request ID、grant secret 和服务端随机结果。同一业务请求用新 nonce 重试时返回首次设备结果，不得重新生成设备、trust 或审计；业务字段变化必须冲突。
- `PATCH /v1/devices/{device_id}` 只接受账号内当前有效 actor 设备的 `rctl-api-input-v1` 签名，请求必须二选一：`display_name`，或 `action = disable | restore | unbind | revoke_public_key`。`restore` 只允许 `disabled -> offline`，且不会自动恢复被控或无人值守能力；`unbound` 和已撤销当前公钥不可通过该接口恢复。
- `disable/unbind/revoke_public_key` 必须原子关闭目标设备参与的全部非终态会话、提升 Relay token epoch、撤销目标设备 active trust、关闭被控和无人值守能力并写审计；会话状态必须落 `closed`、追加 `session_events.closed` 和 `session_ended` 审计，提交后通过 Signal 向双方推送同一 `event_id` 的 `session_close_ack`。`unbind/revoke_public_key` 同时撤销当前公钥，并按 V1 固定策略以 `device_unbound` 撤销账号全部 active `account_sessions`。密钥轮换执行同样的旧 fingerprint trust 撤销和远控会话关闭语义，但不撤销已完成 step-up 的账号会话。
- `POST /v1/devices/{device_id}/temporary-codes` 只允许目标被控设备的已认证设备签名请求发起；仅有账号 access token、没有该 `device_id` 私钥签名的请求不得为设备创建临时验证码。
- 临时验证码注册接口使用 `registration_step = start | finish` 承载 OPAQUE registration；`start` 只接收 `proof_scheme = opaque_ristretto255_sha512_v1`、`opaque_registration_request`、`client_nonce`、期望有效期和最大尝试次数，返回 `registration_id`、`server_nonce` 和 `opaque_registration_response`；`finish` 只接收 `registration_id`、`code_verifier_record`、`code_verifier_salt` 和 `transcript_hash`，不接收验证码明文。
- `POST /v1/sessions` 是创建连接会话的唯一入口，必须携带 `controller_device_id`、`controlled_device_id`、`auth_method` 和幂等键。
- `POST /v1/sessions` 必须先执行条件访问和有效权限评估；条件访问返回 `access_decision = deny` 时不得创建可建链会话，返回 `access_decision = require_mfa` 时必须完成 step-up 后重新评估。
- `POST /v1/sessions` 必须执行反诈与滥用评估；返回 `warn_user` 时客户端必须展示风险提示，返回 `cooldown` 或 `deny_session` 时不得创建可建链会话。
- 条件访问和反诈结果必须合成为统一 `session_access_decision`，至少包含 `access_decision`、`anti_abuse_decision`、`session_access_decision`、`effective_permissions`、`permissions_digest`、`policy_evaluation_id`、`matched_policy_ids`、`abuse_actions`、`risk_challenge_id`、`cooldown_until_epoch_millis` 和 `user_warnings`；最终枚举固定为 `allow | warn_user | require_prompt | require_mfa | cooldown | deny_session`，合成优先级固定为 `deny_session` 或 `access_decision = deny` > `cooldown` > `require_mfa` > `require_prompt` > `warn_user` > `allow`。
- `policy_evaluation_id` 必须来自 PostgreSQL `policy_evaluations` 权威记录；会话、远程重启和 `action = access_policy_evaluated` 审计必须引用同一 ID，不得用异步审计日志替代策略评估事实表。
- `request_type = session_create` 且会创建会话记录时，api-server 必须先预分配 `session_id`，再把同一 ID 写入 `policy_evaluations` 和 `sessions`；策略在创建会话前拒绝时，`session_id` 可以为空，但必须保留 `policy_evaluation_id`、审计和请求摘要。
- `disable_unattended`、`suspend_device`、`suspend_account` 和 `relay_quarantine` 是收紧动作，必须写审计并影响后续会话或 Relay 分配，不得被客户端忽略。
- `POST /v1/sessions`、`accept/reject/cancel/close`、文件传输元数据上报等设备绑定 API 必须校验账号 access token 和设备请求签名，不能只信任请求体中的 `controller_device_id` 或 `actor_device_id`。
- 设备请求签名必须至少绑定 `method`、`path`、`body_hash`、`request_id`、`device_id`、`account_id`、`timestamp` 和一次性 `api_nonce`；服务端必须校验设备归属、公钥、时间窗口和 nonce 未重放。

API 请求 canonical 输入固化（默认适用于所有需设备签名或 step-up 的 API）：

```text
body_hash = SHA256(canonical_request_body)
request_id = 请求随机不可枚举 ID
canonical_api_input = canonical("rctl-api-input-v1", method, path, body_hash, request_id, device_id, account_id, timestamp, api_nonce)
device_signature = Sign(device_private_key, SHA256(canonical_api_input))
operation_binding_hash = SHA256(canonical("rctl-operation-binding-v1", account_id, device_id, purpose, method, path, body_hash, request_id, expires_at_epoch_millis))
```

规则：

- JSON body 使用 RFC 8785 JCS 后计算 SHA-256，显式 `null` 保留、数组顺序保留；重复键、非法 UTF-8、NaN 和 Infinity 必须拒绝。非 JSON body 对原始字节计算 SHA-256，无 body 对空字节串计算 SHA-256。
- `method` 使用 ASCII 大写；`path` 字段包含规范化 path 和 query。path 按 RFC 3986 移除 dot segment并统一百分号编码，query 按编码后的键和值升序，重复键保留且按值排序。
- `operation_binding_hash` 与 `device_signature` 使用不同域分离标签 `rctl-operation-binding-v1` 与 `rctl-api-input-v1`，交叉用途不能复用 hash 或签名。
- `高风险 API` 提交 step-up challenge 时必须同时提交 `risk_challenge_id`，并在服务端重新计算 `operation_binding_hash`；与原请求的 method/path/body hash/request_id/purpose 任一不一致、challenge 未发出、已消费或过期时拒绝。
- `幂等键` 要求绑定的 `account_id`、`device_id`、`method`、`path`、`body_hash` 与该请求 canonical 输入完全一致；重复提交不同 body hash 拒绝并写安全日志。
- `controller_device_id` 必须等于设备请求签名中的 `device_id`；被控端调用 `accept/reject` 时，`actor_device_id` 必须等于会话的 `controlled_device_id`；主控端调用 `cancel` 时，`actor_device_id` 必须等于会话的 `controller_device_id`；主控端或被控端调用 `close` 时，`actor_device_id` 必须等于会话两端设备之一，并且 `actor_role` 必须与会话角色一致。
- `auth_method = temporary_code` 时，服务端按 `controlled_device_id` 选择当前有效且未消费的 verifier，创建 `pending_code_verification` session，并返回 `session_id`、`code_id`、`code_challenge`、`server_nonce` 和过期时间；主控端请求 challenge 前不需要知道 `code_id`。
- `POST /v1/sessions/{session_id}/temporary-code/verify` 只接收 `proof_scheme = opaque_ristretto255_sha512_v1`、`proof_step`、`opaque_ke1/opaque_ke3`、`client_nonce`、`transcript_hash` 和 proof 所需公开材料，不接收验证码明文；`proof_step = start` 返回 `opaque_ke2` 且不改变终态，`proof_step = finish` 校验通过后 session 进入 `code_verified`，失败、过期或尝试次数耗尽必须进入 `failed` 终态。
- `code_verified` 仍必须等待被控端显式 `accept/reject`；只有进入 `accepted` 后才允许候选交换、Relay 分配、signed key exchange 和业务通道建连。
- 无人值守凭据设置和轮换接口使用 `registration_step = start | finish` 承载 OPAQUE registration；启用和轮换必须来自目标被控设备的已认证设备签名请求；`start` 只接收 `proof_scheme = opaque_ristretto255_sha512_v1`、`opaque_registration_request` 和 `client_nonce`，返回 `registration_id`、`server_nonce` 和 `opaque_registration_response`；`finish` 只接收 `registration_id`、`credential_record`、`credential_salt` 和 `transcript_hash`，不接收无人值守密码明文。
- `DELETE /v1/devices/{device_id}/unattended-secret` 可以由目标被控设备、设备 owner 或管理员策略触发，但必须写明 actor 类型、原因和审计；远程关闭可以撤销能力，远程开启或轮换不得绕过目标设备签名。
- `auth_method = unattended` 时，`POST /v1/sessions` 创建 `pending_unattended_verification` session，并返回 `session_id`、`unattended_secret_id`、`version`、`unattended_challenge`、`server_nonce` 和过期时间。
- `POST /v1/sessions/{session_id}/unattended/verify` 只接收 `proof_scheme = opaque_ristretto255_sha512_v1`、`proof_step`、`opaque_ke1/opaque_ke3`、`client_nonce`、`transcript_hash` 和 proof 所需公开材料；`proof_step = start` 返回 `opaque_ke2` 且不改变终态，`proof_step = finish` 校验通过且有效权限 `require_prompt = false` 时 session 进入 `unattended_verified`，校验通过但 `require_prompt = true` 时 session 进入 `waiting_approval` 并等待被控端 `accept/reject`，失败、过期或尝试次数耗尽必须进入 `failed` 终态。
- `auth_method = account_prompt` 用于已登录账号发起需要被控端确认的会话，创建后进入 `waiting_approval` 并等待被控端 `accept/reject`，不得绕过确认。
- `GET /v1/sessions/{session_id}/effective-permissions` 返回服务端物化后的 9 项有效权限和 `permissions_digest`，客户端不得自行拼接权限 digest。
- Relay 分配前必须检查有效权限 `allow_relay`；`allow_relay = false` 时不得分配 Relay token，已有 Relay 打开尝试必须拒绝并写审计。
- Relay token 必须绑定 `permissions_digest` 和 `relay_token_epoch`，首版最大 TTL 为 60 秒；会话关闭、权限变化、`allow_relay` 变为 false、策略关闭会话或 Relay 节点被禁用时必须撤销旧 epoch。
- `privacy_screen = false` 时必须拒绝隐私屏请求；`block_local_input = false` 时必须拒绝本地输入保护请求。被控端本地关闭项不能被远程策略放宽。
- 首版隐私屏和本地输入保护的 step-up 在会话创建、权限授予或被控端本地安全设置变更前完成；运行时 `privacy_mode_request` 是应用层端到端加密业务消息，服务端只校验已物化权限和记录裁剪审计元数据。
- 远程重启必须通过 `POST /v1/sessions/{session_id}/reboot-requests` 创建请求，校验 `allow_remote_reboot`、step-up、主控设备签名、会话状态和幂等键；创建接口只接收 `reason_hash`，不得接收或保存 reason 自由文本；被控端执行前必须收到应用层端到端加密的 `reboot_request`，用其中 reason 重新计算 hash，并通过 `GET /v1/reboot-requests/{reboot_request_id}` 在线校验 API 请求 hash 和当前状态。
- `reboot_request.mode` 固定枚举为 `normal | safe_mode_reserved`；`safe_mode_reserved` 首版只保留，不执行，未知枚举必须拒绝。
- 远程重启 step-up 必须未过期，且完成时间不早于 `permissions_digest_last_changed_at_epoch_millis`、`allow_remote_reboot_last_changed_at_epoch_millis` 和 `policy_evaluated_at_epoch_millis` 三者最大值；`api_request_hash` 必须包含这些快照字段。
- `POST /v1/reboot-requests/{reboot_request_id}/state` 只能由被控端设备签名调用，用于上报本地提示、接受、取消、执行、离线前准备和自动恢复一次同意的裁剪元数据；不得携带 reason 明文、系统命令输出或业务明文。
- `POST /v1/reboot-requests/{reboot_request_id}/resume` 只能创建新会话或返回新会话所需 challenge，不得恢复旧业务通道或复用旧会话密钥。`reconnect_after_reboot = true` 只允许下发恢复意图、`reboot_resume_hint` 或新的 challenge，不能跳过 `accepted`、`code_verified`、`unattended_verified` 状态门控，不能跳过新的权限评估、候选交换、signed key exchange 和 `key_confirm`。无人值守恢复 token 规范格式固定为 `base64url(reboot_resume_token_id) "." base64url(reboot_resume_token_secret)`；API 必须先按 `reboot_resume_token_id` 定位记录，再常量时间比较 secret hash，并校验原账号、原主控设备、原被控设备、原 `reboot_request_id`、`permissions_digest`、恢复窗口、`reboot_resume_token_consumed_at_epoch_millis` 和 token 失效状态。临时协助自动恢复一次还必须校验 `auto_resume_consent = once_by_controlled_user`、被控端设备签名的 `local_consent_proof_hash` 和一次性消费状态；主控端不得提交 `local_consent_token`。
- `resume` API 不接收 `reconnect_after_reboot` 字段；请求体或 query 携带该字段时必须拒绝为 `unexpected_field`，恢复意图只能由原请求记录、`reboot_resume_token` 和权限绑定共同校验。
- 自动恢复一次同意撤销必须写 `consent_revoked_at_epoch_millis`、`consent_revoked_by_actor_type`、`consent_revoked_reason` 和 `remote_reboot_auto_resume_consent_revoked` 审计；撤销后 `/resume` 必须进入新的被控端确认流程或拒绝。
- Redis `reboot:resume:*` 只作为短期缓存、防重放和恢复加速；PostgreSQL `remote_reboot_requests` 行是 token 消费和失效事实源，Redis 缺失、过期或不一致时不得跳过 PostgreSQL 校验。
- 反诈举报必须接受被控设备签名；举报、限流、封禁和误报恢复必须写审计，不得保存远控业务明文。
- M8 组织、角色、设备组、条件访问和策略接口必须写策略变更审计，并记录 old/new policy 摘要和 old/new `permissions_digest`。
- M8 区域策略和 Relay 节点管理接口必须要求管理员权限和 MFA step-up；策略修改只影响新会话，违反新策略的旧会话必须按策略关闭或等待自然结束并写审计。
- `accept/reject/cancel/close/connection-state` 必须同步写 `sessions`、`session_events` 和 `audit_logs`。
- `POST /v1/sessions/{session_id}/accept`、`reject` 和 `cancel` 必须包含 `actor_type = device`、`actor_device_id`、`actor_role` 和幂等键；`reject`、`cancel` 必须额外包含 `reason`。设备主动 `close` 必须包含 `actor_type = device`、`actor_device_id`、`actor_role`、幂等键和 `reason`；服务端超时、服务端策略关闭或后台任务关闭必须使用 `actor_type = system` 或 `actor_type = service`，此时 `actor_device_id` 和 `actor_role` 为空，并记录 `actor_service` 或系统原因。
- 登录失败、未认证请求和限流拒绝审计使用 `actor_type = anonymous`；登录成功、refresh、logout、密码修改等账号级操作使用 `actor_type = account`；设备绑定、会话、文件传输和设备状态类操作使用 `actor_type = device`。
- `POST /v1/sessions`、`accept/reject/cancel/close` 和文件传输元数据写入的幂等键必须绑定设备请求签名中的 `account_id`、`device_id`、`method`、`path` 和 `body_hash`；重复请求只能返回同一结果，不得重复创建 session、event 或 audit。
- `cancel` 只用于业务通道建立前的主控端主动取消 pending 或待确认会话，必须把 `sessions.status` 写为 `cancelled`，并写 `cancelled` 事件和 `session_cancelled` 审计；验证码过期、proof 失败、无人值守 challenge 过期或被控端拒绝不得伪装成主控端取消；已进入 `connected/degraded/reconnecting` 的会话必须走 `close`。
- 主控端断开、被控端断开、超时和服务端策略关闭都走同一 `close` 状态机。
- `POST /v1/sessions/{session_id}/connection-state` 是会话连接状态写入的唯一入口；设备上报路径必须校验账号 access token 和设备请求签名，且上报设备必须属于该会话；signal-server 服务上报路径必须使用服务间 token 和服务身份签名，只能上报服务侧观测到的 `connected/degraded/reconnecting/failed`，不得伪造设备 actor。Signal WebSocket 的 `connection_state` 只能推送 API 已持久化后的非权威通知。
- `POST /v1/sessions/{session_id}/capability-events` 只接收设备签名的运行时能力审计元数据，用于剪贴板二次确认、隐私屏、本地输入保护和媒体状态等 E2EE payload 的裁剪审计；不得接收剪贴板内容、文件内容、输入文本、屏幕内容、密钥或完整 token。服务端必须校验上报设备属于会话角色，并按 `actor_type = device` 写审计。event_type 必须映射到数据库设计中的固定审计动作，未知 event_type 必须拒绝，不得写自由文本 action。
- 文件内容走远控数据通道；文件传输 API 只记录元数据和状态，必须包含 `file_name`、`safe_file_name`、`file_size_bytes`、`sha256`、`sender_device_id`、`receiver_device_id`、`direction`、`confirmed_by_controlled`、`confirmed_by_device_id`、`status`、接收端保存策略、路径 hash 和失败/取消原因。
- `PATCH /v1/file-transfers/{file_transfer_id}` 必须是设备签名的裁剪元数据上报入口，只允许写入 `requested/accepted/rejected/transferring/completed/failed/cancelled` 状态、`bytes_transferred`、`confirmed_by_device_id`、`confirmed_at_epoch_millis`、`cancelled_by_device_id`、安全展示文件名、接收端保存策略、路径 hash、失败/拒绝/取消原因和幂等键；不得上传文件内容、完整本地路径或业务明文。`confirmed_by_device_id` 必须等于会话被控端设备，`confirmed_by_controlled` 由服务端根据被控端签名确认推导写入，客户端不得自报 true；取消归因必须来自签名请求中的设备 ID。
- Relay 节点心跳必须使用服务间 token，不能复用用户 access token。
- 客户端更新 API 只下发签名 manifest 和制品元数据；客户端仍必须本地验证 manifest 签名、artifact hash 和平台安装包签名。
- `GET /v1/client/releases/latest` 返回的 manifest 必须由 `client_release_artifacts` 权威字段生成，覆盖 `manifest_version`、`min_supported_version`、`rollout_percent`、`mandatory`、`release_notes_url` 和 `manifest_expires_at_epoch_millis`，不得临时拼接未落库字段。
- `POST /v1/client/update-checks` 必须校验设备签名，并按 `event_type = checked/downloaded/verified/failed` 写入更新事件和固定审计动作；`verified` 必须包含 manifest 签名、artifact hash 和平台签名校验结果，失败原因使用固定错误码。
- V1 Core/M7 只实现只读更新 API、更新检查记录和 release-check 发布证据，不向普通客户端开放发布管理写接口。客户端发布、撤销和灰度比例变化只允许 M8/Admin 或 CI 受控内部入口执行；CI 入口必须具备等价签名、审批、审计、release key 隔离和制品 hash/SBOM 门禁，并用 `actor_type = service` 或等价 `published_by_service` 记录发布者。

## 3. Signal Server

职责：

- 维护 WebSocket 长连接。
- 设备在线状态。
- 会话邀请推送。
- 会话接受、拒绝、取消和关闭通知。
- 候选地址交换。
- Relay 分配。
- 反诈和区域策略下的 Relay 分配拒绝通知。
- 会话状态转发，且只转发 API 已持久化后的状态通知。

当前状态：

- 已有 `/health`。
- 已有 `/ws`。
- 已有 JSON 信令消息。
- 当前在线状态仍在内存中。

后续必须：

- 在线状态迁移到 Redis。
- 会话邀请可定向推送到被控端。
- 连接断开后清理在线状态。
- WebSocket 连接必须验证账号 token 和设备签名。

WebSocket 鉴权必须符合 `docs/spec/20260719170217641_协议设计.md` 的 `/ws 鉴权握手`：

- access token 只证明账号身份。
- 设备签名只证明设备身份。
- 两者都通过后，设备才允许进入在线状态。
- 服务端必须按 `rctl-client-capabilities-v1` 域分离标签计算 `client_capabilities_hash`，并校验该 hash 与设备签名覆盖字段一致。
- `hello_ok` 必须回显被设备签名覆盖的 `client_supported_protocol_versions_hash` 和 `client_capabilities_hash`；客户端或服务端发现回显值与 `hello_response` 不一致时必须关闭连接并不得写在线状态。
- 重连恢复会话时必须重新校验权限和会话状态。
- WebSocket 不负责首次设备注册；设备绑定、公钥上传和设备资料更新只走 API。

## 4. Relay Server

职责：

- QUIC Relay。
- TLS 443 Relay。
- UDP observe 服务。
- 会话流量统计。
- 限速。
- 节点健康上报。
- Relay token 校验。
- M8 区域策略下的 Relay 节点过滤和拒绝。

Relay 不负责：

- 账号登录。
- 权限决策。
- 解密业务明文。

Relay 业务数据边界：

- Relay 只能读取转发所需外层元数据，例如 `session_id`、通道标识、长度和流量统计。
- Relay 不得持有应用层会话密钥。
- Relay 不得解析视频帧、输入事件、剪贴板内容和文件分片明文。

Relay token 校验：

- token 必须绑定 `session_id`、当前连接设备、`role`、主控设备、被控设备、`relay_node_id`、传输类型、`permissions_digest`、`relay_token_epoch`、`relay_token_id`、签发时间和过期时间。
- 主控端和被控端必须使用不同角色级 token，不得共享同一个 bearer token。
- `relay_open` 必须携带设备签名，签名输入固定为 `SHA256(canonical("rctl-relay-open-v1", relay_open_without_signature))`，即 `device_signature = Sign(device_private_key, SHA256(canonical("rctl-relay-open-v1", relay_open_without_signature)))`；Relay 必须通过 `relay:session:{session_id}:authorization` 或等价服务端 introspection 获取设备公钥、key version 和撤销状态后校验签名。
- Relay 必须拒绝缺失 token、过期 token、跨 session token、跨设备 token 和非本节点 token。
- Relay 必须拒绝 `permissions_digest` 不匹配、`relay_token_epoch` 已撤销、会话已关闭、`allow_relay = false` 或 Relay 节点被禁用的 token。
- Relay 节点被禁用后，api-server/signal-server 发布的撤销状态必须在 2 秒内让所有新 `relay_open` 请求失败；超过该 SLO 仍接受新请求必须阻断发布。
- token 校验失败不得创建转发通道，必须写入安全日志或审计事件。
- Relay 必须校验 `relay_open` 中的 `token_binding_hash` 与 token 绑定字段一致。
- Relay 重放缓存键为 `relay_token_id + role + relay_open_nonce`。
- Relay 必须通过 `relay:session:{session_id}:authorization` 或等价服务端 introspection 获取短期授权状态、双方设备 ID、角色、公钥版本和撤销状态，不能只验证 token 签名就建立转发通道；缓存缺失、过期或显示设备密钥已撤销时必须拒绝。

Relay 必须记录：

- session_id
- relay_node_id
- region
- region_policy_id
- region_policy_version
- bytes_in
- bytes_out

## 6. 权限校验

校验顺序：

```text
账号有效
设备存在

会话权限允许
API 状态达到可建链门槛：`accepted` 或无需当次确认的 `unattended_verified`

反诈处置未拒绝
```

任何一步失败：

- 拒绝会话。
- 返回明确错误码。

## 9. 服务端验收

必须验证：

- API 健康检查。
- Signal WebSocket 握手。
- 设备注册。
- 登录第一段不签 token，finish 的设备签名、双 nonce、binding、IP、User-Agent 和协议版本防篡改、防重放。
- 只有 access token 或攻击者新公钥自签不能注册设备；grant 原子消费、失败回滚、并发一次成功和幂等重试有效。
- 无 MFA 登录注册设备但不建立 trust；TOTP/recovery trust 的 TTL、非滑动续期和高风险 step-up 限制有效。
- TOTP 恢复码 ciphertext 可在响应丢失、服务重启和 Redis 缺失后精确重放，服务端无恢复码明文。
- 启用/禁用 MFA 和修改密码原子撤销全部 account session 与 active trust，旧 access/refresh token 立即失败。
- `PATCH /v1/me/password {current_password,new_password}` 必须覆盖 MFA active 的 TOTP/recovery step-up + 旧密码再校验、无 MFA 的仅 password-change reauthentication、无 MFA 其他高风险 purpose 拒绝、`204` 无替代 token 和重新登录。
- challenge 必须验证 PostgreSQL 唯一事实源、Redis 尽力缓存、`required_methods` 事务条件、verified 未过期未消费精确重试的同语义 token 确定性重签，以及状态/审计事务闭合。
- challenge 取消必须验证 `cancelled` 与 `risk_challenge_failed(result=failure, reason=cancelled)` 同仓储事务提交；审计故障必须回滚状态，且不得出现新增 audit action。
- `account_sessions.mfa_verified` 必须验证登录显式写入、refresh 精确继承、服务重启/缓存丢失后语义不变；`login_mfa` 必须验证 pending 时 `device_id IS NULL` 且 `login_device_id` 保留真实 ID、registered 时两者相等。以上不得替代真实 PostgreSQL 测试结果。
- 未运行隔离、已迁移 PostgreSQL 的账号安全事务、并发和审计故障注入验收时，T005A/M2 必须保持阻断；Memory 测试和 SQL 形状单测不能替代实库门禁。
- 在线状态。
- 会话创建。
- 被控端收到邀请。
- Relay 分配。
- Relay token 缺失、过期、跨 session、跨设备和跨节点时拒绝转发。
- 反诈风险评估、举报、拉黑、限流和处置审计。
- 远程重启请求、取消、设备上线恢复和旧密钥拒绝。
- 键盘/IME 和媒体控制消息不落业务明文。
- 启用 M8 区域策略时，必须验证 Relay 区域过滤和 fail-closed；V1 Core 只验证单区域默认路径，且 UDP observe 的诊断 region 不作为合规权威。
- 审计日志写入。
- 服务重启后状态恢复策略符合预期。

## 10. 生产安全

必须：

- HTTPS/WSS。
- 密码 hash。
- 登录限流。
- MFA 和高风险操作 step-up。
- 条件访问拒绝优先。
- 反诈 cooldown、deny、suspend 处置优先。
- 验证码限流。
- 远程重启必须 step-up、本地提示和新会话恢复。
- 审计日志。
- 请求 ID。
- CORS 白名单。
- 安全响应头。
- 发布 manifest 签名校验和客户端更新审计。

禁止：

- 默认管理员弱密码。
- 日志输出敏感信息。
- Relay 拥有业务明文解密能力。
- 未验证 session relay token 就转发流量。
- 未签名 manifest 下发官方客户端更新。
- 远程绕过被控端本地设置开启隐私屏或本地输入保护。
- 静默远程重启。
- 服务端集中解密录制远控业务流。
- 在 T027B0 二次冻结决策为 `implement` 前开放生产会话录制 producer/API 或产生 `recording_*` 生产审计事件。
