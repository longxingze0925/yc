# 账号 MFA 与风险验证设计

## 1. 目标

账号安全必须覆盖普通登录和高风险操作，避免只靠邮箱密码保护远控入口。

目标：

- 支持账号 MFA。
- 支持新设备、新网络和异常登录的风险验证。
- 支持恢复码和受信任主控设备。
- 高风险操作必须 step-up 验证。
- 所有 MFA 和风险验证过程可撤销、可审计、可限流。

## 2. 范围

`V1 Core` 必须实现：

- 邮箱 + 密码登录。
- TOTP MFA。
- 一次性恢复码。
- 新主控设备登录风险挑战。
- 受信任主控设备。
- 高风险操作 step-up 验证。
- 登录、MFA、恢复码和受信任设备审计。

`V1 Commercial/M8` 增强：

- 组织强制 MFA。
- 条件访问触发 MFA。
- 成员和角色级 MFA 策略。
- SSO、企业 IdP 和 passkey 可以后置，不能阻塞 `V1 Core`。

不做：

- 短信验证码作为默认 MFA。
- 邮件验证码替代 TOTP。
- Face ID / Touch ID 作为服务端 MFA。iOS 生物识别只用于本地解锁客户端和保护本地 token。

## 3. MFA 因子

首版因子：

- `password`：账号主认证。
- `totp`：账号 MFA 主因子。
- `recovery_code`：一次性恢复码。
- `trusted_controller_device`：降低重复 MFA 频率的设备信任状态，不是 MFA 因子。

TOTP 规则：

- 服务端生成 TOTP secret，并只以加密形式保存。
- TOTP secret 只在 enrollment start/finish 窗口内展示给用户。
- enrollment finish 必须提交有效 TOTP code 后才启用。
- TOTP code 验证必须限流。
- 同一时间窗口的 TOTP code 不得重复使用。
- 删除或禁用任何 MFA 因子必须先完成 step-up 验证；禁用最后一个有效因子会让账号进入无 MFA 状态，必须写审计并提示风险。
- TOTP start 前客户端必须生成临时 X25519 密钥对并提交 `recovery_delivery_public_key`；finish 使用 `Idempotency-Key`，服务端只持久化恢复码 hash 和客户端可解密的 ChaCha20-Poly1305 ciphertext，不保存恢复码明文或服务端临时私钥。
- 首次 finish 与同账号、原 session、factor、delivery public key、finish binding 和幂等键的重试必须返回同一 `delivery_id/server_ephemeral_public_key/nonce/ciphertext/created_at_epoch_millis/expires_at_epoch_millis/recovery_code_count`；两个时间字段必须使用响应权威值构造 HKDF/AAD。
- 启用 TOTP 的成功事务必须先写因子、恢复码 hash 和 delivery ciphertext，再撤销账号全部 session 和 active trust；客户端解密并确认保存后重新登录。

恢复码规则：

- 开启 TOTP 后生成恢复码。
- 服务端只保存恢复码 hash。
- 每个恢复码只能使用一次。
- 使用恢复码登录后必须提示重新生成恢复码。
- 重新生成恢复码会立即作废旧恢复码。

受信任主控设备规则：

- 只降低同一账号、同一设备、低风险登录的 MFA 频率。
- 不能替代设备长期密钥签名。
- 不能绕过无人值守开启、策略放宽、隐私屏和本地输入保护等高风险操作的 step-up。
- 修改密码、禁用 MFA、账号被锁定、设备解绑或管理员撤销后必须失效。
- `device_signature_and_mfa` 建立 `standard` trust，最长 30 天；`device_signature_and_recovery_code` 建立 `high_risk_step_up_required` trust，默认 24 小时。
- 无 MFA 账号可以自动注册设备，但不得新增弱化的 trust proof 或创建 trusted-device 记录。
- 普通 trusted login、access token 使用和 refresh token 轮换只更新 `last_used_at_epoch_millis`，不得延长 `expires_at_epoch_millis`；刷新信任必须重新完成设备签名和 TOTP/recovery 风险验证。

## 4. 登录流程

普通登录：

```text
1. 客户端先加载或生成设备长期 Ed25519 密钥，再提交邮箱、密码、设备身份、32-byte client_nonce 和 protocol_version。
2. api-server 校验密码、账号状态、限流和风险信号，创建 `registered | pending_enrollment` 登录 challenge；密码正确也不签发 token。
3. 客户端调用 `POST /v1/auth/login/finish`，提交 challenge ID、登录请求/challenge binding、双 nonce 和可选 TOTP/recovery code，并以本次设备私钥签名请求。
4. api-server 校验 PostgreSQL challenge 状态、IP、User-Agent、协议版本、设备当前公钥或拟注册公钥、nonce 防重放和 required factors。
5. 校验成功后原子消费 challenge、创建 account session；已注册设备按既有 trust 或本次 MFA 结果处理信任，未注册设备签发一次性 enrollment grant。
6. 最后返回 token；未注册设备使用 grant 原子注册，只有本次完成 TOTP/recovery 时才同时建立 trusted controller device。
```

创建 account session 时必须把本次登录认证强度显式写入非空 `mfa_verified`：直接完成 TOTP/recovery code 或命中当前有效 trusted-device 时为 true；无 MFA 且未命中有效 trust 时为 false。该值是 session 快照，不是账号当前 MFA 状态，也不能替代高风险 step-up。

MFA challenge：

- 必须绑定 `account_id`、`request_id`、登录请求、`device_id`、设备状态、公钥 fingerprint、IP、User-Agent、`client_nonce`、`server_nonce`、风险决策、因子集合、协议版本和过期时间。
- 首版固定最大有效期为 5 分钟；私有化部署只能缩短，放宽必须先更新安全设计和测试方案。
- 首版固定最大尝试次数为 5 次；达到上限必须失败并写审计。
- 成功、失败、过期、取消都必须写审计。
- challenge 转为 `cancelled` 时，仓储必须锁定 PostgreSQL 权威行，并在同一事务内写 cancelled 状态与现有 `risk_challenge_failed` 审计；审计固定 `result = failure`、`reason = cancelled`。任一步失败全部回滚，不新增 cancel 专用 audit action。
- PostgreSQL `account_risk_challenges` 是 challenge 状态、尝试次数和终态的唯一事实源；Redis 只保存 payload 缓存、尝试租约、nonce、限流和短 TTL 加速状态。
- login finish 必须在同一 PostgreSQL 事务中锁定 challenge、消费 TOTP counter 或 recovery code、写终态和审计、建立 account session 及可选 enrollment grant。PostgreSQL 提交后 Redis 失败不能重开 challenge。

登录响应规则：

- `login_challenge_required` 响应不得包含 access token、refresh token 或 enrollment grant。
- refresh token 只能在本次登录 `required_factors` 全部通过后签发；账号未启用 MFA 时，仍必须完成密码、设备私钥证明和风险验证。
- MFA 失败不得暴露账号是否存在、TOTP 是否启用或恢复码剩余数量。

## 5. 风险验证

风险信号：

- 新主控设备。
- 新 IP 或新 ASN。
- 新国家或地区。
- 短时间登录失败过多。
- refresh token 异常重放。
- 设备指纹变化明显。
- 访问条件策略要求 MFA。
- 高风险 API 操作。
- 短时间发起大量临时协助会话。
- 同一主控设备连接大量陌生被控设备。
- 被控端举报或拉黑命中。
- Relay token 失败或流量异常。

高风险操作：

- 修改密码。
- 禁用 MFA。
- 重新生成恢复码。
- 添加或撤销受信任设备。
- 替换设备公钥、设备重绑定或设备密钥恢复。
- 开启、轮换无人值守凭据。
- 把 `require_prompt` 调整为免确认。
- 授予或被控端本地允许 `privacy_screen`。
- 授予或被控端本地允许 `block_local_input`。
- 请求远程重启。
- 放宽设备、组织或设备组策略。
- 发布客户端更新或撤销发布制品。
- 修改企业区域驻留策略。

Step-up 方法契约：

- `required_methods` 是 challenge 创建时根据 PostgreSQL 中的账号和 MFA 状态写入的事务级条件，不是客户端可指定字段或 Redis 权威值。
- 登录 challenge 还必须保存 `login_account_updated_at_epoch_millis`，它是第一段登录读取的账号安全版本快照，并被纳入 challenge binding；创建和 finish 都锁定账号并要求严格相等，安全变化、时钟回拨和并发都不得让旧 challenge 成功。
- MFA active 时，所有高风险 purpose 的 `required_methods` 固定为 `totp | recovery_code` 二选一；`password_change` 完成其一后仍必须在修改密码端点再校验旧密码。
- 无 MFA 时，只有 `password_change` 允许 `required_methods = password` 的 password reauthentication；其他高风险 purpose 必须返回 `mfa_enrollment_required`，不创建 challenge。
- password reauthentication 不得扩展为无 MFA 账号的通用 step-up 因子。

隐私屏和本地输入保护 step-up 冻结：

- 首版把 `privacy_screen`、`block_local_input` 的 step-up 放在会话创建、权限授予或被控端本地安全设置变更前完成。
- 完成 step-up 后，结果必须进入策略评估和 `permissions_digest`；运行时 `privacy_mode_request` 走应用层端到端加密业务通道，不再额外调用服务端 step-up API。
- 完成 step-up 后，最终是否启用仍以运行时本地 `device_local_security_settings.allow_*` 和平台实际结果为准；step-up 只是把会话级权限或本地允许项变更放行，不代表绕过本地开关。
- 如果未来要求每次运行时开关都 step-up，必须新增类似远程重启的 API request、canonical hash、过期和端点校验设计后再实现。

处理结果：

- `allow`：低风险，继续。
- `require_mfa`：必须完成 MFA challenge。
- `deny`：拒绝并写审计。
- `lock_account`：临时锁定账号并写审计。

## 6. API 设计

账号 MFA：

```text
PATCH /v1/me/password
GET  /v1/me/mfa
POST /v1/me/mfa/totp/start
POST /v1/me/mfa/totp/finish
DELETE /v1/me/mfa/factors/{factor_id}
POST /v1/me/mfa/recovery-codes/rotate
POST /v1/auth/login/finish
GET  /v1/me/trusted-devices
DELETE /v1/me/trusted-devices/{trusted_device_id}
```

风险 challenge：

```text
POST /v1/auth/risk-challenge
POST /v1/auth/risk-challenge/{challenge_id}/verify
```

规则：

- 高风险 API 可以返回 `step_up_required`，客户端必须先完成 risk challenge。
- step-up token 只能用于指定操作、指定账号、指定设备和短时间窗口。
- step-up token 不得用于 WebSocket 设备上线和会话业务通道。
- `PATCH /v1/me/password` 请求体精确为 `{current_password,new_password}`，成功返回 `204 No Content`。MFA active 时必须同时具备 `password_change` TOTP/recovery step-up 和正确 `current_password`；无 MFA 时必须同时具备 `password_change` password reauthentication 和端点对 `current_password` 的再校验。
- 密码修改事务必须原子消费 challenge、确认已验证的旧密码 hash 仍是当前值、写入新 Argon2id hash、以 `password_changed` 撤销账号全部 `account_sessions` 和 active trust，并写审计。成功后不签发替代 access/refresh/step-up token，客户端必须使用新密码重新登录。
- MFA 和 risk challenge API 必须与 `/ws` 共用 `protocol_version` 端点校验规则；无交集、不支持或低于 `client_min_protocol_version` 时同样返回 `unsupported_version`。
- `/v1/auth/login/finish` 必须使用 `rctl-api-input-v1` 设备签名 Header；旧 `/v1/auth/mfa/verify` 不得继续签发 token，迁移期只能返回升级错误。
- 设备绑定 API 必须同时执行账号 session、一次性 enrollment grant 和拟注册设备私钥签名校验，不能只靠 MFA 或 access token。
- PostgreSQL 是 risk challenge 的唯一事实源，Redis 只做尽力缓存。已验证 challenge 的同账号/设备/purpose/binding 重试只在 `status = verified`、未过期且未消费时确定性重签同语义 token，不重复消费因子或写成功审计。
- challenge 创建与发行审计、因子消费/状态更新与验证审计、高风险业务写入/challenge 消费与业务审计，必须分别在同一 PostgreSQL 事务内闭合；任一审计或状态写入失败都整体回滚。
- refresh token 轮换必须与旧 session 消费、替代 session 插入和刷新审计处于同一账号锁事务；替代 session 的 `mfa_verified` 必须从旧 PostgreSQL 行读取并原样继承，不得根据账号当前 MFA 状态、Redis/内存缓存、请求参数或服务默认值重新计算。服务重启、缓存丢失和 Repository 重建不得使会话认证语义降级或提升；密码/MFA 安全事务提交撤销后，基于撤销前只读快照的 refresh 不得复活 session。
- login finish 的 grant/trust/审计集合校验必须由 Memory 与 PostgreSQL 共用同一契约：跨 challenge、跨账号/设备/session、fingerprint 不匹配、非法 trust 决策或 TTL、已消费/带注册结果的 grant、重复审计 ID 均拒绝。
- logout 的 session 撤销、`account_session_revoked` 对象审计和 `logout` 顶层审计必须在同一仓储事务中完成，审计失败不得留下已撤销 session。

风险 challenge 规则：

- `account_mfa_factors.factor_type` 首版固定集合为 `totp`；`password`、`recovery_code` 和 `trusted_controller_device` 分别由账号密码、恢复码表和受信任设备表表达，不作为本列取值。
- `account_mfa_factors.status` 首版固定集合为 `active`、`disabled`。
- `account_risk_challenges.purpose` 首版固定集合为 `login_mfa`、`new_controller_device`、`trusted_device_change`、`password_change`、`mfa_factor_change`、`recovery_code_rotate`、`device_key_rotation`、`unattended_secret_change`、`require_prompt_relax`、`allow_privacy_screen`、`allow_block_local_input`、`allow_remote_reboot`、`remote_reboot`、`access_policy_change`、`client_release_change`、`region_policy_change`。
- `account_risk_challenges.risk_level` 首版固定集合为 `low`、`medium`、`high`。
- `account_risk_challenges.status` 首版固定集合为 `issued`、`verified`、`failed`、`consumed`、`expired`、`cancelled`。
- `account_risk_challenges.expires_at_epoch_millis` 首版最大窗口为创建后 5 分钟；`attempts_remaining` 初始值最大为 5。
- `purpose = login_mfa` 时，`operation_binding_hash` 保存本次 `login_challenge_binding_hash`，`login_*` 字段结构化保存登录请求 binding、设备身份/公钥、双 nonce、IP/User-Agent hash、可选 trusted-device、协议版本和初始尝试上限；Redis 丢失时从 PostgreSQL 恢复且仍以数据库消费为准。包含 TOTP/recovery code 的 finish body hash 不得落库。
- `login_account_updated_at_epoch_millis` 只用于 `login_mfa`，保存第一段读取的账号安全版本；它必须纳入 challenge binding，创建和 finish 事务必须锁定账号并严格比较当前值。
- `purpose = login_mfa` 且 `login_device_state = pending_enrollment` 时，`device_id` 必须为 NULL，真实拟注册设备 ID 必须保存在非空且不引用 `devices` 的 `login_device_id`；`login_device_state = registered` 时两列必须都非空且严格相等。
- 新增设备唯一授权路径固定为 `/v1/auth/login` 两段式 challenge 加 enrollment grant。`purpose = new_controller_device` 保留在固定枚举中仅用于兼容既有记录和审计语义；V1 通用 `/v1/auth/risk-challenge` 不得为未知 `device_id` 签发该 purpose 的 challenge。未知设备必须走 `login_mfa + pending_enrollment`，写入 `device_id = NULL` 且由 `login_device_id` 保存真实拟注册 ID。
- 其他 purpose 使用 `operation_binding_hash = SHA256(canonical("rctl-operation-binding-v1", account_id, device_id, purpose, method, path, body_hash, request_id, expires_at_epoch_millis))`；`body_hash = SHA256(canonical_request_body)`，与协议其他 canonical 使用一致的 length-prefixed 字段编码。
- `required_methods` 必须在 challenge 创建事务中由账号当前 MFA 状态决定并与 challenge 一起持久化：MFA active 时为 `totp | recovery_code`；无 MFA 时仅 `password_change` 可为 `password`。验证事务必须使用行中值做条件，不得从 Redis 或客户端重建。
- 高风险 API 验证 step-up 时必须重新计算 `operation_binding_hash`，不匹配则拒绝。
- step-up challenge 成功后必须一次性消费；`consumed_at_epoch_millis` 写入、challenge 过期或操作绑定不匹配后，不得再次用于任何高风险操作。仅限 `verified` 且未过期、未消费的精确重试可重签同语义 token。

`trusted_controller_devices` 关键字段：

- `trusted_device_id`
- `account_id`
- `controller_device_id`
- `device_fingerprint_hash`
- `trust_level`
- `status`
- `trust_proof_type`
- `created_at_epoch_millis`
- `last_used_at_epoch_millis`
- `expires_at_epoch_millis`
- `revoked_at_epoch_millis`

规则：

- `trust_level` 首版固定集合为 `standard`、`high_risk_step_up_required`。
- `status` 首版固定集合为 `active | expired | revoked`，最长有效期 30 天。
- `trust_proof_type` 首版固定集合为 `device_signature_and_mfa | device_signature_and_recovery_code`。
- TOTP trust 最长 30 天；recovery-code trust 默认 24 小时且固定 `high_risk_step_up_required`。普通登录和 refresh 不得滑动续期。
- `controller_device_id` 必须通过非空复合外键引用同账号 `devices(device_id, account_id)`；未注册设备不得先插入 trust。

`device_enrollment_grants` 必须保存 grant secret hash、账号、设备 ID、公钥 fingerprint、登录 challenge/binding、`establish_trust`、可空 trust proof/level、协议版本、签发 session、签发/过期/消费时间；TTL 不超过 5 分钟，PostgreSQL 是一次性消费事实源。

`mfa_recovery_code_deliveries` 必须保存账号、原 session、factor、幂等键 hash、finish binding、双方临时公钥、nonce、ciphertext、恢复码数量、过期和确认时间；不得保存恢复码明文或服务端临时私钥。

## 8. 审计

必须新增或支持审计动作：

- `mfa_factor_enrolled`
- `mfa_factor_disabled`
- `mfa_recovery_codes_rotated`
- `mfa_recovery_code_used`
- `mfa_challenge_issued`
- `mfa_challenge_succeeded`
- `mfa_challenge_failed`
- `risk_challenge_issued`
- `risk_challenge_succeeded`
- `risk_challenge_failed`
- `trusted_device_added`
- `trusted_device_revoked`
- `device_enrollment_grant_consumed`
- `account_session_revoked`
- `password_changed`

不得记录：

- TOTP secret 明文。
- TOTP code。
- 恢复码明文。
- step-up token 明文。
- 设备指纹原文。

## 9. 客户端要求

桌面和 iOS 主控端必须提供：

- TOTP 绑定和确认。
- TOTP 输入。
- 恢复码查看、确认保存和重新生成。
- 受信任设备管理。
- step-up 验证弹窗。
- 新设备登录和高风险操作的明确提示。
- 登录前设备身份加载、`login/finish`、一次性 enrollment grant 自动注册和 grant 过期重试。
- TOTP finish 恢复码 ciphertext 解密、相同幂等键重试和确认保存；启用成功后按已撤销 session 重新登录。

客户端本地保存：

- access token 和 refresh token 必须进入系统安全存储。
- iOS 可用 Face ID / Touch ID 保护本地打开客户端，但不能宣称为服务端 MFA。
- 日志不得输出 MFA code、恢复码或 step-up token。

## 10. 测试要求

必须验证：

- 未启用 MFA 的低风险登录可成功。
- 启用 MFA 后密码正确但未完成 MFA 不签发 token。
- 密码正确的第一段登录不得签发 token；finish 任一 binding、双 nonce、IP、User-Agent、协议版本或设备签名变化必须拒绝。
- 已注册设备必须使用数据库当前公钥；未注册设备只能使用 challenge 绑定的拟注册公钥。
- 只有 access token 或攻击者新公钥自签不得注册设备；grant 跨账号、设备、公钥、challenge、过期或重放必须拒绝。
- TOTP 错误、过期、重复使用被拒绝。
- 恢复码只能使用一次。
- TOTP finish 响应丢失后，同幂等键必须返回同一 ciphertext；服务端重启、Redis 丢失后仍以 PostgreSQL 结果重放，数据库和日志均不含恢复码明文。
- 删除或禁用任何 MFA 因子，包括最后一个有效因子，必须 step-up。
- 新设备登录触发 MFA 或风险挑战。
- 受信任设备撤销后重新登录触发 MFA。
- 无 MFA 新设备自动注册但不建立 trust；普通 trusted login 和 refresh 不延长 TTL，recovery-code trust 不能绕过高风险 step-up。
- account session 必须持久化 `mfa_verified`，refresh 前后该值严格相等；服务重启、Redis 丢失或仅从 PostgreSQL 恢复 session 后不得从 true 变 false 或从 false 变 true。
- `login_mfa` 的 `pending_enrollment` 行必须保持 `device_id IS NULL` 且 `login_device_id` 等于真实拟注册 ID；`registered` 行两者必须相等。通用 `/v1/auth/risk-challenge` 对未知设备的 `new_controller_device` 必须拒绝且不落库，未知设备只走两段式登录加 enrollment grant。
- 启用/禁用 MFA 或修改密码必须在安全状态事务内撤销账号全部 session 和 active trust；事务失败不得部分提交。
- 每条实际撤销的 session/trust 必须各写一条对应对象审计；任一对象审计失败时，factor/password、challenge 消费、全部撤销和顶层业务审计都必须回滚。
- MFA active 时 `password_change.required_methods` 必须为 TOTP/recovery code，且 `PATCH /v1/me/password` 对旧密码的独立再校验必须生效；无 MFA 时仅 `password_change` 可使用 password reauthentication，其他高风险 purpose 必须要求先启用 MFA。
- `PATCH /v1/me/password {current_password,new_password}` 成功必须返回 `204`、不返回任何替代 token，并使当前及其他全部 access/refresh session 和 active trust 失效；错误旧密码、旧 hash 并发变化或事务内审计写入失败时不得部分修改。
- Redis 缺失、超时或重启后，challenge 必须以 PostgreSQL 状态继续；`verified` 未过期未消费的精确重试必须确定性重签同语义 token，已消费/失败/过期/取消必须稳定拒绝，且成功审计不重复。
- challenge 发行、验证、失败和业务消费的状态与对应审计必须分别事务闭合，故障注入必须证明不会只写状态或只写审计。
- challenge 取消必须原子提交 `status = cancelled` 与 `risk_challenge_failed(result=failure, reason=cancelled)`；状态写入或审计写入故障必须全部回滚，审计动作集合不得增加 cancel 专用值。
- 旧 login challenge 失效必须覆盖同毫秒、时钟回拨、改密/MFA 变化后 finish、challenge 创建与安全变化并发；必须同时验证 Memory 与真实 PostgreSQL 结果。
- 开启或轮换无人值守凭据必须 step-up。
- 关闭 `require_prompt`、授予或被控端本地允许 `privacy_screen`、授予或被控端本地允许 `block_local_input` 必须 step-up。
- 请求远程重启必须 step-up。
- 反诈举报、拉黑和处置命中时必须按策略要求 MFA、确认、冷却或拒绝。
- 组织强制 MFA 策略在 M8 生效。
- 日志和审计不包含 TOTP secret、TOTP code、恢复码明文或 step-up token。
