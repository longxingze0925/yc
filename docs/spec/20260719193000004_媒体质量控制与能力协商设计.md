# 媒体质量控制与能力协商设计

## 1. 目标

首版远控画面以办公场景 1080p 稳定可用为目标。媒体设计必须支持低延迟、弱网自适应、硬件编解码失败兜底和跨平台能力差异，同时不把首版范围扩大成 4K/144fps 游戏串流。

目标：

- 固定 `client_capabilities` schema。
- H.264 为 V1 必选能力。
- 支持分辨率、帧率、码率和关键帧请求控制。
- 弱网时优先保证输入响应。
- 硬编不可用时可降级软件编码或降低质量。
- V1 Core 只做远控画面视频，不做系统音频采集、传输和远端播放。
- H.265、AV1、4:4:4 和 HDR 只预留，不作为 V1 Core 验收。

## 2. 范围

`V1 Core` 必须实现：

- H.264 baseline/main/high 能力协商。
- 1080p 办公画面质量档位。
- 动态码率。
- 降帧和降分辨率。
- 关键帧请求。
- 硬件编码、硬件解码和软件兜底能力上报。
- 统计上报：RTT、丢包、抖动、码率、帧率、编码耗时、解码耗时、CPU、内存。

后置增强：

- 系统音频采集、传输和远端播放。
- H.265。
- AV1。
- 4:4:4 色彩。
- HDR。
- 4K/高刷新率。
- 游戏级低延迟调优。

## 3. 能力协商

`hello_response.client_capabilities` 必须包含：

- `platform`
- `arch`
- `app_version`
- `protocol_version`
- `role_capabilities`
- `display_capabilities`
- `codec_capabilities`
- `input_capabilities`
- `transport_capabilities`

顶层和嵌套字段类型、顺序固定如下；该顺序也是 `rctl-client-capabilities-v1` canonical 输入顺序：

- `platform: enum(windows|ubuntu|ios)`。
- `arch: enum(x86_64|aarch64)`。
- `app_version: semver string`。
- `protocol_version: u16`。
- `role_capabilities`：按 `controller: bool`、`controlled: bool`、`file_transfer: bool`、`unattended: bool` 顺序。
- `display_capabilities`：按 `max_displays: u16`、`max_width: u32`、`max_height: u32`、`rotation: bool`、`dynamic_resize: bool` 顺序。
- `codec_capabilities`：按下方字段列出顺序编码；数值为无符号整数，能力开关为 bool。
- `input_capabilities`：按 `mouse: bool`、`physical_keyboard: bool`、`text_commit: bool`、`ime_composition: bool`、`touch: bool`、`external_pointer: bool` 顺序。
- `transport_capabilities`：按 `lan_direct: bool`、`udp_p2p: bool`、`quic_relay: bool`、`tls_443_relay: bool`、`quic_datagram: bool`、`max_datagram_bytes: u32` 顺序。

数组字段必须去重并按 UTF-8 字节升序 canonical；未知对象字段、负数、超出整数范围和错误类型必须拒绝握手。iOS 固定 `controlled = false`、`unattended = false`。

`codec_capabilities` 字段：

- `h264`
- `h265_reserved`
- `av1_reserved`
- `max_decode_width`
- `max_decode_height`
- `max_decode_fps`
- `max_encode_width`
- `max_encode_height`
- `max_encode_fps`
- `hardware_encode`
- `hardware_decode`
- `software_encode`
- `software_decode`
- `profiles`
- `pixel_formats`
- `color_modes`

字段类型：`h264/h265_reserved/av1_reserved/hardware_encode/hardware_decode/software_encode/software_decode` 为 bool；宽高和帧率上限为 u32；`profiles/pixel_formats/color_modes` 为去重排序后的字符串数组。V1 profile 固定支持 `baseline | main | high` 中实现子集，pixel format 固定支持 `nv12 | i420` 中实现子集，color mode 必须包含 `yuv420`。

V1 固定：

- `h264 = required`
- `color_modes` 必须支持 `yuv420`
- `yuv444_reserved` 只预留
- `h265_reserved` 和 `av1_reserved` 不作为验收能力

规则：

- 双方能力交集为空时不得建立媒体通道。
- 被控端是编码能力事实源，主控端是解码和显示能力事实源。
- 主控端可以请求质量档位，被控端根据本地负载、网络状态和平台能力决定最终参数。
- 能力协商结果必须写入会话诊断和测试证据，但不得包含屏幕内容。

## 4. 媒体控制消息

新增业务消息类型：

- `media_capabilities`
- `media_config_request`
- `media_config_state`
- `media_quality_request`
- `media_quality_state`
- `keyframe_request`

`media_config_request` 字段：

- `session_id`
- `display_id`
- `preferred_codec`
- `max_width`
- `max_height`
- `max_fps`
- `max_bitrate_kbps`
- `quality_profile`
- `color_mode`
- `timestamp_epoch_millis`

`quality_profile` 取值：

- `balanced`
- `text_clear`
- `low_bandwidth`
- `low_latency`

`media_config_state` 字段：

- `session_id`
- `display_id`
- `codec`
- `width`
- `height`
- `fps`
- `bitrate_kbps`
- `profile`
- `pixel_format`
- `color_mode`
- `hardware_acceleration`
- `state`
- `reason`
- `timestamp_epoch_millis`

`keyframe_request` 字段：

- `session_id`
- `display_id`
- `reason`
- `last_received_frame_id`
- `timestamp_epoch_millis`

规则：

- 媒体控制消息必须走应用层端到端加密业务通道。
- 服务端可保存的能力摘要仅限 `/ws` hello 中已由设备签名覆盖的粗粒度 `client_capabilities`，用于在线状态、调度和诊断。
- 会话内 `media_capabilities`、媒体配置和质量控制 payload 必须走应用层端到端加密业务通道；Signal/API 不得明文保存或解析这些 payload，也不得保存视频帧明文。
- `keyframe_request` 必须限流，避免被滥用造成编码压力。

## 5. 自适应策略

优先级：

```text
输入延迟 > 当前画面时效 > 文字可读性 > 帧率 > 分辨率 > 文件传输速度
```

降级顺序：

1. 降低视频帧率。
2. 降低码率。
3. 降低分辨率。
4. 切换到更保守 H.264 profile。
5. 禁用非必要视觉增强。
6. 软件编码压力过高时进一步降帧。

禁止：

- 旧帧堆积导致画面延迟持续扩大。
- 文件传输抢占控制通道。
- 为保持清晰度让输入事件持续排队。
- 把 H.265/AV1 能力写成 V1 必选。
- 把系统音频写成 V1 Core 必选。

可验收指标定义：

- 输入排队时延采集点固定为：主控端发送输入事件的 monotonic timestamp 到被控端完成 SendInput、Wayland portal、X11 注入或明确返回 unsupported 的 monotonic timestamp 差值；该指标不等同于视频 RTT。
- “持续 500ms 以上输入排队”指连续 5 秒滑动窗口内，超过 500ms 的输入排队样本占比大于 20%，或任一单段连续排队时间超过 500ms 且没有丢弃旧帧/降级动作。
- 当前画面时效使用帧 age 衡量：被控端采集 timestamp 到主控端完成渲染 timestamp，LAN Direct 目标不超过 200ms，Relay 目标不超过 350ms；弱网降级时必须优先丢弃旧帧而不是排队。
- 文字可读性使用 `text_clear` 质量档位约束：1080p 办公文本场景不得低于 baseline 1.5x 等效 DPI；如果网络无法满足，必须明确降级原因并优先保持输入可达。
- `media_quality_state.reason` 枚举固定为 `link_loss_high | rtt_high | jitter_high | encode_backpressure | decode_backpressure | cpu_high | thermal_limit | battery_saver | keyframe_loss | user_requested | policy_limited`。
- 降级开始和恢复必须分别上报 `media_quality_changed` 裁剪审计，metadata 只记录 reason、质量档位、fps/bitrate/resolution 摘要和统计摘要，不得记录画面内容。

## 6. 平台策略

Windows：

- 编码优先级：NVENC/QSV/AMF -> 软件兜底。
- 渲染使用 D3D11 / DirectComposition。
- 硬编失败必须降级，不得直接崩溃会话。

Ubuntu：

- 编码优先级：VAAPI -> 软件兜底。
- Wayland/PipeWire 和 X11 fallback 的帧率、损耗和权限状态必须进入诊断。
- 驱动能力不足时必须明确提示。

iOS：

- 解码使用 VideoToolbox。
- 渲染使用 Metal。
- 热、后台、低电量或解码失败时必须降低质量或提示。

## 7. 数据和观测

V1 不新增专用媒体质量表。媒体质量数据优先通过：

- 客户端本地诊断日志。
- `stats` 业务消息。
- `session_events` 的裁剪 metadata。
- `relay_session_stats` 的 Relay 元数据。
- 测试证据包。

可以记录：

- codec。
- 分辨率。
- 帧率。
- 码率。
- RTT、丢包、抖动。
- 编码/解码耗时。
- CPU、内存。

不得记录：

- 视频帧内容。
- 截图内容，除非是 QA 人工证据并按测试方案保存。
- 窗口标题、输入文本和剪贴板内容。

## 8. 测试要求

必须验证：

- 双方 H.264 能力协商成功。
- 能力不匹配时拒绝媒体通道并显示原因。
- Windows 硬编可用和硬编不可用兜底。
- Ubuntu VAAPI 可用和不可用兜底。
- iOS VideoToolbox 解码和失败提示。
- 弱网下降帧、降码率或降分辨率。
- `keyframe_request` 能恢复花屏或丢关键帧后的画面。
- 100MB 文件传输时输入不持续排队。
- LAN Direct 1080p 办公场景不低于 30fps。
- Relay 1080p 办公场景不低于 20fps。
- 系统音频不作为 V1 Core 验收。
- 日志和服务端不包含视频帧明文。
