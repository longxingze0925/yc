# 安全与密钥协议设计

## 1. 目标

远控软件的安全设计必须从第一版开始固定。目标是：

- 服务端不能伪造设备身份。
- 服务端不保存设备私钥。
- Relay 不具备业务明文解密能力。
- 会话必须绑定账号、设备、权限和传输路径。
- 隐私屏和本地输入保护必须作为独立权限绑定到会话密钥上下文。
- 远程重启后只能创建新安全会话，不得复用旧会话密钥。
- 未来会话录制只能端点侧显式录制，Relay/API/Signal 仍不得解密业务明文。
- 验证码、无人值守凭据、私钥不得明文传输或记录。

## 2. 身份边界

账号身份：

- 代表用户。
- 由 `api-server` 认证。
- 产生登录态和访问令牌。

设备身份：

- 代表一台安装客户端的设备。
- 每台设备首次初始化时生成长期密钥对。
- 服务端只保存设备公钥。
- 设备私钥仅保存在本机安全存储中。

会话身份：

- 由 `session_id` 标识。
- 绑定主控设备、被控设备、账号、权限和过期时间。

## 3. 推荐算法

设备签名：

```text
Ed25519
```

会话密钥交换：

```text
X25519
```

密钥派生：

```text
HKDF-SHA256
```

应用层加密：

```text
ChaCha20-Poly1305
```

密码哈希：

```text
Argon2id
```

说明：

- QUIC/TLS 提供传输层加密。
- 应用层端到端密钥用于防止 Relay 或中间层获取业务明文。
- 第一版远控业务通道必须实现应用层端到端加密。

首版强制要求：

- 视频帧、媒体控制、输入事件、剪贴板内容、文件分片和远程重启业务消息必须经过应用层端到端加密后再进入 P2P 或 Relay 通道。
- 隐私屏和本地输入保护控制消息必须经过应用层端到端加密，并按会话权限校验。
- Signal/API/Relay 只能处理会话元数据、连接候选、权限结果和流量统计，不得获得业务明文或会话密钥。
- 未完成应用层端到端加密前，只允许做本地协议桩和受控测试，不允许把真实远控链路标记为通过验收。
- TLS/QUIC 传输层加密不能替代应用层端到端加密。

## 4. 设备注册

流程：

```text
1. 客户端生成 device_keypair。
2. 客户端登录账号。
3. 客户端提交 device_id、platform、display_name、public_key。
4. api-server 校验账号。
5. api-server 保存设备公钥、`public_key_id` 和 `public_key_version`。
6. 设备后续上线时用私钥签名 challenge。
```

设备上线证明：

```text
server_nonce
client_nonce
account_id
device_id
protocol_version
client_supported_protocol_versions_hash
client_capabilities_hash
timestamp
signature = Sign(device_private_key, SHA256(canonical("rctl-ws-hello-v1", server_nonce, client_nonce, account_id, device_id, protocol_version, timestamp, client_supported_protocol_versions_hash, client_capabilities_hash)))
```

服务端必须校验：

- `account_id` 来自 access token，并与客户端签名 payload 中的 `account_id` 一致。
- `protocol_version` 来自服务端和客户端支持版本交集；无交集、不支持或低于客户端 `client_min_protocol_version` 时必须返回 `unsupported_version`，不得写在线状态。
- 设备存在。
- 公钥、`public_key_id` 和 `public_key_version` 匹配，且该公钥未撤销。
- `client_supported_protocol_versions_hash` 与 Upgrade Header 中 `X-Rctl-Protocol-Versions`、`X-Rctl-Min-Protocol-Version` 解析后的去重升序集合和最低版本的 canonical hash 一致，并被设备签名覆盖；hash 固定为 `SHA256(canonical("rctl-protocol-versions-v1", sorted_unique_client_supported_protocol_versions, client_min_protocol_version))`。
- `client_capabilities_hash = SHA256(canonical("rctl-client-capabilities-v1", client_capabilities))`，必须与 `hello_response.client_capabilities` 一致，并被设备签名覆盖。
- nonce 未使用。
- timestamp 在允许窗口内。
- 签名有效。

设备公钥版本规则：

- 首次绑定时 `public_key_version = 1`。
- 替换设备公钥必须视为设备重绑定或密钥轮换，高风险场景需要 step-up，并写设备安全审计。
- 公钥版本变化后，旧版本不得再通过 WebSocket、API 设备签名、signed key exchange 或 Relay `relay_open` 校验。
- 公钥撤销必须关闭或重新评估受影响会话，并撤销对应 Relay 授权缓存。
- `device_public_key_rotated` 和 `device_public_key_revoked` 审计 metadata 必须包含旧公钥 ID、旧公钥版本、旧公钥 fingerprint、撤销时间、原因和新公钥 ID/版本；不得保存设备私钥。

## 5. 会话密钥交换

会话建立时：

```text
1. api-server 创建 session_context。
2. API 状态达到可建链门槛：临时验证码和账号确认会话必须进入 `accepted`，无人值守会话在 `require_prompt = false` 时进入 `unattended_verified`，在 `require_prompt = true` 时进入 `accepted`。
3. 双方完成候选竞速，确定 selected_transport。
4. 主控端生成 ephemeral_x25519_keypair。
5. 被控端生成 ephemeral_x25519_keypair。
6. 双方用设备长期 Ed25519 私钥签名 signed_key_exchange_payload。
7. 双方通过 signal-server 交换已签名的临时公钥。
8. 双方校验对端设备公钥、签名和 signed_key_exchange_payload。
9. 双方使用 X25519 得到 shared_secret。
10. 双方用 HKDF 派生 send_key / receive_key。
11. 双方交换并验证 `key_confirm`。
12. `key_confirm` 通过后才允许发送业务密文。
```

`session_context` 必须包含：

```text
account_id
session_id
controller_device_id
controlled_device_id
permissions_digest
protocol_version
session_expires_at_epoch_millis
```

`session_context_hash`：

```text
session_context_hash = SHA256(canonical_session_context)
```

`canonical_session_context` 使用协议规范中的确定性字段顺序和长度前缀编码，不使用 JSON 对象自然顺序。

`signed_key_exchange_payload` 必须包含：

```text
session_id
device_id
role
session_context_hash
permissions_digest
session_expires_at_epoch_millis
ephemeral_public_key
key_exchange_nonce
selected_transport_path
selected_candidate_pair_id
relay_node_id
timestamp
```

签名：

```text
signed_key_exchange_canonical_bytes = canonical("rctl-signed-key-exchange-v1", signed_key_exchange_payload_fields)
key_exchange_signature = Sign(device_private_key, SHA256(signed_key_exchange_canonical_bytes))
key_exchange_transcript_hash = SHA256(controller_signed_key_exchange_canonical_bytes || controller_key_exchange_signature || controlled_signed_key_exchange_canonical_bytes || controlled_key_exchange_signature)
```

规则：

- `ephemeral_public_key` 未携带有效设备签名时必须拒绝会话。
- `role` 只能是 `controller` 或 `controlled`，不能复用对端签名。
- `permissions_digest` 和 `session_expires_at_epoch_millis` 必须与 `session_context_hash` 对应的 canonical session context 一致。
- `selected_transport_path` 必须是最终选用路径：`lan_direct`、`udp_p2p`、`quic_relay` 或 `tls_443_relay`。
- 非 Relay 路径下 `relay_node_id` 为空；Relay 路径下必须绑定实际 Relay 节点。
- `key_exchange_transcript_hash` 不得放入 `signed_key_exchange_payload`，避免自引用。
- 双方必须独立计算 `session_context_hash` 和 canonical payload，不得直接信任对端传来的 hash。
- `signed_key_exchange_canonical_bytes` 是包含 `rctl-signed-key-exchange-v1` 域分离标签的 exact canonical bytes，签名校验和 transcript 必须使用同一份 bytes，不得改用不带标签的 payload bytes。
- `controller_key_exchange_signature` 和 `controlled_key_exchange_signature` 固定为原始 64-byte Ed25519 signature bytes。
- 双方必须按 `controller`、`controlled` 固定顺序，使用带域分离标签的 exact canonical bytes 和原始签名计算 `key_exchange_transcript_hash`。
- Signal/API 只能转发已签名材料，不得生成、替换或代签临时公钥。
- `account_id` 不直接放入 `signed_key_exchange_payload`，只能通过 `session_context_hash` 覆盖；但 HKDF `info_base` 必须显式包含 `account_id`。实现不得擅自把 `account_id` 加入 payload 或从 HKDF 中删除。

HKDF 输入：

```text
shared_secret
account_id
session_id
controller_device_id
controlled_device_id
permissions_digest
protocol_version
session_expires_at_epoch_millis
selected_transport_path
selected_candidate_pair_id
relay_node_id
key_exchange_transcript_hash
```

HKDF 固定规则：

- HKDF 算法固定为 `HKDF-SHA256`。
- `salt = SHA256(canonical("rctl-hkdf-salt-v1", session_id, controller_device_id, controlled_device_id, permissions_digest, session_expires_at_epoch_millis))`。
- `info_base = canonical("rctl-session-v1", account_id, session_id, controller_device_id, controlled_device_id, permissions_digest, protocol_version, session_expires_at_epoch_millis, selected_transport_path, selected_candidate_pair_id, relay_node_id, key_exchange_transcript_hash)`。
- `canonical` 使用协议规范中的固定字段顺序和长度前缀编码：`field_name_len || field_name || value_len || value`；字符串 UTF-8，整数 big-endian，UUID 使用 16-byte UUID bytes，空值长度为 0。

API 设备签名与 step-up operation_binding_hash 采用上述同一编码规则：

```text
body_hash = SHA256(canonical_request_body)
canonical_api_input = canonical("rctl-api-input-v1", method, path, body_hash, request_id, device_id, account_id, timestamp, api_nonce)
device_signature = Sign(device_private_key, SHA256(canonical_api_input))
operation_binding_hash = SHA256(canonical("rctl-operation-binding-v1", account_id, device_id, purpose, method, path, body_hash, request_id, expires_at_epoch_millis))
```

`rctl-api-input-v1` 与 `rctl-operation-binding-v1` 为不同域分离标签，不能互换。查询参数也须依同样规则进入 canonical，避免请求与验证不一致。该公式是 `docs/spec/20260719170217641_服务端设计.md` 与本文共享的唯一权威输入，T002F/T005A/T024B/T006 等任务必须以此为准。

`canonical_request_body` 和请求目标固定规则：

- `Content-Type: application/json` 的 body 必须按 RFC 8785 JSON Canonicalization Scheme（JCS）编码后计算 SHA-256；显式 `null` 保留，数组顺序保留，重复对象键、非法 UTF-8、NaN 和 Infinity 必须拒绝。
- 非 JSON body 对原始字节计算 SHA-256；无 body 时对空字节串计算 SHA-256。
- `method` 转为 ASCII 大写。`path` 字段实际承载规范化 request target：RFC 3986 path 移除 dot segment、百分号编码使用大写十六进制，查询参数按编码后的键和值升序排列；重复键按值升序保留，不得使用 `+` 代替空格。
- 客户端、API、step-up 验证器和测试向量必须使用同一 canonical 实现，不能分别手写 JSON 排序或 URL 拼接。
- 每个输出项单独 expand：`HKDF-Expand(prk, info_base || output_label, output_len)`。
- `shared_secret` 只作为 HKDF-Extract 的 IKM，不得直接拼入 `info_base`。
- 任一 HKDF 输入字段变化都必须重新派生全部会话密钥。

HKDF 输出标签：

```text
controller_to_controlled_key
controller_to_controlled_nonce_prefix
controlled_to_controller_key
controlled_to_controller_nonce_prefix
key_confirmation_controller_to_controlled
key_confirmation_controlled_to_controller
```

输出长度固定为：

- 两个方向的业务密钥各 32 bytes，用于 `ChaCha20-Poly1305`。
- 两个方向的 nonce prefix 各 4 bytes，与 2-byte big-endian `channel_id` 和 6-byte big-endian `sequence` 拼成 12-byte AEAD nonce；同一方向同一 `channel_id` 使用独立 sequence 空间，达到 `2^48 - 1` 前必须 rekey。
- 两个方向的 key confirmation key 各 32 bytes。
- `confirm_mac` 固定使用 `HMAC-SHA256`，输出完整 32 bytes，不允许截断。

方向映射：

- 主控端发送视频控制、输入、剪贴板和文件请求时，使用 `controller_to_controlled_key` 和 `controller_to_controlled_nonce_prefix`。
- 被控端发送视频帧、剪贴板响应、文件响应和状态上报时，使用 `controlled_to_controller_key` 和 `controlled_to_controller_nonce_prefix`。
- 接收方必须按相反方向选择 receive key。
- `sequence` 作用域为 `direction + channel_id`，同一方向同一通道内单调递增。
- 两个方向的 key 和 nonce prefix 必须不同；实现测试必须断言方向标签不同会派生出不同 key。

密钥确认：

```text
confirm_mac = HMAC(key_confirmation_<direction>, canonical("rctl-key-confirm-v1", session_id, device_id, role, key_exchange_transcript_hash, timestamp))
```

规则：

- 主控端使用 `key_confirmation_controller_to_controlled` 生成发送给被控端的 `confirm_mac`。
- 被控端使用 `key_confirmation_controlled_to_controller` 生成发送给主控端的 `confirm_mac`。
- 验证方不得信任消息体中的隐式方向，必须由 `role` 推导方向：`controller` 固定对应 `controller_to_controlled`，`controlled` 固定对应 `controlled_to_controller`。
- `device_id` 必须等于该 `role` 在会话上下文中的设备 ID。
- `timestamp` 必须在短窗口内，且同一 `role + key_exchange_transcript_hash + timestamp + confirm_mac` 不得重复接受。
- 任一方验证失败必须关闭本次安全会话，写入 `key_exchange_failed` 会话事件。
- 双方都验证成功前，不得投递输入、剪贴板、文件分片或视频帧。

必须绑定：

- 账号 ID。
- 会话 ID。
- 双方设备 ID。
- 权限位。
- 协议版本。
- 会话过期时间。
- 最终传输路径。
- 候选对或 Relay 节点。
- 完整密钥交换 transcript。

路径切换和重协商：

- `selected_transport_path`、`selected_candidate_pair_id` 或 `relay_node_id` 任一变化，都必须进入 `Reconnecting -> EstablishingSecureSession` 并重新执行 signed key exchange。
- 同一 `selected_candidate_pair_id` 内的短断恢复可以在链路心跳丢失后 30 秒窗口内复用原会话密钥，但必须恢复每个通道最后确认的 sequence。
- 从 P2P 切到 Relay、从 Relay 切回 P2P、Relay 节点重分配、候选对变化，都不得复用旧应用层会话密钥。
- 远程重启进入 `accepted/executing/device_offline/resume_ready/resumed` 任一状态、收到有效 `reboot_resume_hint`、系统重启、被控端服务重启超过短断窗口或旧会话关闭后，都不得复用旧应用层会话密钥；远程重启 10 分钟恢复窗口只允许使用 `reboot_resume_token` 创建新安全会话。
- 新密钥确认前不得投递视频帧、输入、剪贴板或文件分片。

应用层加密包：

```text
aad = magic || protocol_version || kind || flags || channel_id || session_id || sequence || payload_len || permissions_digest || direction
nonce = session_nonce_prefix(4 bytes) || channel_id_u16_be(2 bytes) || sequence_u48_be(6 bytes)
ciphertext = AEAD_Encrypt(send_key, nonce, aad, plaintext_payload)
```

规则：

- `session_nonce_prefix` 由 HKDF 派生，不能复用长期设备密钥材料。
- 二进制头里的 `payload_len` 表示 `ciphertext || auth_tag` 的总长度，不表示 plaintext 长度。
- plaintext 长度只允许放在业务 payload 元数据中，不能用于外层帧切分。
- AAD 必须绑定完整二进制消息头语义字段，防止中间层篡改 `kind`、`flags` 或长度后造成误解析。
- `direction` 只能是 `controller_to_controlled` 或 `controlled_to_controller`。
- 同一 `send_key` 下 `direction + channel_id + sequence` 组合不得重复。
- 单通道 sequence 达到 `2^48 - 1` 前必须重新协商会话密钥。
- 收到大于 `2^48 - 1` 的业务消息 sequence 必须视为协议错误。
- 接收端必须先校验 AEAD，再解析业务 payload。
- Relay 只能按外层 `session_id`、通道和长度转发密文，不解析业务 payload。

## 6. 重放保护

每条应用层加密消息必须包含：

- `session_id`
- `sequence`
- `channel_id`
- `timestamp` 或单调计数

规则：

- `sequence` 按 `direction + channel_id` 单调递增。
- 接收方拒绝重复 sequence。
- 接收方拒绝明显过旧消息。
- 30 秒断线重连窗口内可以延续原会话，但必须恢复每个通道最后确认的 sequence；窗口起算点为最后一次成功接收已认证业务帧或心跳的时间。
- 超过重连窗口或权限变化后必须重新协商会话密钥，旧 sequence 和旧密钥立即失效。

## 7. 密钥生命周期

设备长期密钥：

- 设备初始化时生成。
- 用户解绑设备时作废。
- 设备重置时重新生成。

会话临时密钥：

- 每个会话独立。
- 会话结束后立即销毁。
- 断线重连可在短窗口内恢复，超过窗口必须重新协商。

无人值守凭据：

- 不得等同于设备私钥。
- 必须可单独撤销。
- 修改或关闭无人值守后，旧凭据立即失效。
- 首版必须通过 `opaque_ristretto255_sha512_v1` 证明流程使用，不得把密码或等价长期密钥发给服务端；更换 proof scheme 必须先更新协议、认证、服务端、客户端和测试文档。

## 8. 日志禁止项

禁止记录：

- 设备私钥。
- 会话密钥。
- 验证码明文。
- TOTP code。
- 恢复码明文。
- step-up token 明文。
- 无人值守密码明文。
- 无人值守证明中的可重放长期密钥。
- 剪贴板内容。
- 文件内容。
- 输入文本、按键内容和 IME 组合内容。
- release private key。
- reboot resume token 明文。
- recording encryption key。
- 完整 Authorization header。

允许记录：

- 设备 ID。
- 会话 ID。
- 错误码。
- 连接路径。
- Relay 节点 ID。
- 延迟、丢包、码率等指标。

## 9. 必须测试

- 设备签名错误时拒绝上线。
- nonce 重放时拒绝上线。
- Signal 替换任一方 `ephemeral_public_key` 时密钥交换必须失败。
- HKDF transcript 中账号、权限、传输路径或 Relay 节点被篡改时必须失败。
- 链路切换未重新 signed key exchange 时业务数据必须拒绝。
- 验证码和无人值守凭据明文不得出现在请求、信令或日志中。
- 临时验证码和无人值守 `proof_scheme` 不是 `opaque_ristretto255_sha512_v1` 时必须拒绝。
- 无人值守 proof 跨 session 重放时必须失败。
- 会话权限被修改后旧密钥不能继续使用。
- `permissions_digest` 漏掉 `privacy_screen` 或 `block_local_input` 时必须作为协议不兼容失败。
- 未完成 step-up 时不得执行替换设备公钥、设备重绑定或设备密钥恢复、无人值守开启/轮换、关闭 `require_prompt`、授予或本地允许隐私屏、授予或本地允许本地输入保护、请求远程重启、发布客户端更新、撤销发布制品或修改企业区域驻留策略。
- 权限 digest 变化后，旧 step-up 不得继续用于远程重启等高风险动作；必须重新验证并写 `step_up_revalidated` 或重新完成 challenge。
- Relay 只能转发密文。
- Relay token 的 `permissions_digest`、`relay_token_epoch`、TTL 或短期授权状态不匹配时必须拒绝转发。
- WebSocket `client_capabilities_hash` 被篡改、未被设备签名覆盖、缺少 `rctl-client-capabilities-v1` 域分离标签，或 `hello_ok` 回显 hash 与 `hello_response` 不一致时必须拒绝上线。
- WebSocket 版本 Header 缺失、格式非法、无交集或 `client_supported_protocol_versions_hash` 与 Header 不一致时必须拒绝上线。
- signed key exchange 缺少 `rctl-signed-key-exchange-v1` 域分离标签或 transcript canonical bytes 不一致时必须失败。
- 未签名或 hash 不匹配的客户端更新必须拒绝。
- 日志扫描不包含敏感明文。
- 被控端断开后旧会话密钥不能继续投递输入。
- 远程重启后旧会话密钥不能继续投递任何业务消息。
- Relay/API/Signal 不能通过会话录制获取业务明文。
- 输入日志不得包含文本、按键内容或 IME 组合内容。
