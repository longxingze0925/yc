# 数据库设计

## 1. 数据存储边界

PostgreSQL 保存持久数据：

- 账号
- 账号登录态
- 账号 MFA、恢复码和风险验证
- 反诈举报、风险事件和处置
- 设备
- 设备策略
- 条件访问和设备访问规则
- 策略评估结果
- 组织和设备组策略
- 验证码摘要
- 无人值守凭据
- 会话
- 连接候选和候选对
- 会话事件
- 远程重启请求
- Relay 节点
- Relay 会话统计
- 文件传输记录
- 审计日志
- 组织、成员、角色和设备组
- 客户端发布渠道、制品和更新检查
- M8/V2 区域策略和数据驻留配置
- M8/V2 会话录制策略和录制元数据

Redis 保存短期状态：

- 在线设备
- WebSocket 连接映射
- MFA 和风险验证 challenge
- 反诈限流和冷却状态
- 验证码限流
- 会话临时状态
- 远程重启恢复 token 状态
- Relay 节点实时负载

对象存储保存大对象：

- 客户端升级包
- SBOM
- 日志归档
- QA 证据
- M8 可选文件传输临时缓存
- M8/V2 录制密文和 QA 证据，必须按对应区域和留存策略保存

V1 Core 基础文件传输内容默认走应用层端到端加密远控数据通道，不经服务端对象存储。对象存储中的文件传输临时缓存只作为离线传输、断点续传或 M8 企业增强的可选能力；启用前必须新增并冻结对象元数据、权限、区域驻留和留存策略。

关键字段：

- `email`
- `display_name`
- `password_hash`
- `status`
- `created_at_epoch_millis`
- `updated_at_epoch_millis`

规则：

- `updated_at_epoch_millis` 同时作为账号安全版本使用；密码、MFA 和账号状态安全事务必须单调推进它，login challenge 只接受创建时冻结且 finish 时仍严格相等的版本快照。

## 4. account_sessions

用途：

- 保存 refresh token hash。
- 支持退出登录、修改密码撤销登录态和设备级登录管理。

关键字段：

- `account_session_id`
- `account_id`
- `refresh_token_hash`
- `mfa_verified`
- `device_label`
- `ip_address`
- `user_agent`
- `expires_at_epoch_millis`
- `revoked_at_epoch_millis`
- `revoked_reason`
- `created_at_epoch_millis`
- `updated_at_epoch_millis`

规则：

- refresh token 明文不得落库。
- `mfa_verified` 必须是非空布尔值，并由创建 session 的登录事务显式写入：本次登录直接完成 TOTP/recovery code 或命中当前有效 trusted-device 时为 true；无 MFA 且未命中有效 trust 时为 false。它是会话认证强度快照，不是账号当前 MFA 开关，也不能替代高风险 step-up。
- 退出登录只撤销当前 `account_session_id`。
- 修改密码、启用 MFA、禁用 MFA、账号锁定必须撤销账号下全部未过期 session；撤销与安全状态变化、active trust 撤销和审计处于同一事务。
- `revoked_reason` 首版固定集合为 `logout | password_changed | mfa_enabled | mfa_disabled | account_locked | device_unbound | refresh_replay`；未撤销时必须为空，已撤销时必须非空，Schema Freeze 必须加 CHECK。
- 每次 refresh 和 API 鉴权都必须查询本表的撤销状态，不能只验证 token 签名。
- refresh 轮换必须按账号锁顺序在同一事务内消费旧 session、插入替代 session 并写审计；替代行的 `mfa_verified` 必须从旧 session 权威行读取并原样复制，不得根据账号当前 MFA 状态、Redis/内存缓存、请求参数或默认值重新计算。服务重启和 Repository 重建不得造成认证语义降级或提升；不得先提交旧 token 消费、再用独立事务补插入新 session。这样修改密码或 MFA 状态撤销与 refresh 并发时，不能在撤销提交后复活登录态。

## 4A. api_idempotency_keys

用途：

- 保存关键 API 的幂等结果，避免客户端重试造成重复会话、重复关闭、重复事件或重复审计。

关键字段：

- `idempotency_key`
- `account_id`
- `device_id`
- `method`
- `path`
- `body_hash`
- `request_id`
- `resource_type`
- `resource_id`
- `response_status`
- `response_body_hash`
- `expires_at_epoch_millis`
- `created_at_epoch_millis`

规则：

- 唯一键必须至少覆盖 `account_id`、`device_id`、`method`、`path`、`idempotency_key`。
- 重复请求的 `body_hash` 必须一致；同一幂等键携带不同 `body_hash` 必须拒绝并写安全日志。
- `POST /v1/sessions`、`accept/reject/cancel/close` 和文件传输元数据写入必须使用该模型或等价事务内幂等表。
- Redis 可以作为短期加速缓存，PostgreSQL 是关键幂等结果的权威存储。

- `account_mfa_factors.status` 首版固定集合为 `active`、`disabled`。
- `account_risk_challenges.purpose` 首版固定集合为 `login_mfa`、`new_controller_device`、`trusted_device_change`、`password_change`、`mfa_factor_change`、`recovery_code_rotate`、`device_key_rotation`、`unattended_secret_change`、`require_prompt_relax`、`allow_privacy_screen`、`allow_block_local_input`、`allow_remote_reboot`、`remote_reboot`、`access_policy_change`、`client_release_change`、`region_policy_change`。
- `account_risk_challenges.risk_level` 首版固定集合为 `low`、`medium`、`high`。
- `account_risk_challenges.status` 首版固定集合为 `issued`、`verified`、`failed`、`consumed`、`expired`、`cancelled`。
- `account_risk_challenges.expires_at_epoch_millis` 首版最大窗口为创建后 5 分钟；`attempts_remaining` 初始值最大为 5。
- PostgreSQL `account_risk_challenges` 是 challenge 状态、尝试次数和终态的唯一事实源；Redis 不能单独决定 `verified/consumed/failed/expired/cancelled`。
- `purpose = login_mfa` 且 `login_device_state = pending_enrollment` 时，`device_id` 必须为 NULL，真实拟注册设备 ID 必须写入非空 `login_device_id`；`login_device_id` 不建立 `devices` 外键。`login_device_state = registered` 时，`device_id` 与 `login_device_id` 必须都非空且严格相等。`operation_binding_hash` 必须保存本次 `login_challenge_binding_hash`；`login_*` 字段必须结构化保存设备状态、拟注册或已注册公钥、公钥 fingerprint/ID/version、双 nonce、登录请求 binding、IP/User-Agent hash、可选 trusted-device、协议版本和初始尝试上限。Redis payload 丢失后只能从这些 PostgreSQL 字段重建，不得接受 finish 自报公钥或上下文；包含低熵 TOTP/recovery code 的 finish body hash 不得落库。
- 新增设备唯一授权路径为 `/v1/auth/login` 两段式 challenge 加 enrollment grant。`purpose = new_controller_device` 保留在固定枚举中仅用于兼容既有记录和审计语义；V1 通用 `/v1/auth/risk-challenge` 不得为未知 `device_id` 创建该 purpose 的行。未知设备必须写为 `purpose = login_mfa`、`login_device_state = pending_enrollment`、`device_id IS NULL`，并由 `login_device_id` 保存真实拟注册 ID；不得新增通用未知设备字段、借用 login 字段实现通用 step-up 或取消 `device_id -> devices` 外键。
- `trusted_controller_devices.trust_level` 首版固定集合为 `standard`、`high_risk_step_up_required`。
- `trusted_controller_devices.status` 首版固定集合为 `active | expired | revoked`；最长有效期 30 天，到期后必须重新完成设备签名和风险验证。
- `trusted_controller_devices.trust_proof_type` 首版固定集合为 `device_signature_and_mfa | device_signature_and_recovery_code`，不得只凭账号 token 建立信任。
- `trusted_controller_devices.controller_device_id` 必须通过非空复合外键引用同账号 `devices(device_id, account_id)`；未注册设备不得先插入信任记录。
- `device_signature_and_mfa` 的 trust 最长 30 天；`device_signature_and_recovery_code` 的 trust 默认 24 小时且 `trust_level = high_risk_step_up_required`。普通登录、access 使用和 refresh 只更新 `last_used_at_epoch_millis`，不得延长到期时间。
- grant secret 只保存 SHA-256 hash 并常量时间比较；grant TTL 默认和最大均为 5 分钟，`device_public_key_fingerprint/login_challenge_binding_hash` 固定 32 bytes，`grant_secret_hash` 唯一。
- `device_enrollment_grants.login_challenge_id` 必须引用 `account_risk_challenges(risk_challenge_id)`，`issued_account_session_id` 必须引用 `account_sessions(account_session_id)`；`device_id` 在注册前不建立 `devices` 外键，必须通过 grant binding 和注册事务保证一致，注册成功后由 `devices` 记录接管归属事实。
- `mfa_recovery_code_deliveries.account_session_id/factor_id` 必须分别引用 `account_sessions/account_mfa_factors`，已撤销 session 仍需保留精确幂等 ciphertext 重放所需的引用与保留期。
- `device_enrollment_grants.establish_trust = true` 时 `trust_proof_type/trust_level` 必须非空且属于冻结枚举，并由 Schema CHECK 强制 `device_signature_and_mfa -> standard`、`device_signature_and_recovery_code -> high_risk_step_up_required`；false 时两列必须为空。账号未启用 MFA 时 grant 固定 false。
- 未消费 grant 的 `registration_request_binding_hash/registered_public_key_id/registered_trusted_device_id` 必须全部为空；消费后必须保存稳定业务请求 binding 和首次生成的 `public_key_id`，`registered_trusted_device_id` 当且仅当 `establish_trust = true` 时非空。`registered_public_key_id` 是幂等结果 snapshot，不建立到当前 `devices.public_key_id` 的外键，避免阻断后续密钥轮换；`registered_trusted_device_id` 必须通过账号和设备复合外键绑定首次创建的 trust。
- 注册业务 binding 固定绑定账号、签发 account session、grant ID、设备 ID、规范化设备资料、能力、公钥 fingerprint 和协议版本；明确排除 grant secret、API nonce、签名时间戳、request ID、服务端随机 `public_key_id/trusted_device_id` 和创建时间，使响应丢失后的新 nonce 重试可返回首次结果。
- 首次注册必须在同一事务锁定并消费 grant、插入 `devices`、写注册和 grant 审计，并按 grant 决策可选插入 trusted-device；Repository 在锁定 grant 后必须再次用拟注册公钥验证原始 `rctl-api-input-v1` 签名。任一步失败全部回滚。已消费 grant 只有业务 binding 完全相同且当前设备仍使用该注册公钥时可返回首次结果，不同设备、公钥或业务字段返回冲突。
- `mfa_recovery_code_deliveries` 的 ephemeral public key 固定 32 bytes、nonce 固定 12 bytes，ciphertext 最长保留 24 小时；确认保存后可清理 ciphertext，hash 和审计按各自保留周期处理。
- 高风险操作 step-up 结果必须绑定账号、设备、操作目的和短有效期。
- 除上述 `login_mfa` 特例外，`operation_binding_hash` 必须绑定 `account_id`、`device_id`、`purpose`、请求方法、路径、body hash、request_id 和过期时间；高风险 API 验证 step-up 时必须重新计算并匹配。
- step-up challenge 成功后必须一次性消费；`consumed_at_epoch_millis` 写入后不得再次用于新的高风险操作。

## 7. verification_codes

用途：

- 保存临时验证码 `opaque_ristretto255_sha512_v1` verifier、挑战和重试次数。

关键字段：

- `code_id`
- `device_id`
- `code_verifier_record`
- `code_verifier_salt`
- `proof_scheme`
- `active_challenge_id`
- `active_session_id`
- `server_nonce`
- `challenge_status`
- `challenge_expires_at_epoch_millis`
- `expires_at_epoch_millis`
- `attempts_remaining`
- `consumed_at_epoch_millis`
- `created_at_epoch_millis`

规则：

- 不保存验证码明文。
- 不保存可直接离线重放的短码 hash。
- `proof_scheme` 首版只能是 `opaque_ristretto255_sha512_v1`。
- `challenge_status` 首版固定集合为 `active | consumed | expired | replaced`；`failed` 请记入 `session_events`。

- `attempts_remaining` 首版初始值不超过 5；Schema Freeze 必须加 CHECK，consumed/expired/replaced 后不重置。
- 有过期时间。
- 有重试次数。
- 每次 challenge 必须绑定 `active_session_id`、`code_id`、`server_nonce`、过期时间和尝试次数。
- 同一验证码只保留一个 active challenge；重新签发 challenge 时，旧 `active_challenge_id/server_nonce` 必须标记失效。
- 短码 OPAQUE proof 成功、验证码过期、尝试次数耗尽或 pending session 关闭后，challenge 必须标记为 consumed/expired。
- 使用后写入 `consumed_at_epoch_millis`。
- PostgreSQL 的 `verification_codes` 只保存 OPAQUE registration finish 后的 verifier、当前 active challenge 摘要和最终消费状态，是重启恢复和审计依据。
- OPAQUE registration server state 只保存在 Redis 短期 key，不能落入长期表。
- Redis `verification:challenge:{session_id}:{code_id}` 保存短期 proof 校验状态、OPAQUE server state、nonce 重放缓存和尝试计数，是在线校验的快速状态。
- Redis 过期、proof 成功或 pending session 关闭时，服务端必须同步更新 PostgreSQL 的 `challenge_status`、`attempts_remaining` 和 `consumed_at_epoch_millis`。

## 9. sessions

用途：

- 保存远控会话主记录。

关键字段：

- `session_id`
- `controller_account_id`
- `controller_device_id`
- `controlled_device_id`
- `status`
- `permissions`
- `permissions_digest`
- `permissions_digest_last_changed_at_epoch_millis`
- `policy_evaluation_id`
- `relay_token_epoch`
- `session_expires_at_epoch_millis`
- `transport_path`
- `selected_candidate_pair_id`
- `relay_node_id`
- `started_at_epoch_millis`
- `ended_at_epoch_millis`

规则：

- `permissions` 使用 JSONB，便于后续扩权限位。
- `permissions_digest` 保存 canonical 权限模型的 SHA-256，必须与 signed key exchange 和 HKDF 使用的值一致。
- `permissions_digest_last_changed_at_epoch_millis` 记录当前 digest 最近一次变化时间；远程重启等高风险动作校验 step-up 时必须确认 step-up 完成时间不早于该时间。
- `policy_evaluation_id` 必须引用 `policy_evaluations.policy_evaluation_id`，记录创建或最近一次重算有效权限时的策略评估结果，用于审计、远程重启 hash 和排障。
- `relay_token_epoch` 是 Relay token 撤销版本，创建会话时从 1 开始；会话关闭、权限变化、`allow_relay` 变为 false、策略关闭会话或 Relay 节点被禁用影响当前会话时必须递增。
- `session_expires_at_epoch_millis` 必须参与 `session_context_hash`、`signed_key_exchange_payload` 和 HKDF 输入。
- `transport_path` 记录最终选用路径。
- `selected_candidate_pair_id` 必须对应 `connection_candidate_pairs.candidate_pair_id`。
- Relay 路径必须记录 `relay_node_id`。
- 会话状态变化必须同步写 `session_events`；`status = closed` 只表示未被拒绝的终态，拒绝走 `status = rejected` 独立终态。
- `status` 首版固定集合为 `pending_code_verification`、`pending_unattended_verification`、`code_verified`、`unattended_verified`、`waiting_approval`、`accepted`、`connected`、`degraded`、`reconnecting`、`cancelled`、`closed`、`rejected`、`failed`。
- `被控端拒绝` 映射到 `status = rejected` + `event_type = invite_rejected` + 审计 `session_rejected`；不再复用 `closed` 表示拒绝。
- `主控端取消` 映射到 `status = cancelled` + `event_type = cancelled` + 审计 `session_cancelled`。
- `主控端断开、被控端断开、超时或策略关闭` 映射到 `status = closed` + `event_type = closed` + 审计 `session_ended`。
- `code_verified` 只表示临时验证码 proof 已通过，仍必须等待被控端确认；不得直接进入候选交换、Relay 分配、signed key exchange 或业务传输。
- `unattended_verified` 表示无人值守 proof 已通过且无需被控端当次确认，可以进入建链；如策略要求提示，必须转入 `waiting_approval`。
- `waiting_approval` 表示账号内设备确认或 prompt-required 无人值守会话正在等待被控端确认；进入该状态后仍不得候选交换、Relay 分配、signed key exchange 或业务传输。
- proof 失败、验证码过期、无人值守 challenge 过期或被控端拒绝时，pending session 必须进入对应终态并写 `session_events`，具体按下方映射执行。

状态到事件映射：

| 触发 | `sessions.status` | `session_events.event_type` | 审计动作 |
| --- | --- | --- | --- |
| 创建临时验证码会话 | `pending_code_verification` | `invite_created` | `session_invited` |
| 创建无人值守会话 | `pending_unattended_verification` | `invite_created` | `session_invited` |
| 创建账号确认会话 | `waiting_approval` | `invite_created` | `session_invited` |
| 临时验证码 proof 成功 | `code_verified` | `code_verified` | `verification_code_consumed` |
| 无人值守 proof 成功且无需确认 | `unattended_verified` | `unattended_verified` | `unattended_auth_succeeded` |
| 无人值守 proof 成功但需要确认 | `waiting_approval` | `waiting_approval` | `unattended_auth_succeeded` |
| 被控端接受 | `accepted` | `invite_accepted` | `session_accepted` |
| 被控端拒绝 | `rejected` | `invite_rejected` | `session_rejected` |
| 主控端取消 | `cancelled` | `cancelled` | `session_cancelled` |
| 连接成功 | `connected` | `connected` | `session_connected` |
| 链路降级 | `degraded` | `degraded` | `session_degraded` |
| 重连中 | `reconnecting` | `reconnecting` | `session_reconnecting` |
| 主控端断开、被控端断开、超时或策略关闭 | `closed` | `closed` | `session_ended` |
| proof 失败、验证码过期、challenge 过期或不可恢复建链失败 | `failed` | `failed` | `session_failed` |
| signed key exchange 失败 | `failed` | `key_exchange_failed` | `key_exchange_failed` |

权限 canonical 模型：

```text
remote_desktop
input_control
clipboard
file_transfer
unattended
privacy_screen
block_local_input
require_prompt
allow_relay
```

规则：

- 所有权限字段都是 boolean。
- 服务端计算 digest 前必须先物化全部字段，不允许缺字段参与计算。
- 安全缺省：`remote_desktop/input_control/clipboard/file_transfer/unattended/privacy_screen/block_local_input/allow_relay` 缺省为 `false`；`require_prompt` 缺省为 `true`。
- canonical 字段顺序以上方 9 项为唯一权威；编码规则与协议设计的确定性长度前缀编码一致：`field_name_len || field_name || value_len || value`。
- boolean 编码为 `value_len = 1 || bool_u8`，`true = 1`，`false = 0`。
- `permissions_digest = SHA256(canonical_permissions)`。
- 数据库可以继续保存 `permissions` JSONB 方便扩展，但服务端写入和更新时必须同步计算并保存 `permissions_digest`。
- 会话权限变化必须生成新 `permissions_digest`，旧应用层会话密钥立即失效。
- 会话权限变化后，已完成的高风险 step-up 不得自动继续适用于新的 `permissions_digest`；需要继续执行远程重启等高风险动作时必须重新验证或写入 `step_up_revalidated` 审计。

- `auto_resume_consumed_at_epoch_millis`

- `expires_at_epoch_millis`

- `accepted_at_epoch_millis`
- `executed_at_epoch_millis`
- `cancelled_at_epoch_millis`
- `failure_reason`

规则：

- `allow_remote_reboot` 是独立高风险策略字段，不加入 V1 的 9 项 `permissions_digest`。
- 远程重启必须要求高风险 step-up、账号 token、主控设备签名和有效会话。
- `api_request_hash` 必须保存协议文档定义的 canonical hash；`api_request_hash_status`、`mode`、`reason_hash`、`allow_remote_reboot`、`allow_remote_reboot_last_changed_at_epoch_millis`、`step_up_*`、`idempotency_key_hash`、`policy_evaluation_id`、`policy_evaluated_at_epoch_millis`、`permissions_digest`、`permissions_digest_last_changed_at_epoch_millis`、`created_at_epoch_millis` 和 `expires_at_epoch_millis` 是 hash 输入快照，创建后不可修改。
- `api_request_hash_status` 是数据库列名，对应协议 canonical 输入字段 `request_status`；二者必须保存同一值，固定枚举为 `pending | accepted`，不得另建第二套语义。T002E Schema Freeze 必须加 CHECK 约束。
- `mode` 固定枚举为 `normal | safe_mode_reserved`；`safe_mode_reserved` 首版只保留，不实现。T002E Schema Freeze 必须加 CHECK 约束。
- 远程重启请求必须校验 step-up 未过期，且 `step_up_verified_at_epoch_millis >= max(permissions_digest_last_changed_at_epoch_millis, allow_remote_reboot_last_changed_at_epoch_millis, policy_evaluated_at_epoch_millis)`；权限 digest、远程重启允许项或策略评估在 step-up 后变化时必须重新 step-up 或重新验证后再创建请求。
- `status` 是当前请求状态，状态流转不得重算或覆盖 `api_request_hash`；被控端执行前必须确认当前 `status` 仍处于 `pending/accepted` 范围。
- API 和数据库不得保存 reason 自由文本；只保存 `reason_hash`，被控端用 E2EE 业务消息中的 reason 重新计算 hash。
- `auto_resume_consent` 取值为 `none | once_by_controlled_user`，默认 `none`，只能由被控端本地用户确认后经被控设备签名上报。
- `consent_local_user_principal_hash` 只保存本地用户主体 hash 或平台不可逆标识 hash，不保存用户名、邮箱、真实姓名或系统账号明文。
- `consent_revoked_by_actor_type` 固定为 `controlled_device | account | system`；`consent_revoked_reason` 固定为 `controlled_user_revoked | unattended_disabled | device_unbound | mfa_reset | policy_changed | token_invalidated`。撤销只能由被控端签名、本账号高风险操作或系统策略触发，必须写 `remote_reboot_auto_resume_consent_revoked` 审计。
- `local_consent_token_hash` 只能由被控端本地生成并经设备签名上报；明文 token 不得离开被控端本地安全存储。
- `auto_resume_consumed_at_epoch_millis` 非空后不得再次自动恢复。
- `reboot_resume_token` 格式固定为 `base64url(reboot_resume_token_id) "." base64url(reboot_resume_token_secret)`；数据库保存 `reboot_resume_token_id` 和 `reboot_resume_token_secret_hash = SHA256(canonical("rctl-reboot-resume-token-secret-v1", reboot_resume_token_secret))`，不得保存 secret 明文。
- `reboot_resume_token_id` 只作为随机不可枚举查找 ID，不是授权凭据；`reboot_resume_token_secret_hash` 必须常量时间比较。
- `reboot_resume_token_consumed_at_epoch_millis` 只在成功恢复后写入；过期、取消或恢复失败必须写入 `reboot_resume_token_invalidated_at_epoch_millis` 和固定 `reboot_resume_token_invalidation_reason`。二者任一非空后，`/resume` 必须拒绝。
- `reboot_resume_token_invalidation_reason` 固定枚举为 `expired | cancelled | resume_failed | policy_changed | permissions_changed | device_key_revoked | manual_revoked`；Schema Freeze 必须加 CHECK 约束，不得写自由文本。
- 原账号、主控设备、被控设备、旧会话、`reboot_request_id`、`permissions_digest`、过期时间、token 消费时间和 token 失效状态必须保存为独立不可变绑定字段并逐项校验；恢复 token 只能换取恢复意图或新的 unattended challenge，不能替代无人值守 proof、被控端确认或新会话密钥交换。
- 临时协助自动恢复一次还必须校验被控端设备签名的 `local_consent_proof_hash`，该 proof 绑定 `local_consent_token_hash`、`reboot_request_id`、被控设备、服务端 challenge 和时间戳；主控端不得持有或提交 `local_consent_token`。
- 重启后恢复必须创建新会话，旧会话密钥不得复用。
- `status` 首版固定集合为 `pending`、`accepted`、`cancelled`、`executing`、`device_offline`、`resume_ready`、`resumed`、`failed`、`expired`；`shown_to_user` 和 `device_online` 只作为 `reboot_state.state` 瞬时状态和审计事件，不进入权威状态列。T002E Schema Freeze 必须加 CHECK 约束。
- `remote_reboot_requests.status = executing / device_offline / expired` 不对应任何 `session_events.event_type`；这些状态只写审计事件 `remote_reboot_started` / `remote_reboot_device_offline` / `remote_reboot_expired`，不进入会话事件表。
- `远程重启状态到审计事件映射`：`accepted -> remote_reboot_accepted`；`cancelled -> remote_reboot_cancelled`；`executing -> remote_reboot_started`；`device_offline -> remote_reboot_device_offline`；`resume_ready -> remote_reboot_resume_ready`；`resumed -> remote_reboot_resumed`；`failed -> remote_reboot_failed`；`expired -> remote_reboot_expired`；`pending` 只对应 `remote_reboot_requested`。
- `remote_reboot_requests.policy_evaluation_id` 必须强 FK 到 `policy_evaluations.policy_evaluation_id`；不得写入不存在的策略评估 ID。
- `reboot_resume_token_id` 必须有唯一索引，`policy_evaluation_id` 必须有普通索引，远程重启历史查询必须至少有 `(controller_account_id, controller_device_id, controlled_device_id, created_at_epoch_millis)` 复合索引。

用途：

- 保存会话建链期间双方上报或分配的候选链路。

规则：

- `candidate_id` 使用协议文档定义的确定性算法生成。

- `role` 只能是 `controller` 或 `controlled`。

- `role` 首版固定集合为 `controller | controlled`；`kind` 首版固定集合为 `lan_direct | udp_p2p | quic_relay | tls_443_relay`；`source` 首版固定集合为 `udp_observed | local_interface | relay_allocated | static_config`。Schema Freeze 必须加 CHECK。

- `actor_type = device` 时 `actor_account_id` 和 `actor_device_id` 必填，`actor_service` 必须为空。
- `actor_role` 首版固定集合为 `controller`、`controlled`、`none`；会话、文件传输、连接状态、远程重启等会话内设备动作必须填 `controller`/`controlled`，设备注册、设备状态变更等非会话设备动作或 `actor_type = service/system/anonymous` 时必须填 `none`。Schema Freeze 必须加 CHECK 约束。
- `actor_service` 首版固定集合为 `api_server`、`signal_server`、`relay_server`、`release_checker`、`scheduler`；`actor_type = service` 时必须填，其他 actor_type 必须为空。Schema Freeze 必须加 CHECK 约束。
- `actor_type = service` 时 `actor_service` 必填，`actor_account_id`、`actor_device_id` 和 `actor_role` 必须为空。
- `actor_type = system` 时 `actor_account_id`、`actor_device_id`、`actor_role` 和 `actor_service` 必须为空。
- 每条实际撤销的 `account_session` 必须有且仅有一条 `account_session_revoked` 对象审计，每条实际撤销的 active trusted-device 必须有且仅有一条 `trusted_device_revoked` 对象审计；`metadata` 至少保存对应 session/trusted-device ID 和 `revoked_reason`。安全状态、challenge 消费、撤销和对象/顶层审计必须在同一事务中全成全败。logout 同样必须原子写入 session 撤销、对象审计和 `logout` 顶层审计。
- 权限和策略变更必须记录 old/new policy 摘要、old/new `permissions_digest`、操作者和目标资源。
- 删除账号或设备时不得清空审计归因；必须保留不可变 ID 和必要 snapshot 字段。
- 物理迁移中外键删除策略优先使用 `RESTRICT/NO ACTION`，确需允许删除时也必须保留 snapshot。

## 17. 企业组织、策略和设备组

首版实际建表：

- `organizations`
- `organization_devices`
- `organization_members`
- `roles`
- `role_permissions`
- `organization_policies`
- `device_groups`
- `device_group_members`
- `device_group_policies`

基础字段：

- 所有表必须包含稳定 ID、状态、创建时间和更新时间。
- `organization_devices` 必须绑定 `organization_id`、`device_id`、设备组织角色或归属类型。
- `organization_members` 必须绑定 `organization_id`、`account_id` 和 `role_id`。
- `device_groups` 必须绑定 `organization_id`。
- `device_group_members` 必须绑定 `device_group_id` 和同一组织内的 `device_id`。
- `roles` 第一版内置 `owner`、`admin`、`member`、`viewer`。
- `roles` 必须明确作用域：系统内置角色使用 `scope = system`，组织自定义角色使用 `scope = organization` 并绑定 `organization_id`。
- `role_permissions` 必须绑定 `role_id`、会话能力字段、`can_bypass_prompt`、`allow_remote_reboot`、后台管理权限字段和 `updated_at_epoch_millis`。
- `organization_policies` 必须绑定 `organization_id`、`priority`、权限字段、`updated_by_account_id` 和 `updated_at_epoch_millis`。
- `device_group_policies` 必须绑定 `device_group_id`、`priority`、权限字段、`updated_by_account_id` 和 `updated_at_epoch_millis`。

策略字段：

- `allow_remote_desktop`
- `allow_input_control`
- `allow_clipboard`
- `allow_file_transfer`
- `allow_unattended`
- `allow_privacy_screen`
- `allow_block_local_input`
- `require_prompt`
- `allow_relay`
- `allow_remote_reboot`

规则：

- 管理后台可以后置，但数据模型必须允许后续按组织、角色和设备组扩展策略。
- 首版个人用户可以自动归属个人默认组织。
- 管理员覆盖策略的存储位置是 `organization_policies` 和 `device_group_policies`。
- `allow_*` 能力字段在 `organization_policies` 和 `device_group_policies` 中必须支持三态：`inherit`、`allow`、`deny`；不得用非空 boolean 表示所有含义。
- `require_prompt` 不能套用 `allow/deny` 语义，必须使用三态：`inherit`、`require`、`no_prompt`；`require` 是更严格策略，`no_prompt` 只表示本层不强制当次确认。
- `role_permissions` 对能力字段使用 boolean；能力字段为 `false` 表示该角色拒绝对应能力，等价于参与求交集时的 deny。
- `role_permissions.can_bypass_prompt = false` 表示该角色不能免确认，最终 `require_prompt` 必须为 `true`；`true` 也只能在设备本地和组织/设备组策略都未要求确认时让最终 `require_prompt = false`。
- `allow_remote_reboot` 是独立高风险动作策略字段，不加入 9 项 `permissions_digest`；组织、设备组和角色可以拒绝该动作。
- 最终策略计算规则是拒绝优先和确认优先：任一组织、设备组策略为能力 `deny`，或角色能力为 `false` 时，设备本地策略不能重新开启；任一层 `require_prompt = require` 或角色 `can_bypass_prompt = false` 时，最终必须要求被控端确认。
- `allow` 只表示该层不阻断能力，不能越过设备本地关闭项或更高层 `deny`。
- `require_prompt = no_prompt` 不能越过设备本地 `require_prompt = true`、更高优先级 `require` 或角色 `can_bypass_prompt = false`。
- 多条策略同时命中时先按 `priority` 和创建时间得到本层结果，再参与全局求交；能力字段同优先级冲突时按 `deny` 优先，`require_prompt` 同优先级冲突时按 `require` 优先。
- `roles` 首版用于管理权限和策略修改权限，不得绕过会话权限求交集。
- 角色参与会话权限求交集时，以 `role_permissions` 中的会话能力字段和 `can_bypass_prompt` 为准。

## 17A. 条件访问、隐私保护和客户端发布模型

### 17A.1 access_policies

用途：

- 保存账号、组织、设备组或设备范围的条件访问策略。

关键字段：

- `access_policy_id`
- `scope_type`
- `scope_id`
- `name`
- `priority`
- `status`
- `conditions`
- `effects`
- `created_by_account_id`
- `updated_by_account_id`
- `created_at_epoch_millis`
- `updated_at_epoch_millis`

规则：

- `conditions` 和 `effects` 首版可以使用 JSONB，但服务端必须做 schema 校验。
- `scope_type` 首版固定集合为 `account`、`organization`、`device_group`、`device`。
- `status` 首版固定集合为 `active`、`disabled`、`deleted`。
- 多条策略命中时按优先级和拒绝优先计算。
- `effects` JSONB 内部原子效果首版固定集合为 `deny_session | require_mfa | require_prompt | disable_relay | disable_clipboard | disable_file_transfer | disable_privacy_screen | disable_block_local_input | disable_remote_reboot`；Schema Freeze 必须通过 JSON schema 校验函数和 CHECK 拒绝未知效果。
- `conditions` JSONB 内部原子条件首版固定集合为 `country | ip_range | asn | device_posture | login_mfa | step_up | recent_activity | device_trust | connection_kind | time_window`，Schema Freeze 必须把原子条件集合落 CHECK。
- 条件访问只负责会话前决策，不能绕过设备签名、被控端确认或本地权限开关。

### 17A.2 policy_evaluations

用途：

- 保存条件访问、反诈与会话准入合成后的权威策略评估结果。
- 为会话、远程重启和审计提供不可变引用，避免只依赖异步审计日志追溯权限来源。

关键字段：

- `policy_evaluation_id`
- `account_id`
- `controller_device_id`
- `controlled_device_id`
- `session_id`
- `request_type`
- `access_decision`
- `anti_abuse_decision`
- `session_access_decision`
- `effective_permissions`
- `permissions_digest`
- `matched_policy_ids`
- `abuse_actions`
- `risk_challenge_id`
- `cooldown_until_epoch_millis`
- `user_warnings`
- `metadata`
- `created_at_epoch_millis`

规则：

- `policy_evaluation_id` 由 api-server 生成，是策略评估结果的权威落点。
- 记录创建后不可修改；策略、权限、反诈输入、step-up 状态或请求类型变化时必须生成新的 `policy_evaluation_id`。
- `effective_permissions` 必须是已物化后的 9 项会话权限，`permissions_digest` 必须按协议 canonical 权限顺序计算。
- `request_type = session_create` 且会创建会话记录时，api-server 必须先预分配 `session_id`，再把同一 ID 写入 `policy_evaluations` 和 `sessions`。如果策略在创建会话前拒绝，`session_id` 可以为空，但必须写入审计和裁剪后的请求摘要。
- `sessions.policy_evaluation_id`、`remote_reboot_requests.policy_evaluation_id` 和 `audit_logs.action = access_policy_evaluated` 必须引用同一评估 ID。
- `access_policy_evaluated` 审计不能替代本表，只能作为事件索引和查询入口。
- `metadata` 只能保存裁剪后的策略输入摘要、版本和错误码，不得保存验证码、MFA code、无人值守凭据、剪贴板内容、文件内容、输入文本或远控画面。
- `access_decision` 首版固定集合为 `allow | deny | require_mfa | require_prompt`。
- `anti_abuse_decision` 首版固定集合为 `allow | warn_user | cooldown | deny_session`。
- `session_access_decision` 首版固定集合为 `allow | warn_user | require_prompt | require_mfa | cooldown | deny_session`。
- 拒绝原因、警告和审计原因分别进入裁剪后的 `deny_reason`、`user_warnings` 和 `metadata`，不得编码进枚举值；Schema Freeze 必须为三列分别加 CHECK。

### 17A.3 access_policy_assignments

用途：

- 保存条件访问策略和目标对象的绑定关系。

关键字段：

- `assignment_id`
- `access_policy_id`
- `target_type`
- `target_id`
- `status`
- `created_by_account_id`
- `disabled_at_epoch_millis`
- `deleted_at_epoch_millis`
- `created_at_epoch_millis`

规则：

- `target_type` 首版固定集合为 `account`、`organization`、`role`、`device_group`、`device`。
- `status` 首版固定集合为 `active`、`disabled`、`deleted`。
- `DELETE` 语义必须是软删除或禁用，不得默认物理删除。
- 被删除或禁用的 assignment 不得参与新会话评估；已用于会话、策略评估或审计的 assignment 关系必须可追溯，物理删除只能在确认审计和策略历史不需要继续引用后执行。

### 17A.4 device_access_rules

用途：

- 保存被控设备的访问 allow/deny/trusted 规则，支撑个人黑名单和设备级访问控制。

关键字段：

- `device_access_rule_id`
- `controlled_device_id`
- `controller_account_id`
- `controller_device_id`
- `rule_type`
- `reason`
- `created_by_account_id`

规则：

- `rule_type` 首版固定集合为 `allow`、`deny`、`trusted`。
- 黑名单 `deny` 优先，不能被普通 allow 策略覆盖。
- 过期规则不参与新会话评估，但历史审计必须可追溯。

### 17A.5 device_local_security_settings

用途：

- 保存被控端本地对隐私屏和本地输入保护的允许状态和能力探测结果。

关键字段：

- `device_id`
- `allow_privacy_screen`
- `allow_block_local_input`
- `local_escape_hint_enabled`
- `privacy_screen_supported`
- `block_local_input_supported`
- `last_capability_probe_at_epoch_millis`

规则：

- 本表是本地允许状态的事实源。

- `allow_privacy_screen` 或 `allow_block_local_input` 从 false 改 true 时必须先完成高风险 step-up，并写入 `last_allow_step_up_*`；从 true 改 false 不需要 step-up，但必须写审计。

- `device_id`
- `platform`
- `arch`
- `current_version`
- `channel`
- `event_type`
- `result`
- `artifact_id`
- `manifest_signature_valid`
- `artifact_hash_valid`
- `platform_signature_valid`
- `failure_reason`
- `checked_at_epoch_millis`
- `downloaded_at_epoch_millis`
- `verified_at_epoch_millis`
- `failed_at_epoch_millis`
- `created_at_epoch_millis`

## 18. Redis Key 设计

在线设备：

```text
online:device:{device_id}
```

账号设备列表缓存：

```text
account:{account_id}:online_devices
```

WebSocket 连接映射：

```text
signal:conn:{device_id}
```

UDP observe 结果：

```text
observe:result:{observe_result_id}
```

该 key 保存 `session_id`、`device_id`、`role`、`local_socket_nonce`、`observed_endpoint`、`source`、`expires_at_epoch_millis` 和 `observe_result_binding_hash`，只用于 `candidate_token` 签发校验，首版最大有效期不超过 30 秒。

Relay 会话授权状态：

```text
relay:session:{session_id}:authorization
```

该 key 保存 `status`、`allow_relay`、`permissions_digest`、`relay_token_epoch`、当前允许的 `relay_node_id` 集合、`session_expires_at_epoch_millis`、双方 `device_id/role`、双方设备签名公钥或 `device_public_key_id/key_version`、设备密钥撤销状态和 `updated_at_epoch_millis`。Relay 接受 `relay_open` 前必须读取并校验该 key 或等价服务端 introspection 结果；缓存缺失、过期、公钥版本不匹配或设备密钥已撤销时必须拒绝。会话关闭、权限变化、策略关闭、`allow_relay = false`、设备密钥撤销或 Relay 节点禁用时必须更新或撤销该 key。

API 幂等缓存：

```text
idempotency:{account_id}:{device_id}:{method}:{path}:{idempotency_key}
```

该 key 只缓存短期响应摘要；关键幂等结果仍以 PostgreSQL `api_idempotency_keys` 为准。

MFA challenge：

```text
mfa:challenge:v2:{risk_challenge_id}
```

该 key 保存 MFA/risk challenge payload 缓存、尝试租约、nonce、限流和短 TTL 加速状态。PostgreSQL `account_risk_challenges` 是尝试次数和终态事实源；Redis 缺失、重启或 finalize 失败不得使已消费 challenge 重新可用。部署新登录契约时必须清理旧 namespace，旧 payload 不得被新代码接受。

反诈限流和冷却：

```text
abuse:rate:{scope}:{subject_id}:{bucket}
abuse:cooldown:{subject_type}:{subject_id}:{reason}
```

这些 key 保存账号、设备、IP/ASN、验证码、无人值守 proof、会话创建和 Relay token 失败的短期计数或冷却状态。Redis 只作为短期执行状态，最终处置和审计必须写 PostgreSQL。

验证码限流：

```text
verify:attempts:{device_id}
```

验证码 challenge：

```text
verification:challenge:{session_id}:{code_id}
```

该 key 保存 proof 校验状态、OPAQUE server state、nonce 重放缓存、尝试计数和过期时间。

验证码 registration：

```text
verification:registration:{device_id}:{registration_id}
```

该 key 保存 OPAQUE registration server state、`server_nonce`、`client_nonce`、过期时间、最大尝试次数和重放缓存；registration finish、过期或取消后必须清理。

无人值守 challenge：

```text
unattended:challenge:{session_id}
```

该 key 保存 proof 校验状态、OPAQUE server state、nonce 重放缓存、尝试计数和过期时间。

无人值守 registration：

```text
unattended:registration:{device_id}:{registration_id}
```

该 key 保存 OPAQUE registration server state、`server_nonce`、`client_nonce`、目标 `unattended_secret_id/version`、过期时间和重放缓存；registration finish、过期或取消后必须清理。

会话临时状态：

```text
session:{session_id}:state
```

远程重启恢复：

```text
reboot:resume:{reboot_resume_token_id}
```

该 key 保存短期恢复状态、`reboot_request_id`、`reboot_resume_token_secret_hash`、`local_consent_token_hash`、`resume_challenge_nonce`、原主控设备、被控设备、过期时间、`reboot_resume_token_consumed_at_epoch_millis`、`reboot_resume_token_invalidated_at_epoch_millis`、`reboot_resume_token_invalidation_reason` 和使用状态；首版最大有效期固定为 10 分钟。PostgreSQL `remote_reboot_requests` 行是 token 消费和失效事实源，Redis 只作为短期缓存、防重放和恢复加速；Redis 缺失、过期或与 PostgreSQL 不一致时，必须回读 PostgreSQL 并按事实源拒绝或重建缓存，不得用 Redis 状态替代 PostgreSQL 校验。`reboot_resume_token_secret` 和 `local_consent_token` 明文不得落库或写日志。

Relay 实时负载：

```text
relay:{relay_node_id}:load
```

## 20. 数据保留

首版默认保留策略：

- 会话记录：保留 180 天。
- 会话事件：保留 180 天。
- 审计日志：保留 365 天。
- MFA/risk challenge：过期后 30 天可清理，审计日志按审计保留周期保存。
- 设备注册 grant：过期或消费后 30 天可清理，消费审计按审计保留周期保存。
- 恢复码 delivery ciphertext：确认保存后可清理，未确认最长保留 24 小时；恢复码 hash 和审计按各自保留周期保存。
- 反诈风险事件：保留 180 天；处置动作和举报按审计保留周期保存。
- 验证码记录：过期后 7 天可清理。
- 远程重启请求：保留 180 天；`reboot_resume_token_id` 和 `reboot_resume_token_secret_hash` 过期后可清理。
- M8 可选文件传输临时缓存：完成或失败后 24 小时清理；V1 Core 默认无服务端文件内容缓存。
- 客户端更新检查记录：保留 180 天。
- 客户端发布制品元数据和撤销记录：至少保留 365 天，企业版可按合规要求延长。
- M8/V2 会话录制密文、QA 证据和区域数据按组织或测试证据留存策略保存。

规则：

- V1 Core 默认保留策略可以按部署配置缩短；延长、跨区域归档或产品化留存策略管理必须先更新数据驻留、审计和测试文档。

企业版允许管理员配置保留周期。
