# 登录设备身份与受信任主控设备契约

## 状态

`accepted`

- 接受日期：2026-07-22
- 负责角色：Agent-Blueprint-AccountIdentity
- 用户已接受本 ADR 全部决策，并确认 `0001_initial_schema.sql` 未进入任何共享开发库、测试库或生产库。
- 本 ADR 的契约必须同步到账号 MFA、认证、服务端、数据库、客户端、测试方案、里程碑和 AI 开发任务清单；实现与验收不得继续使用旧登录或设备注册路径。

## 1. 背景与问题

冻结规范要求：

- 客户端先完成账号登录/MFA，再自动注册当前设备。
- 受信任主控设备必须引用已注册设备，不能替代设备长期私钥签名。
- `trusted_controller_devices.controller_device_id` 是指向 `devices(device_id)` 的非空外键。
- 信任证明只能是 `device_signature_and_mfa` 或 `device_signature_and_recovery_code`。
- MFA challenge 必须绑定账号、登录请求、IP、User-Agent、客户端 nonce、服务端 nonce 和过期时间。
- 信任最长 30 天，到期后必须重新完成设备签名和风险验证。

现有实现存在以下契约缺口：

1. 首次登录时设备尚未写入 `devices`，不能先插入 `trusted_controller_devices`。
2. `POST /v1/auth/login` 未携带 `client_nonce` 和设备身份意图；登录 MFA challenge 未保存 `server_nonce`、IP、User-Agent 或原请求绑定。
3. `POST /v1/auth/mfa/verify` 未证明已注册设备私钥持有权。
4. 现有代码只有受信任设备查询和撤销，没有建立、使用和刷新信任的完整路径。
5. 当前 `POST /v1/devices` 只要求任意有效 access token 和请求体中新公钥的自签。攻击者取得 access token 后，可以生成自己的密钥并注册攻击者设备。
6. 当前 TOTP finish 在事务提交恢复码 hash 后只返回一次恢复码明文；响应丢失时，服务端无法再次返回同一批恢复码。
7. 当前启用 MFA 后不撤销既有 `account_sessions`，MFA 启用前签发的 refresh token 仍可刷新出登录态，从而绕过新启用的 MFA。

本 ADR 只解决账号登录、设备身份、设备注册授权、受信任主控设备及其直接会话撤销契约，不扩展远控业务权限。

## 2. 决策摘要

采用以下契约：

1. 登录改为统一的两段式 challenge：`POST /v1/auth/login` 校验密码并签发 challenge，`POST /v1/auth/login/finish` 完成设备私钥证明和可选 MFA 后才签发 token。
2. 已注册设备使用数据库当前有效 Ed25519 公钥完成私钥证明；未注册设备只能用拟注册公钥完成“新密钥持有证明”，该证明本身不建立设备信任。
3. 未注册设备完成密码登录 challenge 和拟注册私钥证明后，服务端签发 PostgreSQL 持久化的、一次性、短 TTL `device_enrollment_grant`；账号已启用 MFA 时还必须完成 MFA。任意 access token 不再具有新增设备权限。
4. 首次注册必须在一个 PostgreSQL 事务中锁定并消费 grant、插入 `devices` 和写审计；只有 grant 已绑定 MFA/recovery 证明时才同时插入 `trusted_controller_devices`。任一步失败则全部回滚。
5. 普通低风险登录只能使用仍有效的既有信任，不得静默延长信任 TTL；只有重新完成设备签名和 MFA/风险验证才能刷新信任。
6. TOTP finish 使用客户端临时 X25519 公钥加密恢复码，服务端只持久化恢复码 hash 和客户端可解密的可重放 ciphertext，不持久化恢复码明文。
7. 启用 MFA、禁用 MFA 和修改密码均在各自成功事务中撤销该账号全部 `account_sessions` 和全部 active trusted devices。当前会话也必须撤销。
8. 修改密码固定为 `PATCH /v1/me/password`：MFA active 时必须以 TOTP 或 recovery code 完成 `password_change` step-up，并独立再校验旧密码；无 MFA 时只有 `password_change` 可使用 password reauthentication，其他高风险操作必须先启用 MFA。成功固定返回 `204 No Content`，不签发替代 token，客户端必须使用新密码重新登录。

## 3. 安全不变量

- access token 只证明账号会话，不授予新增设备的能力。
- 首次设备注册必须同时具备有效账号会话、有效 enrollment grant 和拟注册设备私钥证明；账号已启用 MFA 时还必须具备本次 challenge 的 MFA 证明。
- enrollment grant 不能跨账号、跨设备 ID、跨公钥、跨登录 challenge 或跨协议版本使用。
- 已注册设备登录必须使用 `devices` 中当前未撤销的 `public_key_id/public_key_version/public_key`，不得信任客户端自报公钥。
- 新公钥自签只证明请求方持有该新私钥，不证明它已经属于账号。
- MFA code、恢复码明文、密码和包含低熵 code 的请求 body hash 不得持久化或写日志。
- Redis 缺失或重启不得使 grant 重新可用；grant 的一次性消费事实源必须是 PostgreSQL。
- `trusted_controller_devices` 的非空复合外键保持不变，不允许用 nullable FK、临时 device ID 或延迟约束绕过。
- refresh token 不延长 trusted-device TTL，普通 access/refresh 流程也不能创建或刷新信任。
- 无 MFA 时的 password reauthentication 只是 `password_change` 的最小账号恢复例外，不得用于禁用 MFA、恢复码轮换、设备密钥替换、无人值守凭据变更或任何其他高风险 purpose。

## 4. 推荐登录契约

### 4.1 客户端前置条件

客户端在登录前必须加载或生成本地设备长期 Ed25519 密钥对，并准备：

- `device_id`
- `device_public_key`
- 已知时携带 `public_key_id/public_key_version`
- 32-byte CSPRNG `client_nonce`
- `protocol_version`

私钥不得上传。桌面和 iOS 客户端都执行同一身份流程，iOS 的能力仍固定为 `controller only`。

### 4.2 第一段：创建登录 challenge

`POST /v1/auth/login` 请求增加：

```text
email
password
device_id
device_public_key
public_key_id                 # 新设备为空
public_key_version            # 新设备为 0
client_nonce                  # base64url，无 padding，解码后固定 32 bytes
protocol_version
```

密码正确后，服务端才解析账号下设备状态：

- `registered`：`device_id` 属于该账号，客户端提交的公钥 fingerprint、key ID 和 version 必须与当前未撤销公钥一致。
- `pending_enrollment`：账号下不存在该 `device_id`，记录拟注册公钥 fingerprint。
- `conflict`：设备属于其他账号、已解绑/禁用、公钥版本不匹配或公钥已撤销；返回统一设备身份错误，不签发 challenge 或 token。

`purpose = login_mfa` 的 PostgreSQL 字段映射固定如下：

- `pending_enrollment`：`account_risk_challenges.device_id` 必须为 NULL，避免触发 `devices` 外键；客户端提交的真实拟注册设备 ID 必须完整写入不引用 `devices` 的 `login_device_id`。
- `registered`：`device_id` 与 `login_device_id` 都必须非空且严格相等，并由 `device_id` 的现有外键证明设备已注册。

新增设备的唯一授权路径固定为 `/v1/auth/login` 两段式 challenge 加一次性 enrollment grant。`purpose = new_controller_device` 保留在固定枚举中仅用于兼容既有记录和审计语义；V1 通用 `/v1/auth/risk-challenge` 不得为未知 `device_id` 签发该 purpose 的 challenge。未知设备必须进入 `login_mfa + pending_enrollment`，写入 `device_id = NULL` 并在 `login_device_id` 保存真实拟注册 ID；不得擅自新增字段、借用 login 字段实现通用 step-up 或绕过 `devices` 外键。

密码正确也不直接签发 token。服务端生成 32-byte `server_nonce` 和 challenge，返回：

```text
code = login_challenge_required
account_id
login_challenge_id
login_request_binding_hash
login_challenge_binding_hash
server_nonce
device_state
required_factors
expires_at_epoch_millis
attempts_remaining
```

`account_id` 只在密码已验证后返回，不形成账号枚举接口。challenge 最大有效期 5 分钟、最大 5 次尝试；私有化部署只能缩短。

### 4.3 第二段：完成登录

新增统一端点：

```text
POST /v1/auth/login/finish
```

请求体：

```text
login_challenge_id
login_request_binding_hash
login_challenge_binding_hash
client_nonce
server_nonce
factor                       # trusted device 时为空；否则 totp | recovery_code
code                         # factor 为空时不得出现
protocol_version
```

该请求必须携带现有设备签名 Header：

```text
X-Request-ID
X-Rctl-Device-ID
X-Rctl-Timestamp
X-Rctl-Api-Nonce
X-Rctl-Device-Signature
```

签名继续使用冻结的 `rctl-api-input-v1` canonical。对于 `registered`，服务端只用 `devices` 当前公钥验签；对于 `pending_enrollment`，只用第一段 challenge 已绑定的拟注册公钥验签。

服务端按以下顺序 fail closed：

1. 校验 challenge 存在、类型、状态、TTL 和尝试次数。
2. 校验账号、设备状态、两个 nonce、两个 binding hash、IP、User-Agent 和协议版本完全匹配。
3. 校验 timestamp 窗口及 `api_nonce` 未重放。
4. 校验设备签名。
5. 按 `required_factors` 校验 TOTP 或恢复码；同一 TOTP counter 和恢复码不得复用。
6. 原子消费 challenge。
7. 持久化账号 session；根据设备状态建立/刷新 trust，或签发绑定 `establish_trust` 决策的 enrollment grant。
8. 最后返回 token。

challenge、设备证明或 MFA 任一失败均不得签发 access token、refresh token 或 enrollment grant。

### 4.4 无 MFA 账号

未启用 MFA 的低风险账号在密码校验和拟注册设备私钥证明都成功后，可以取得账号 token 和 `establish_trust = false` 的 enrollment grant。客户端据此自动完成设备注册，保持“登录后自动加入我的设备”的冻结产品语义，但服务端不创建 `trusted_controller_devices` 记录。

账号已启用 MFA 时，新设备必须同时完成 TOTP 或 recovery code，grant 才可设置 `establish_trust = true` 并携带冻结集合中的 `trust_proof_type`。无 MFA 账号后续启用 TOTP 并重新验证当前设备后，才建立该设备的 trusted-device 记录。

这样既不新增弱化的 `device_signature_and_password` trust proof，也不让 access token 泄露直接获得新增设备权限。

## 5. Canonical 与请求绑定

所有 `canonical` 继续使用现有长度前缀编码：字段名和值分别以 4-byte big-endian 长度开头；字符串使用 UTF-8，整数使用 big-endian，hash 使用原始 bytes，空值编码为长度 0。JSON body 使用 RFC 8785 JCS，request target 使用现有 RFC 3986 规范化实现。

### 5.1 派生值

```text
device_public_key_fingerprint = SHA256(raw_ed25519_public_key_32_bytes)

ip_address_hash = SHA256(canonical(
  "rctl-login-ip-v1",
  address_family,
  exact_network_order_address_bytes
))

user_agent_hash = SHA256(canonical(
  "rctl-login-user-agent-v1",
  sanitized_user_agent_utf8
))

required_factors_hash = SHA256(JCS(sorted_unique_required_factors))
```

IP 使用服务端观测到的完整地址，不采用客户端自报值。第一段和 finish 之间 IP 变化时 challenge 失效并重新登录；不使用 `/24`、`/64` 前缀弱化冻结的 IP 绑定要求。User-Agent 缺失时按空字符串处理，最大保留 512 个 UTF-8 字符用于计算，不记录原始值到安全审计 metadata。

### 5.2 登录请求绑定

密码和包含密码的完整 body hash 不得进入持久化 binding。密码已由本次请求在线校验，binding 使用下列非秘密字段：

```text
login_request_binding_hash = SHA256(canonical(
  "rctl-login-request-binding-v1",
  account_id,
  method,                         # POST
  path,                           # /v1/auth/login
  request_id,
  device_id,
  device_state,                   # registered | pending_enrollment
  public_key_id,                  # pending_enrollment 为空
  public_key_version,             # pending_enrollment 为 0
  device_public_key_fingerprint,
  client_nonce,
  protocol_version
))
```

### 5.3 登录 challenge 绑定

```text
login_challenge_binding_hash = SHA256(canonical(
  "rctl-login-challenge-v1",
  login_challenge_id,
  account_id,
  account_updated_at_epoch_millis,  # 账号安全版本快照
  login_request_binding_hash,
  device_id,
  device_state,
  device_public_key_fingerprint,
  client_nonce,
  server_nonce,
  ip_address_hash,
  user_agent_hash,
  risk_decision,                  # allow | require_mfa | deny
  required_factors_hash,
  issued_at_epoch_millis,
  expires_at_epoch_millis,
  attempts_limit
))
```

finish 请求的 JCS body 包含 challenge ID、两个 binding hash、两个 nonce、factor 和 code，因此现有 `rctl-api-input-v1` 设备签名同时绑定 finish 请求及 factor。该请求的 body hash 只允许在内存中计算验签，不得持久化、写审计或日志；否则 6 位 TOTP 的低熵 hash 可被离线枚举。

### 5.4 PostgreSQL 与 Redis 事实源

- PostgreSQL `account_risk_challenges` 是 login MFA 和 step-up challenge 的发行、`required_methods`、尝试次数、验证、消费、过期、取消及审计关联的唯一事实源。`purpose = login_mfa` 时，未注册设备的 `device_id` 列保持 NULL 且真实拟注册 ID 存入 `login_device_id`；已注册设备的两列必须非空且相等。`operation_binding_hash` 必须覆盖本 ADR 的完整登录 challenge binding。
- Redis 只尽力保存 challenge payload 缓存、尝试租约、nonce、限流和短 TTL 加速状态；Redis 缺失、超时、重启或与 PostgreSQL 不一致时都必须回读 PostgreSQL，不能单独决定 `issued/verified/consumed/failed/expired/cancelled` 任一状态。
- `required_methods` 是创建 challenge 时根据已锁定账号/MFA 状态持久化的事务级授权条件，不是客户端建议值或 Redis 派生值。验证事务必须以 PostgreSQL 行中集合为准；集合内的 `totp | recovery_code` 表示允许任选其一完成本次 challenge，不表示两者都要提交。
- 登录第一段读取的 `accounts.updated_at_epoch_millis` 必须作为 `login_account_updated_at_epoch_millis` 快照持久化到 `login_mfa` challenge，并纳入 `login_challenge_binding_hash`。创建和 finish 都必须锁定账号并要求当前版本与快照严格相等；密码、MFA 或账号状态安全事务必须单调推进该版本，因此同毫秒、时钟回拨或并发安全变化都不能使旧 challenge 成功。
- MemoryRepository 与 PostgreSQL 必须执行同一 login finish authority 契约：enrollment grant 的账号、设备、challenge、session、fingerprint、TTL、trust 决策和未消费形状，以及新 trusted-device 的因子、fingerprint、固定 TTL、账号/设备绑定和 active 形状，任一不一致都拒绝；成功审计集合的 ID、账号、时间和唯一性也必须一致校验。
- challenge 创建必须把状态与 `risk_challenge_issued` 审计同事务提交。验证必须在一个 PostgreSQL 事务中锁定权威行，校验状态、binding 和 `required_methods`，消费 TOTP counter 或 recovery code，写尝试次数/状态及成功或失败审计；login finish 还要在同一事务建立 account session 和可选 enrollment grant。任一状态写入或审计写入失败均整体回滚。
- PostgreSQL 提交后 Redis finalize 失败时，不得回滚或重开数据库终态。客户端以相同 challenge、账号、设备、purpose 和 binding 重试验证时，只有 PostgreSQL 状态为 `verified`、当前未过期且 `consumed_at_epoch_millis IS NULL` 才可不再消费因子、不再写成功审计，并以原权威字段确定性重签同语义 step-up token；已 `consumed/failed/expired/cancelled` 或 binding 不同必须返回对应稳定拒绝结果。
- login finish 已提交但 token 响应丢失时，不重放 refresh token 明文；客户端必须重新创建登录 challenge。服务端不得为恢复响应而保存 refresh token、MFA code 或 recovery code 明文。
- logout 必须由仓储在同一事务内完成 session 撤销、`account_session_revoked(reason=logout)` 对象审计和 `logout` 顶层审计；任一审计写入失败，session 撤销必须整体回滚。
- 对 `issued` 且已超过 TTL 的 PostgreSQL 行，权威读取路径和后台清理任务都使用 `issued -> expired` CAS，并只写一次过期审计；Redis key 提前丢失不能跳过该转换。
- 必须加入 PostgreSQL commit 后 Redis 超时、服务重启、并发重试、过期清理和审计恰好一次的故障注入测试。

### 5.5 高风险 step-up 与密码修改

step-up challenge 的 `required_methods` 固定按创建事务中的账号 MFA 状态决定：

- MFA active：所有高风险 purpose 都固定为 `totp | recovery_code` 二选一；`password` 不得被加入 `required_methods`。
- 无 MFA：仅 `purpose = password_change` 可固定为 `password`，作为 password reauthentication；任何其他高风险 purpose 必须返回 `mfa_enrollment_required`，不创建 challenge。

密码修改端点固定为：

```text
PATCH /v1/me/password
{
  "current_password": "...",
  "new_password": "..."
}

204 No Content
```

端点必须同时校验有效 account session、与该 PATCH 的 method/path/body hash/request ID 完整绑定的 `password_change` step-up，以及 `current_password`。MFA active 时，TOTP/recovery step-up 不替代旧密码校验；无 MFA 时，password reauthentication 成功后 PATCH 仍必须再校验 `current_password`。

最终 PostgreSQL 事务必须锁定账号与 challenge，再次确认当前密码 hash 仍等于刚刚验证的旧 hash，并在同一事务内完成：

1. 消费 `password_change` challenge。
2. 写入 `new_password` 的 Argon2id hash。
3. 以 `revoked_reason = password_changed` 撤销该账号全部 active `account_sessions`，包含当前 session。
4. 撤销该账号全部 active `trusted_controller_devices`。
5. 对每条被撤销的 session 写一条 `account_session_revoked`，对每条被撤销的 active trust 写一条 `trusted_device_revoked`，再写入 `password_changed` 顶层审计。

密码 hash、challenge 消费、session/trust 撤销、逐对象审计和顶层审计必须全部提交或全部回滚。成功后不签发新 access token、refresh token 或 step-up token，也不保留当前 session 例外；客户端收到 `204` 后必须清理本地 token 并使用新密码重新登录。

## 6. Device Enrollment Grant

### 6.1 签发条件

以下登录结果可以签发 enrollment grant：

- 未注册设备已完成密码登录 challenge 和拟注册私钥证明；未启用 MFA 时 grant 固定 `establish_trust = false`。
- 未注册设备已完成拟注册私钥证明和 TOTP MFA；grant 可设置 `establish_trust = true`。
- 未注册设备已完成拟注册私钥证明和一次性恢复码验证；grant 可设置 `establish_trust = true`。

已注册设备不签发 enrollment grant，只按当前设备公钥和 trusted-device 状态完成登录。

未注册设备的 login finish 返回 token 时，同时返回一次性：

```text
device_enrollment_grant = base64url(grant_id) "." base64url(grant_secret)
device_enrollment_grant_expires_at_epoch_millis
```

`establish_trust = false` 时，`trust_proof_type` 和 `trust_level` 均以空字段参与 canonical，数据库列必须为 NULL；客户端不得自报或覆盖这三个决策字段。

grant 默认和最大 TTL 均为 5 分钟，部署只能缩短。服务端只保存 `SHA256(grant_secret)`，比较必须常量时间完成，明文 secret 不落库、不进日志和审计。

### 6.2 Grant 绑定

```text
device_enrollment_grant_binding_hash = SHA256(canonical(
  "rctl-device-enrollment-grant-v1",
  grant_id,
  account_id,
  device_id,
  device_public_key_fingerprint,
  login_challenge_id,
  login_challenge_binding_hash,
  establish_trust,
  trust_proof_type,
  trust_level,
  protocol_version,
  issued_at_epoch_millis,
  expires_at_epoch_millis
))
```

### 6.3 首次设备注册事务

`POST /v1/devices` 请求体必须增加 `device_enrollment_grant`。现有账号 token 和新公钥自签仍需校验，但二者不再足以注册设备。

服务端在单个 PostgreSQL 事务中：

1. 以 `SELECT ... FOR UPDATE` 锁定 `device_enrollment_grants` 行。
2. 校验 grant secret hash、未消费、未过期、账号、设备 ID、公钥 fingerprint、challenge binding 和协议版本。
3. 校验 access token 的账号和原登录 session 仍有效。
4. 再次校验 `rctl-api-input-v1` 请求签名确由拟注册私钥生成。
5. 插入 `devices`，固定 `public_key_version = 1`。
6. 将 grant 写为 consumed，并记录 `consumed_at_epoch_millis`。
7. `establish_trust = true` 时插入 `trusted_controller_devices`；为 false 时禁止插入。
8. 写 `device_registered`、`device_enrollment_grant_consumed` 审计；实际建立信任时再写 `trusted_device_added`。
9. 提交事务后才返回成功。

重复提交同一 grant 和完全相同请求只能返回同一注册结果；不同设备 ID、公钥或 body 必须返回冲突。grant 已消费但设备/信任记录缺失视为数据完整性错误，不得补写未经验证的数据。

## 7. 信任建立、使用与刷新

### 7.1 建立

推荐默认值：

| 证明 | trust level | TTL | 行为 |
| --- | --- | --- | --- |
| 设备签名 + TOTP | `standard` | 30 天 | 可降低同设备低风险登录的 MFA 频率 |
| 设备签名 + recovery code | `high_risk_step_up_required` | 24 小时 | 仅降低短期低风险重复登录；必须提示轮换恢复码 |

私有化部署只能缩短 TTL。高风险操作无论 trust level 都必须重新 step-up。

### 7.2 使用

trusted login 必须同时满足：

- account、device、fingerprint 全部匹配。
- device 当前状态可认证，公钥未撤销，key ID/version 未变化。
- trusted row 为 `active` 且当前时间严格小于 `expires_at_epoch_millis`。
- 密码验证、登录风险评估和本次 challenge 私钥证明均成功。
- 密码、MFA 因子、账号状态、设备绑定状态没有触发全局撤销。

命中后只更新 `last_used_at_epoch_millis`，不改变 `expires_at_epoch_millis`。

### 7.3 刷新

- 普通 trusted login、access token 使用和 refresh token 轮换均不得延长信任。
- 到期或用户主动重新验证时，必须重新完成当前设备签名和 TOTP/recovery challenge。
- 刷新不覆盖旧行的创建时间。事务内先把旧 active 行标记为 `revoked`，审计 reason 使用 `refreshed`，再插入新的 trusted row，以满足当前 `expires_at <= created_at + 30 days` 约束并保留历史。
- 公钥轮换、设备解绑、账号锁定、密码变化或 MFA 状态变化立即撤销，不得把旧 fingerprint 的信任迁移到新公钥。

## 8. Account Sessions 与信任撤销矩阵

所有撤销必须与触发安全变化的数据库写入处于同一个 PostgreSQL 事务。`authenticate` 必须继续逐请求校验 `account_sessions`，不能只验证 access token 签名。

每条实际从 active 变为 revoked 的 `account_session` 必须对应一条 `account_session_revoked` 审计；每条实际从 active 变为 revoked 的 trusted-device 必须对应一条 `trusted_device_revoked` 审计。安全状态、challenge 消费、撤销和全部对象审计必须全成全败，不能只提交业务状态或只提交审计。

refresh token 轮换必须先锁定账号，再在同一个 PostgreSQL 事务中消费旧 session、插入替代 session 并写刷新审计。修改密码或 MFA 状态事务一旦取得账号锁并撤销 session，任何先前只读取得的旧 refresh authority 都不得在提交后补插入替代 session；并发轮换只能一个成功。

`account_sessions.mfa_verified` 是登录完成时的认证强度快照，必须以非空布尔值持久化。直接完成 TOTP/recovery code 或命中当前有效 trusted-device 的登录写入 true；无 MFA 且未命中有效 trust 的登录写入 false。refresh 必须从旧 session 权威行读取并原样复制该值，禁止根据账号当前 MFA 状态、Redis/内存缓存、请求参数或服务默认值重新计算；服务重启、缓存丢失和 Repository 重建都不得把旧会话降级为 false 或提升为 true。该快照不能替代高风险操作的独立 step-up。

| 事件 | account_sessions | trusted_controller_devices | 客户端后续行为 |
| --- | --- | --- | --- |
| 启用 TOTP 成功 | 撤销该账号全部 session，包含当前 session | 撤销全部 active trust | 客户端先取得恢复码密文并解密，再重新登录/MFA |
| 禁用任一 MFA 因子 | 撤销该账号全部 session，包含当前 session | 撤销全部 active trust | 重新登录；如仍有因子，按新因子状态验证 |
| 修改密码 | 撤销该账号全部 session，包含当前 session | 撤销全部 active trust | 使用新密码重新登录并重新建立信任 |
| 管理员锁定/禁用账号 | 撤销全部 session | 撤销全部 active trust | 账号恢复后重新登录/MFA |
| 设备解绑或当前公钥撤销 | 可至少撤销绑定该设备的 session；推荐 V1 撤销账号全部 session | 撤销该设备 trust | 重新绑定或账号恢复 |
| 恢复码轮换 | 不自动撤销其他 session | 不自动撤销 TOTP 建立的 trust | 当前高风险操作已由 step-up 保护 |
| 使用单个恢复码登录 | 仅消费该恢复码 | 最多建立 24 小时受限 trust | 提示尽快轮换恢复码 |

启用 MFA 的事务顺序固定为：

1. 验证 TOTP counter 和 enrollment 状态。
2. 插入 active MFA factor。
3. 插入恢复码 hash。
4. 插入恢复码 delivery ciphertext 和幂等结果。
5. 撤销该账号全部 `account_sessions`，包括当前 session。
6. 撤销该账号全部 active trusted devices。
7. 写审计并提交。
8. 返回 ciphertext；客户端解密后重新登录。

因此，MFA 启用前签发的 refresh token 立即失效，旧 access token 也因 session 被撤销而在下一次 `authenticate` 时失效。

禁用 MFA 和修改密码同样先完成 step-up/旧密码校验，再在事务中更新安全状态、撤销全部 session/trust、写审计。不能先返回成功再异步撤销。

## 9. TOTP Finish 恢复码响应丢失

### 9.1 推荐密文交付

客户端在 TOTP start 前生成临时 X25519 密钥对，把私钥保存到平台安全存储直到成功解密恢复码；start 请求提交 `recovery_delivery_public_key`。服务端在 finish 时生成一次性 X25519 临时密钥对并派生交付密钥：

```text
salt = SHA256(canonical(
  "rctl-recovery-delivery-salt-v1",
  account_id,
  account_session_id,
  factor_id,
  delivery_id,
  idempotency_key_hash
))

info = canonical(
  "rctl-recovery-delivery-v1",
  account_id,
  account_session_id,
  factor_id,
  delivery_id,
  client_ephemeral_public_key,
  server_ephemeral_public_key,
  created_at_epoch_millis,
  expires_at_epoch_millis
)

delivery_key = HKDF-SHA256(x25519_shared_secret, salt, info, 32)
```

服务端生成随机 12-byte nonce，使用 ChaCha20-Poly1305 加密 JCS：

```json
{"recovery_codes":["..."]}
```

AAD 使用上述 `info` 的 canonical bytes。明文只在请求内存中存在，生成 hash 和 ciphertext 后立即清零。服务端不得保存临时私钥或恢复码明文。

finish 首次响应和幂等重放响应返回：

```text
delivery_id
server_ephemeral_public_key
nonce
ciphertext
created_at_epoch_millis
expires_at_epoch_millis
recovery_code_count
```

### 9.2 幂等与当前会话已撤销

`POST /v1/me/mfa/totp/finish` 必须要求 `Idempotency-Key`。同一账号、原 `account_session_id`、factor、delivery public key、finish binding 和幂等键只能生成一次结果。

由于成功事务已经撤销当前 session，该端点需要一个严格受限的“已完成结果重放”分支：

- 先正常验证 access token 签名、token 类型和原始过期时间。
- 即使原 session 已因 `mfa_enabled` 撤销，也只允许查询同一 session、同一幂等键、同一 request binding 的已提交 delivery ciphertext。
- 该分支不得重新校验/消费 TOTP、生成新恢复码、修改数据库或访问其他 API。
- session 因其他原因撤销、token 已自然过期、binding 不一致或 delivery 不存在时必须拒绝。
- 重放窗口不得超过原 access token 过期时间和 delivery TTL 的较小值。

这样即使首个 HTTP 响应丢失，客户端仍可用原 access token 和幂等键取得同一 ciphertext；服务端仍无法解密。客户端成功解密并确认保存后应调用确认端点删除 ciphertext，未确认 ciphertext 最长保留 24 小时并按后台任务清理。

如果重放窗口已经结束，服务端不能恢复原恢复码。用户必须用已绑定 TOTP 重新登录并执行恢复码 rotate；不得把旧 hash 反推为明文。

关键约束：TTL 不超过 5 分钟；未消费时 `consumed_at` 为空；同一 grant 只能消费一次；fingerprint 和 binding hash 固定 32 bytes。`establish_trust = true` 时 `trust_proof_type/trust_level` 必须非空且属于冻结枚举，false 时两列必须为 NULL。

表中只保存客户端可解密 ciphertext，不保存服务端临时私钥或恢复码明文。

`account_sessions` 必须增加非空 `mfa_verified` 和 `revoked_reason`。`mfa_verified` 必须由登录 finish 显式写入、由 refresh 原样继承，不得使用会在恢复路径静默降级的进程内默认值。`revoked_reason` 至少固定：

```text
logout
password_changed
mfa_enabled
mfa_disabled
account_locked

refresh_replay
```

### 10.2 现有表

- 保持 `trusted_controller_devices.controller_device_id` 非空及复合 FK 不变。
- 保持现有 trust level、status 和 proof type 固定集合不变。
- 现有 trusted rows 不自动升级；若 fingerprint 和设备当前公钥一致且未过期可继续使用，否则迁移时撤销。
- 已过期但仍为 `active` 的 trusted rows 先批量标记 `expired`，再启用新唯一写路径。

### 10.3 迁移顺序

1. 先新增表、索引、CHECK、审计枚举、`account_sessions.mfa_verified` 和 `revoked_reason`，不切流量。
2. 部署支持两段式登录、密文 delivery 和 grant 校验的服务端。
3. 更新桌面/iOS 客户端，先加载身份再登录，并支持 finish、grant 和恢复码解密。
4. 强制 `POST /v1/devices` 缺少 grant 时返回 `device_enrollment_grant_required`。
5. 清理旧 Redis login challenge namespace，使用版本化新 key，避免旧 payload 被新代码接受。
6. 删除旧 `/v1/auth/mfa/verify` 的 token 签发路径；迁移期可返回升级错误，但不得继续产生未绑定 token。

用户已确认 `0001` 未进入任何共享环境，本次实现固定重写 `0001`。若迁移落盘前共享状态发生变化，必须停止并重新确认迁移路径，不得自行修改已使用迁移或自动新增 `0002_account_identity_contract.sql`；生产迁移仍需单独确认。

## 11. 验收测试

### 11.1 登录与 challenge

- 密码正确也不在第一段签发 token。
- `client_nonce/server_nonce/request_id/IP/User-Agent/device_id/fingerprint/protocol_version` 任一变化均拒绝 finish。
- nonce 重放、challenge 过期、超过 5 次、并发 finish 只允许一次成功。
- 已注册设备缺少签名、使用新自报公钥、旧 key version、撤销 key 或其他设备签名均拒绝。
- 未注册设备只能由 challenge 绑定的拟注册私钥签名 finish。
- MFA code、密码和低熵 finish body hash 不出现在日志、审计和数据库。

### 11.2 Enrollment grant

- 只有 access token、没有 grant 时 `POST /v1/devices` 拒绝。
- 被盗 access token 配合攻击者新公钥自签仍不能注册设备。
- grant 跨账号、跨 device ID、跨 fingerprint、跨 challenge、过期、已消费或 secret 错误均拒绝。
- grant 与注册请求签名都有效时，`devices`、grant consumed 和注册审计同时提交；`establish_trust = true` 时 trusted row 与 `trusted_device_added` 也必须在同一事务提交。
- 无 MFA grant 必须固定 `establish_trust = false`，即使客户端篡改请求也不能创建 trusted row。
- 在事务每一步注入失败时四类写入全部回滚。
- 并发消费同一 grant 只能有一个成功，重试相同请求返回相同设备，不重复创建 trust。

### 11.3 信任 TTL 与撤销

- TOTP trust 最多 30 天，recovery-code trust 默认 24 小时。
- 普通 trusted login 和 refresh 不延长 `expires_at`，只更新 `last_used_at`。
- 到期、撤销、密码修改、MFA 启用/禁用、公钥轮换、设备解绑后下一次登录重新要求 MFA/风险验证。
- recovery-code trust 不能绕过任何高风险 step-up。

### 11.4 Session 撤销

- 启用 MFA 成功后，账号所有旧 refresh token 立即失败。
- 启用 MFA 成功后，当前及其他旧 access token 因 session authority 检查立即失败。
- 禁用 MFA 和修改密码同样撤销当前及全部其他 session 和 active trust。
- session/trust 撤销事务失败时，MFA/密码状态变化不得部分提交。
- 撤销后仅 TOTP finish 的精确幂等 ciphertext 重放分支可读取既有结果，其他 API 全部拒绝。

### 11.5 Step-up 与密码修改

- MFA active 时创建 `password_change` challenge，`required_methods` 必须精确为 `totp | recovery_code`；完成其一后，`PATCH /v1/me/password` 仍必须校验 `current_password`。
- 无 MFA 时，仅 `password_change` 可得到 `required_methods = password`；其他高风险 purpose 返回 `mfa_enrollment_required` 且 PostgreSQL 不新增 challenge。
- `current_password` 错误、`new_password` 不合规、step-up purpose/binding 不匹配、challenge 已过期或已消费时，密码、session、trust 和成功审计均不得变更。
- `PATCH /v1/me/password` 成功必须返回 `204 No Content` 且响应不含任何替代 token；原 access/refresh token 立即失效，必须使用新密码重新登录。
- PostgreSQL 提交 verified 后在 token 签发或响应前失败时，相同 challenge/binding 重试只在未过期且未消费时确定性重签同语义 token，不重复消费 TOTP/recovery code、不重复写成功审计。
- challenge 发行/状态与审计、因子消费/验证结果与审计、业务操作/challenge 消费与审计分别必须在同一 PostgreSQL 事务内闭合；Redis 故障不能改变结果。

### 11.6 恢复码交付

- 首次 finish 与同幂等键重试返回字节完全相同的 ciphertext。
- 客户端临时私钥可解密，其他私钥、篡改 AAD/nonce/ciphertext 均失败。
- 服务重启后仍可重放 PostgreSQL 中的 ciphertext。
- 服务端数据库、Redis、日志和审计均不含恢复码明文及服务端临时私钥。
- 同幂等键配不同 factor、session、客户端公钥或 binding 返回冲突。
- 原 access token 自然过期或 delivery 到期后不可重放；使用 TOTP step-up rotate 可生成新恢复码。

## 12. 备选方案及拒绝理由

### 12.1 让 trusted device FK 可空，注册后再回填

拒绝。它会产生没有设备权威身份的 trust row，扩大孤儿数据、并发接管和错误授权风险，也违反当前非空 FK 的安全意图。

### 12.2 继续允许 access token + 新公钥自签注册

拒绝。自签只能证明攻击者持有攻击者自己的私钥；被盗 access token 足以把攻击者设备绑定到账号。

### 12.3 使用纯 JWT enrollment grant，不持久化消费状态

拒绝。无法在设备插入事务内形成一次性权威消费，重放和部分提交只能依赖易丢失缓存。

### 12.4 普通 trusted login 自动滑动续期 30 天

拒绝。高频使用设备会永久不再 MFA，实质绕过“到期后重新验证”。普通使用只更新 `last_used_at`。

### 12.5 为无 MFA 首台设备增加 `device_signature_and_password` trust proof

拒绝。无 MFA 账号仍可通过 challenge、拟注册私钥证明和一次性 grant 自动注册设备，但该路径不建立 trusted-device 记录，因此不需要扩大冻结 proof 枚举或把长期信任降级为单因子密码。

### 12.6 服务端保存恢复码明文或用服务端长期密钥加密后重放

拒绝。它违背“恢复码只保存 hash”的边界，并使服务端或长期密钥泄露可恢复全部明文。

### 12.7 响应丢失后自动轮换一批新恢复码

拒绝。客户端无法区分首次提交、重试和轮换，可能反复作废用户已经保存的恢复码；并发请求也更难保持确定性。

### 12.8 启用 MFA 后保留当前或其他既有 session

拒绝。MFA 启用前签发的 refresh token 可以继续获得新 access token，形成明确 MFA 绕过；仅缩短 access token TTL 不能解决该问题。

用户于 2026-07-22 明确确认：

1. 接受两段式登录和 `POST /v1/auth/login/finish`，停止旧 `/v1/auth/mfa/verify` 直接签发 token。
2. 接受无 MFA 账号可自动注册设备但不建立 trusted-device 记录；账号已启用 MFA 时，新设备注册必须完成 TOTP/recovery MFA。
3. 接受 TOTP trust 最长 30 天、recovery-code trust 默认 24 小时且都不滑动续期。
4. 接受新增 PostgreSQL `device_enrollment_grants`、`mfa_recovery_code_deliveries` 及 `account_sessions.revoked_reason`。
5. 确认当前 `0001_initial_schema.sql` 未进入共享环境，账号身份 Schema 修订固定重写 `0001`，不新增 `0002`。
6. 接受启用/禁用 MFA、修改密码都撤销该账号全部 session（含当前）和全部 active trusted devices。
7. 接受 `PATCH /v1/me/password {current_password,new_password} -> 204`、MFA active 与无 MFA 的 step-up 方法分支、成功后不签发替代 token，以及 PostgreSQL 权威 challenge、verified 未过期未消费重试和审计/状态事务闭合契约。
8. 接受 `account_sessions.mfa_verified` 作为非空持久化认证强度快照，refresh 只能原样继承，服务重启或缓存丢失不得改变其语义。
9. 接受 `login_mfa` 的字段条件：`pending_enrollment` 时 `device_id IS NULL` 且真实拟注册 ID 存 `login_device_id`；`registered` 时两者非空且相等。新增设备唯一授权路径为两段式登录加 enrollment grant；`new_controller_device` purpose 仅保留作兼容/审计，V1 通用 risk challenge 不为未知设备签发。

本 ADR 已接受；规范同步不代表实现或迁移已经完成，`T005A` 必须保持 `todo` 直至代码和验收全部通过。

## 14. 影响与回滚

正向影响：

- 首次设备注册从“账号 token 权限”提升为“账号验证 + challenge + 新私钥证明 + 一次性授权”。
- trusted-device FK 与登录先后顺序不再冲突，无 MFA 登录后自动加入“我的设备”的产品语义保持不变。
- 已注册设备每次登录都能证明当前私钥持有权。
- MFA 启用后旧 refresh/access token 立即失效。
- 恢复码响应可确定性重放，而服务端不保留明文。

代价：

- 登录增加一次网络往返。
- 无 MFA 设备可自动注册，但不会获得降低后续 MFA 频率的 trusted-device 状态。
- 新增两张短期安全状态表、客户端密文解密和迁移期版本门禁。

回滚要求：

- 协议版本 1 发布前可回滚客户端和新端点，但不得恢复“任意 access token 可新增设备”的旧路径。
- 已创建的设备、信任和审计记录不得删除；回滚时统一撤销新 grant 和本 ADR 创建的 active trust。
- 已进入共享环境的迁移只能追加反向兼容迁移，不能改写历史。
