# 核心架构决策记录

文档状态：历史决策记录，仅保留背景。当前架构方向必须以 README 文档入口中的 `20260719170217641` 与 `20260719171718533` 系列冻结文档为准。

## ADR-001 平台范围

决策：

```text
被控端：Windows 10/11、Ubuntu Desktop 26.04 LTS
主控端：iOS 16 及以上、Windows 10/11、Ubuntu Desktop 26.04 LTS
```

原因：

- Windows 是最核心被控场景。
- Ubuntu 26.04 LTS 是明确、长期支持的 Linux 基准系统。
- iOS 主控是差异化重点。
- 暂时排除 Android、macOS、Web 被控，避免第一版范围失控。

影响：

- Linux 适配优先围绕 Ubuntu 26.04 LTS，不泛化到所有发行版。
- iOS 只做主控，不承诺被控。

## ADR-002 核心语言选择 Rust

决策：

```text
客户端核心、协议、传输、加密、服务端核心优先使用 Rust。
```

原因：

- 跨平台能力强。
- 适合网络、协议、加密、编解码调度等性能敏感模块。
- 内存安全更适合长期运行的远控软件。
- 可通过 FFI 接入 iOS 原生 UI。

影响：

- 团队需要建立 Rust 工程规范。
- UI、平台采集、编码硬件接口需要通过平台绑定集成。

## ADR-003 桌面 UI 选择 Slint，iOS 使用原生

决策：

```text
Windows/Linux 桌面 UI 使用 Slint。
iOS UI 使用 SwiftUI/UIKit。
```

原因：

- Slint 相比 Electron/Flutter 更轻，和 Rust 集成更直接。
- iOS 对触控、外接键鼠、横竖屏、系统权限要求特殊，原生体验和性能更好。
- 远控画面单独由原生渲染层处理，不依赖普通 UI 框架高频绘制。

影响：

- UI 不能完全一套代码多端复用。
- 需要维护桌面和 iOS 两套交互实现。

## ADR-004 主连接方案为 P2P over QUIC

决策：

```text
优先 P2P over QUIC。
P2P 失败时使用 QUIC Relay。
UDP 受限时使用 TLS 443 Relay。
```

原因：

- P2P 降低延迟和中继成本。
- QUIC 提供低延迟、多路复用、加密、拥塞控制和更好的网络切换能力。
- Relay 保障复杂网络下的连接成功率。
- TLS 443 fallback 保障企业网络和 UDP 被封场景。

影响：

- 需要实现连接竞速、链路切换和 Relay 调度。
- 不能只依赖单一协议或单一路径。

## ADR-005 Ubuntu 优先 Wayland/PipeWire

决策：

```text
Ubuntu 26.04 LTS 优先支持 Wayland/PipeWire，提供 X11 fallback。
```

原因：

- Ubuntu 桌面主流方向是 Wayland。
- Wayland 下屏幕采集和输入控制必须走系统授权路径。
- X11 仍需兼容部分用户环境。

影响：

- Wayland 下不能承诺无授权静默控制。
- 需要在产品中清楚展示权限状态和能力限制。

## ADR-006 视频编码 H.264 优先

决策：

```text
第一版默认 H.264，预留 H.265 和 AV1。
```

原因：

- H.264 在 Windows、Linux、iOS 上兼容性最好。
- iOS 硬解成熟。
- 首版稳定性比极限压缩率更重要。

影响：

- 4K/高帧率/低码率能力后续通过 H.265、AV1 和更强码控演进。
- 必须有软件编码兜底。

## ADR-007 服务端采用 SaaS + 私有化双形态

决策：

```text
服务端同时面向 SaaS 和私有化部署设计。
```

原因：

- 个人和小团队需要开箱即用。
- 企业客户通常需要私有化、审计和权限管控。
- Relay、信令、账号和审计天然适合模块化部署。

影响：

- 服务配置、密钥、节点注册和数据库迁移必须可自动化。
- 第一版用 Docker Compose，后续预留 Kubernetes。
