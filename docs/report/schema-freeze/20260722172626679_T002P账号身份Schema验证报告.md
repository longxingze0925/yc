## 验证证据

1. 在全新空库执行 `infra/migrations/run-0001.sh --apply`，迁移成功。
2. 对迁移结果执行 `infra/migrations/verify-0001.sql`，全部结构断言通过。
3. `make fmt-check`、`make lint`、`make test`、`make check` 全部通过。
4. 最终收紧恢复码 delivery 为账号级幂等认领后，在全新空库再次执行最新 `0001` 和 `verify-0001.sql`，结果为 `schema verification passed`；验证脚本同时断言唯一约束的精确列顺序为 `account_id, idempotency_key_hash`。
5. API 常规测试结果为 `80 passed; 0 failed; 9 ignored`；随后使用上述隔离 PostgreSQL/Redis 实跑全部 ignored 集成测试，结果为 `9 passed; 0 failed`：
   - Redis nonce、challenge、登录锁和在线状态。
   - Redis TOTP 临时密文与跨实例 lease。
   - PostgreSQL 风险 challenge 跨实例一致性。
   - PostgreSQL 登录 finish 使用持久化账号安全快照，旧 challenge 在账号安全变化后拒绝。
   - 设备注册并发单结果。
   - 设备密钥轮换、撤销和身份权限关闭。
   - 完整会话、MFA 密文持久化、恢复码 ciphertext 重启重放，以及同账号同幂等键异绑定的第二实例冲突。
   - 双实例会话图与状态迁移并发一致性。
6. 静态检查确认：
   - 存在 `device_enrollment_grants` 和 `mfa_recovery_code_deliveries`。
   - `account_sessions.mfa_verified` 非空，`revoked_reason` 受冻结枚举约束。
   - `login_device_state` 对 `registered` 与 `pending_enrollment` 使用不同 `device_id/login_device_id` 约束。
   - 登录双 nonce、binding hash、公钥上下文和账号安全快照可从 PostgreSQL 恢复。
   - `mfa_recovery_code_deliveries` 使用 `UNIQUE(account_id, idempotency_key_hash)`；session、factor、finish binding 和客户端交付公钥由服务端继续做常量时间绑定比较。
   - 不存在 `0002_account_identity_contract.sql`。
