# 测试方案

## 1. 测试目标

测试必须证明：

- 核心链路可运行。
- 平台矩阵可连接。
- 权限和安全边界有效。
- 弱网和断线可恢复。
- 后续 AI 开发不会破坏已有能力。

## 2. 测试层级

单元测试：

- 协议编解码。
- 权限策略。
- 状态机。
- 链路选择。
- 反诈风险决策。
- 键盘/IME 输入事件映射。
- 媒体能力协商和质量策略。
- 远程重启状态机。
- 数据模型序列化。

集成测试：

- API Server + PostgreSQL。
- Signal Server + Redis。
- Relay Server 基础转发。
- 客户端核心与服务端协商。

端到端测试：

- Windows 被控 -> Windows 主控。
- Windows 被控 -> Ubuntu 主控。
- Windows 被控 -> iOS 主控。
- Ubuntu 被控 -> Windows 主控。
- Ubuntu 被控 -> Ubuntu 主控。
- Ubuntu 被控 -> iOS 主控。

手工验收：

- 系统权限弹窗。
- 安装和卸载。
- MFA 绑定、恢复码和高风险操作 step-up。
- 反诈提示、举报、拉黑和误报恢复。
- 隐私屏和本地输入保护的本地提示、退出和恢复。
- 远程重启倒计时、取消、系统重启后上线和新会话恢复。
- iOS 手势、虚拟键盘、快捷键面板、外接键盘鼠标、横竖屏切换。
- 媒体质量档位和弱网降级提示。
- Wayland 权限限制提示。

## 3. 平台矩阵

被控端：

- Windows 10。
- Windows 11。
- Ubuntu Desktop 26.04 LTS x86_64 Wayland。
- Ubuntu Desktop 26.04 LTS x86_64 X11。

主控端：

- iOS 16 及以上真机。
- Windows 10。
- Windows 11。
- Ubuntu Desktop 26.04 LTS x86_64 Wayland。
- Ubuntu Desktop 26.04 LTS x86_64 X11。

平台链路定义：

- 箭头固定表示 `被控端 -> 主控端`，iOS 只作为主控端。
- 六条平台链路指 OS 家族链路：Windows 被控 -> Windows 主控、Windows 被控 -> Ubuntu 主控、Windows 被控 -> iOS 主控、Ubuntu 被控 -> Windows 主控、Ubuntu 被控 -> Ubuntu 主控、Ubuntu 被控 -> iOS 主控。
- 发布验收必须展开 Windows 10/11 和 Ubuntu Wayland/X11 变体。
- 每个 OS 家族链路必须至少有一个完整端到端用例。
- Windows 10/11、Ubuntu Wayland/X11 变体必须至少覆盖安装、启动、登录、设备注册、连接、断开和日志检查。

发布真实远控矩阵：

| 被控端变体 | 必测主控端变体 | 每个组合必测项 | 证据目录 |
| --- | --- | --- | --- |
| Windows 10 | Windows 10、Windows 11、Ubuntu Wayland、Ubuntu X11、iOS 真机 | 画面非空、分辨率正确、鼠标/键盘输入可达、断开、资源释放、敏感日志扫描 | `docs/report/os-variant/windows10/**` |
| Windows 11 | Windows 10、Windows 11、Ubuntu Wayland、Ubuntu X11、iOS 真机 | 画面非空、分辨率正确、鼠标/键盘输入可达、断开、资源释放、敏感日志扫描 | `docs/report/os-variant/windows11/**` |
| Ubuntu Wayland | Windows 10、Windows 11、Ubuntu Wayland、Ubuntu X11、iOS 真机 | PipeWire/portal 授权、portal 失效矩阵见第 6 节、画面非空、分辨率正确、鼠标/键盘输入可达、断开、资源释放、敏感日志扫描 | `docs/report/os-variant/ubuntu-wayland/**` |
| Ubuntu X11 | Windows 10、Windows 11、Ubuntu Wayland、Ubuntu X11、iOS 真机 | X11 fallback、画面非空、分辨率正确、鼠标/键盘输入可达、断开、资源释放、敏感日志扫描 | `docs/report/os-variant/ubuntu-x11/**` |

- 上表共 20 个真实远控组合，必须在 M5-M7 完成；任一组合未通过时，必须在发布阻断清单中列明，不得用 OS 家族链路通过替代。
- iOS 真机作为主控端时，每个被控端变体至少覆盖一台 iOS 16 真机；当前主版本真机可用于补充回归和性能基线。

## 4. 网络矩阵

必须覆盖：

- 同局域网。
- 家庭宽带 NAT。
- 手机热点。
- 公司网络。
- UDP 阻断。
- Relay 强制模式。
- TLS 443 fallback。
- 断网 5 秒恢复。
- Wi-Fi 切热点。

交叉验证规则：

- 六条平台链路必须分别验证 LAN Direct over QUIC、UDP P2P over QUIC、QUIC Relay、TLS 443 Relay。
- M4 的 24 组网络矩阵指 6 条 OS 家族链路 x 4 条网络路径；Windows 10/11 和 Ubuntu Wayland/X11 变体展开属于 M5-M7 真实远控验收，不把 M4 扩大为全变体笛卡尔积。
- M4 阶段允许使用 client-core、CLI 或测试桩验证传输建链、消息往返和断线恢复；真实远控画面、输入和 iOS 真机网络栈/FFI 约束验收必须等 M5-M7 完成。
- M4 传输验收的“消息往返”必须是完成 signed key exchange 和 `key_confirm` 后的业务密文往返；未完成应用层端到端加密时，只能标记为传输桩通过，不能标记真实远控链路通过。
- TLS 443 Relay 路径在 T016 尚未完成业务密文往返时不得标记通过；M4 退出必须以 T016 的真实业务密文往返证据为准。
- Windows 10/11 和 Ubuntu Wayland/X11 变体不要求全部网络路径笛卡尔积，但每个变体至少验证 LAN Direct 和一种 Relay 路径。
- Ubuntu Wayland 和 X11 作为被控端时必须分别验证采集、输入、断开后资源释放。

测试用例记录格式：

```text
case_id
被控端 OS / 主控端 OS
网络路径
前置条件
执行步骤或命令
采集指标
通过标准
证据文件
失败原因
```

证据要求：

- 网络路径测试必须记录实际 `transport_path`、`candidate_pair_id`、`relay_node_id`、RTT、丢包和日志片段。
- 画面测试必须保留截图或录屏，证明画面非空且显示器选择正确。
- iOS 外设测试必须记录设备型号、iOS 版本、输入外设类型和横竖屏状态。
- 设备池至少包含 Windows 10/11 被控与主控、Ubuntu Desktop 26.04 LTS Wayland/X11 被控与主控、iOS 主控真机。
- iOS 真机至少覆盖最低支持 iOS 16 和当前主版本各一台。外设测试至少覆盖一种蓝牙键盘和一种蓝牙鼠标或触控板；设备不足时必须记录缺口并阻断 iOS 完整发布验收。
- iOS 真机网络矩阵必须在 `T021` 进入集成验收前补齐；设备未到位时，必须冻结替代用例（iOS 模拟器 + Windows/Ubuntu 主控交叉验证 + iOS 真机设备缺口记录），证据保存到 `docs/report/network-matrix/ios-substitute/**`，并阻断 M6/M7 的 iOS 完整发布验收。
- 每次网络矩阵执行必须记录 OS 版本、客户端 commit、服务端 commit、Relay 节点、网络类型和公网出口。
- 同局域网和家庭 NAT 使用真实路由器环境；手机热点使用真实热点；公司网络如不可用，可以用防火墙规则模拟 UDP 阻断并标记为模拟。
- UDP 阻断必须有明确配置证据，例如防火墙规则、容器网络策略或测试路由器 ACL。
- 弱网和丢包可使用 `tc netem`、路由器限速或系统网络调试工具；命令、参数和恢复命令必须写入证据。
- Relay 强制模式必须通过客户端配置或服务端策略禁用 P2P，并在日志中证明选择了 QUIC Relay 或 TLS 443 Relay。
- 证据统一保存到 `docs/report/network-matrix/{case_id}/`，至少包含 client 日志、server 日志、relay 日志、关键截图或命令输出、指标摘要和结论。
- M4 允许使用 client-core、CLI 或测试桩输出证据；M5-M7 必须补真实画面、输入和功能证据。

## 5. 安全测试

必须验证：

- 未登录不能创建设备。
- `POST /v1/auth/login` 密码正确时也只能返回 `login_challenge_required`，不得签发 access token、refresh token 或 enrollment grant。
- `POST /v1/auth/login/finish` 的 `client_nonce/server_nonce/request_id/IP/User-Agent/device_id/device_public_key_fingerprint/protocol_version` 任一变化必须拒绝；challenge 过期、超过 5 次、nonce 重放或并发 finish 只能有一次成功。删除 Redis login payload 后，已注册和 `pending_enrollment` 必须都能从 PostgreSQL 结构化上下文恢复；恢复不得重置数据库尝试次数、重开已消费 challenge 或接受 finish 自报公钥。
- 真实 PostgreSQL 行必须验证 `login_mfa + pending_enrollment` 写入 `device_id IS NULL` 且 `login_device_id` 精确保留客户端真实拟注册 ID，不触发 `devices` 外键；`login_mfa + registered` 必须写入相等且非空的 `device_id/login_device_id`，不一致组合必须被 CHECK 拒绝。
- `purpose = new_controller_device` 必须保留枚举兼容性，但 V1 通用 `/v1/auth/risk-challenge` 对未知 `device_id` 必须拒绝且 PostgreSQL 不新增 challenge。未知设备必须改走两段式登录，数据库行固定为 `purpose = login_mfa`、`login_device_state = pending_enrollment`、`device_id IS NULL`，并由 `login_device_id` 精确保留拟注册 ID。
- 已注册设备必须使用 `devices` 当前未撤销公钥完成 finish；客户端自报新公钥、旧 key version、已撤销 key 或其他设备签名必须拒绝。未注册设备只能使用第一段绑定的拟注册私钥。
- 只有 access token、没有 `device_enrollment_grant` 时 `POST /v1/devices` 必须拒绝；被盗 access token 配合攻击者新公钥自签仍不能注册设备。
- grant 跨账号、跨 device ID、跨 fingerprint、跨登录 challenge、过期、已消费或 secret 错误必须拒绝；并发消费同一 grant 只能一个成功。
- 有效 grant 注册必须将 `devices`、grant consumed、稳定注册业务 binding、首次 `public_key_id`、注册审计和可选 trusted-device 在同一事务提交；每一步故障注入都必须全部回滚。响应丢失后以新 nonce、时间戳、request ID 和服务端随机候选重试必须返回首次设备/trust 结果，不得重复创建 trust 或审计；业务字段变化必须冲突。
- 无 MFA grant 固定 `establish_trust = false`，客户端篡改 trust 决策字段也不得创建 trusted-device。
- `PATCH /v1/devices/{device_id}` 必须覆盖跨账号 actor、缺设备签名、改名、disable、disabled-only restore、unbind、显式 key revoke 和非法终态恢复；收紧动作必须原子关闭非终态会话、追加 `closed` 事件和 `session_ended` 审计、提升 Relay epoch、撤销 active trust 和关闭被控/无人值守能力，提交后向双方推送同一 `event_id` 的 `session_close_ack`；`unbind/revoke_public_key` 还必须以 `device_unbound` 撤销账号全部 active account session，事务故障不得部分提交。
- 设备 key 轮换必须撤销旧 fingerprint 对应的 active trust、关闭或重新评估全部受影响非终态会话并使旧 Relay epoch 失效；旧 key 不能登录、调用设备 API、重新开 Signal 或 Relay。
- `/ws`、MFA 和 risk challenge API 的 `protocol_version` 无交集、不支持或低于 `client_min_protocol_version` 时必须返回 `unsupported_version`，不得写在线状态或签发 challenge。
- `/ws` 缺少版本 Header、版本 Header 格式非法、`hello_response.client_supported_protocol_versions_hash` 与 Upgrade Header 重算值不一致时必须拒绝上线，不得写在线状态。
- 启用 MFA 后，密码正确但未完成 MFA 不得签发 token。
- access token 首版默认 15 分钟、refresh token 首版默认 30 天；SaaS/V1 Core 或私有化部署放宽该默认值必须被配置校验或发布门禁拒绝。
- MFA/risk challenge 首版最大有效期 5 分钟、最大尝试次数 5 次；过期、超过次数或私有化部署放宽上限必须失败并写审计。
- risk challenge 必须以 PostgreSQL `account_risk_challenges` 为唯一事实源，Redis 只作尽力缓存。删除 Redis key、Redis 超时、服务重启或 Redis/PostgreSQL 状态冲突后，必须从 PostgreSQL 继续，不得重置尝试次数、重开终态或改变 `required_methods`。
- `required_methods` 事务级条件必须覆盖：MFA active 的所有高风险 purpose 只允许 TOTP/recovery code 二选一；无 MFA 时仅 `password_change` 允许 password reauthentication；无 MFA 请求其他高风险 purpose 必须返回 `mfa_enrollment_required` 且 PostgreSQL/Redis 都不得留下 challenge。
- 在 challenge 验证事务已提交 `verified`、但 step-up token 签发/响应或 Redis finalize 失败处注入故障：相同账号/设备/purpose/binding 重试只在未过期且未消费时确定性重签同语义 token，不再消费 TOTP counter/recovery code，不减少尝试次数，不重复写成功审计；已消费、失败、过期、取消或 binding 变化必须稳定拒绝。
- TOTP 错误、过期或重复使用必须拒绝。
- 恢复码只能使用一次。
- TOTP trust 最长 30 天，recovery-code trust 默认 24 小时且必须为 `high_risk_step_up_required`；普通 trusted login、access 使用和 refresh 只能更新 `last_used_at`，不得延长 `expires_at`。
- 启用 MFA、禁用 MFA 和修改密码必须在同一安全状态事务中撤销账号全部 account session（含当前）和全部 active trust；旧 access/refresh token 在下一次鉴权或刷新时必须失败，事务失败不得部分提交。
- refresh 轮换必须覆盖与修改密码、启用 MFA、禁用 MFA 的并发交错：旧 refresh authority 只读完成后安全事务提交撤销，再继续轮换时不得插入替代 session；轮换先提交时后续安全事务必须连同替代 session 一起撤销。
- `account_sessions.mfa_verified` 必须覆盖 false/true 两组真实 PostgreSQL 用例：登录 finish 显式持久化；refresh 前后严格相等；服务重启、Redis 清空和仅从 Repository 恢复后仍保持原值。任何按账号当前 MFA 状态、请求字段或代码默认值把 true 降为 false 或把 false 提升为 true 的实现都必须失败；该字段不得替代高风险 step-up。
- `PATCH /v1/me/password` 只接受 `{current_password,new_password}`；MFA active 时必须先完成 `password_change` TOTP/recovery step-up 并在 PATCH 中再校验 `current_password`，无 MFA 时必须同时通过 `password_change` password reauthentication 和 PATCH 的旧密码再校验。
- 密码修改成功必须返回 `204 No Content`，响应 body 不含 access token、refresh token 或 step-up token；当前与其他 session 均已撤销，客户端只能使用新密码重新登录。
- 密码修改故障注入必须逐步覆盖 challenge 消费、旧 hash 并发校验、新 hash 写入、全 session 撤销、全 active trust 撤销和 `password_changed`/撤销审计；任一步失败时上述状态必须全部回滚，不得出现密码已更换但 session/trust 未撤销或状态已提交但审计缺失。
- challenge 发行与发行审计、验证状态/因子消费与成功或失败审计、高风险操作/challenge 消费与业务审计必须分别同事务提交；审计写入故障必须让对应状态转换失败。
- challenge 取消必须在同一仓储事务提交 `status = cancelled` 和唯一一条 `risk_challenge_failed` 审计，审计固定 `result = failure`、`reason = cancelled`。分别在状态更新、审计插入和 commit 注入故障时，两者必须同时不存在；不得产生 `risk_challenge_cancelled` 等新 audit action，也不得重复写取消审计。
- TOTP finish 首次响应和相同幂等键重试必须返回字节一致的 `delivery_id/server_ephemeral_public_key/nonce/ciphertext/created_at_epoch_millis/expires_at_epoch_millis/recovery_code_count`；服务重启、Redis 缺失或提交后超时仍从 PostgreSQL 返回相同结果，不得生成第二批恢复码。
- 客户端临时 X25519 私钥可以解密恢复码 ciphertext；错误私钥、篡改 AAD/nonce/ciphertext 必须失败，数据库、Redis、日志和审计不得含恢复码明文或服务端临时私钥。
- 新主控设备和高风险操作必须按策略触发 step-up。
- 禁用 MFA、替换设备公钥、设备重绑定或设备密钥恢复、开启或轮换无人值守、关闭 `require_prompt`、授予或本地允许 `privacy_screen`、授予或本地允许 `block_local_input`、请求远程重启必须 step-up。
- 运行时 `privacy_mode_request` 不额外调用服务端 step-up API；测试必须验证未获会话权限时被控端拒绝，且服务端不能明文解析该 E2EE payload。
- 无权限不能发起会话。
- 反诈处置命中 cooldown、deny、suspend 时不能创建可建链会话。
- 被控端举报并拉黑后，同一主控设备再次连接必须被拒绝或要求被控端重新显式确认。
- 验证码、无人值守 proof、会话创建和 Relay token 失败过多必须触发限流。
- 黑名单或条件访问 denylist 命中时不能发起会话。
- 条件访问要求 MFA 时，未完成 step-up 不得创建可建链会话。
- 设备本地关闭能力时，组织或远程策略不能重新开启。
- 验证码错误次数限制。
- 验证码过期。
- 临时验证码注册必须要求目标被控设备签名；只有账号 access token、没有目标设备私钥签名时不得创建验证码。
- 无人值守开启和轮换必须要求目标被控设备签名；远程账号或管理员可以关闭/禁用并写审计，但不能远程开启或轮换。
- 账号内设备确认连接必须先进入 `waiting_approval`，被控端接受前不得交换候选、Relay token 或密钥。
- 被控端拒绝后不能连接；最终会话状态必须为 `rejected`，必须写入 `invite_rejected` 事件和 `session_rejected` 审计动作，双方不得继续交换候选、Relay token 或密钥。
- 临时验证码和无人值守 challenge 不能超过 5 分钟过期和 5 次试验；超限一律拒绝，不允许重置或改变 `attempts_remaining`。
- 主控端取消邀请后，被控端必须收到 `session_cancel_ack`，最终会话状态必须为 `cancelled`，双方不得继续交换候选或密钥。
- 被控端断开后不能自动重连。
- 剪贴板关闭时不能同步。
- 文件传输关闭时不能发送文件。
- 隐私屏关闭时不能启用隐私屏。
- 本地输入保护关闭时不能锁定本地输入。
- 隐私屏和本地输入保护的平台 unsupported 状态不得伪装成功。
- 日志不包含密码、验证码明文、私钥、剪贴板内容。
- 日志不包含 TOTP code、恢复码明文、step-up token、release private key。
- 设备签名错误时不能上线。
- nonce 重放时不能上线。
- refresh token 明文不能落库。
- 无人值守关闭后旧凭据不能连接。
- Relay 不能解密业务明文。
- 未完成应用层端到端加密时，真实远控链路不得通过验收。
- WebSocket 重连必须重新通过账号 token 和设备签名校验。
- WebSocket access token 过期、撤销或与设备签名中的 `account_id` 不一致时必须拒绝上线；客户端必须 refresh 后重新连接。
- WebSocket `client_capabilities_hash` 被篡改或未被设备签名覆盖时必须拒绝上线。
- WebSocket `client_capabilities_hash` 必须使用 `rctl-client-capabilities-v1` 域分离标签；缺失标签、`hello_ok` 回显 hash 与 `hello_response` 不一致、`server_supported_protocol_versions` 与 Upgrade 协商结果不一致时必须拒绝上线或关闭连接。
- Signal 替换任一方 X25519 临时公钥时密钥交换必须失败。
- signed key exchange 必须提供二进制测试向量，覆盖 `signed_key_exchange_canonical_bytes`、原始 64-byte Ed25519 signature、`key_exchange_transcript_hash` 和 HKDF 输出；任一端使用不带域分离标签的 canonical bytes 时必须失败。
- `key_confirm` 必须使用 `rctl-key-confirm-v1` 域分离标签；缺失标签、方向标签错误或重放同一 `role + key_exchange_transcript_hash + timestamp + confirm_mac` 必须失败。
- `key_confirm.timestamp` 超出接收端本地时间前后 30 秒窗口时必须失败。
- `account_id` 必须通过 `session_context_hash` 间接覆盖并显式进入 HKDF；篡改 `account_id` 一个 bit 后，签名校验或 HKDF 派生密钥必须不一致。
- HKDF 绑定字段被篡改时会话密钥验证必须失败。
- Relay token 缺失、过期、跨 session、跨设备、跨节点时必须拒绝转发。
- Relay token 的 `permissions_digest` 不匹配、`relay_token_epoch` 被撤销、TTL 超过上限、会话已关闭或 Relay 节点被禁用时必须拒绝转发；Relay 节点禁用后 2 秒内必须拒绝新 `relay_open`。
- `relay_open_nonce` 重放必须在 token 过期后至少 60 秒内被拒绝。
- observe token、observe result、candidate token、Relay token binding hash 和 `relay_open` 设备签名必须分别验证域分离标签；`relay_open` 签名必须使用 `Sign(device_private_key, SHA256(canonical("rctl-relay-open-v1", relay_open_without_signature)))` 并提供测试向量；跨用途复用 binding hash、签名 payload 或直接签名未 hash 的 canonical bytes 必须失败。
- `relay_open_without_signature` 字段顺序与 `rctl-relay-token-binding-v1` 一致；跨实现调用变更字段顺序、重复签名 `device_signature`、直接签名未 hash 的 canonical bytes、重复使用 binding hash 作为 `relay_open` 输入都必须拒绝。Relay 验证还必须明确拒绝 transport 不匹配、服务端授权缓存缺失/过期、设备公钥 key version 不匹配或设备密钥已撤销的 `relay_open`。
- `connection_candidates.role/kind/source`、`connection_candidate_pairs.status/selected_transport_path`、`relay_nodes.status` 必须落入固定集合；超出集合必须拒绝并写审计。Relay 角色在会话 token 与 `relay_open` 中校验，不属于 `relay_nodes` 表。
- `relay_open.transport` 与 `session_relay_token` payload 或 `relay_allocated` 明文字段不一致时必须拒绝；授权缓存缺失、过期、公钥版本不匹配或设备密钥已撤销时必须拒绝，不得只验证 token 签名就建立转发通道。
- observe token 过期、candidate token 过期或 P2P probe nonce 重放时必须拒绝；candidate token TTL 首版不得超过 60 秒，observe token TTL 首版不得超过 30 秒。
- `allow_relay = false` 时不得分配 Relay token；已有 Relay 尝试必须被拒绝并写审计。
- `source = udp_observed` 的候选缺少有效 `observe_result_id` 或 `observe_result_binding_hash` 时，signal-server 不得签发 `candidate_token`。
- LAN Direct 候选缺少有效 `candidate_token` 时不得通过 P2P 探测。
- LAN Direct `endpoint` 使用 loopback、multicast、broadcast、link-local、documentation/test-net 或公网地址时 signal-server 必须拒绝签发 `candidate_token`。
- 探测方本地判断远端 LAN Direct 地址不在本机可路由局域网接口范围内时必须跳过，远端提交远端作为公网/任意私网地址的 LAN Direct 候选时探测接收端必须拒绝。
- 每个会话每个设备的 LAN Direct 候选数量超过 8 个时 signal-server 必须拒绝超出的候选。探测包必须仅含 session_id/candidate_id/role/candidate_token/candidate_token_binding_hash 和 probe nonce，出现任何业务 payload 时接收端必须丢弃。
- LAN Direct 候选请求缺少 `interface_name_hash/interface_index_hash/local_socket_nonce/timestamp_epoch_millis`、claim hash 不可重算、签名无效、时间偏差超过 30 秒或同一 `device_id + session_id + local_socket_nonce + candidate_id` 重放时，signal-server 不得签发 `candidate_token`。
- LAN Direct 候选的 `endpoint` 为 `unspecified`、loopback、multicast、broadcast、documentation/test-net、link-local、公网地址或低位/非临时 UDP 端口时必须拒绝；每设备每会话超过 8 个 LAN Direct 候选必须拒绝；候选交换和 P2P 探测限速必须生效。
- 探测方必须跳过不在本机可路由局域网接口范围内的远端 LAN Direct 地址；测试必须证明 LAN Direct 不能被用来探测任意私网地址。
- `candidate_id` 必须由候选拥有方、signal-server 和探测方按相同字段集合独立重算；非 Relay 候选 `relay_node_id` 缺失、未按 0 长度空值参与计算或直接信任信令里的 `candidate_id` 时必须失败。
- `candidate_token`、`candidate_token_binding_hash` 和 `expires_at_epoch_millis` 必须作为探测临时附加物处理；落库、写日志或跨会话复用必须失败或被敏感扫描阻断。
- `connection_candidates` 表不得出现完整 `candidate_token`/`candidate_token_binding_hash`/token 过期时间字段；该三项只允许在内存、Redis 短期 key、探测包中持有；敏感扫描命中表则代表迁移与规范不一致。探测调试需提交 P2P probe 包与 signal 发出的 binding hash 一致的正向证例，以及探测包改动任一字段后探测接收端必须拒绝的负例。
- 条件访问和反诈合成结果必须按 `deny_session`（即 `access_decision = deny` 或 `anti_abuse_decision = deny_session`）、`cooldown`、`require_mfa`、`require_prompt`、`warn_user`、`allow` 优先级测试。
- 设备上报 `connection-state` 必须通过账号 token 和设备签名；signal-server 服务上报必须通过服务间 token，且不得伪造设备 actor。
- 客户端不得通过 Signal WebSocket 直接写入 `connected/degraded/reconnecting/failed` 会话状态；Signal 只能推送 API 已持久化后的 `connection_state` 通知。
- 服务端超时或策略关闭产生的 `session_close_ack` 必须使用 `actor_type = system` 或 `actor_type = service`，不得伪造 `actor_device_id`。
- 会话权限被服务端或被控端修改后，旧会话密钥不能继续发送输入、剪贴板或文件传输业务数据。
- 被控端主动断开后，旧 session key 不能继续注入输入事件。
- 远程重启后，旧 session key 不能继续投递任何业务消息。
- 远程重启 `api_request_hash` 字段顺序、step-up、幂等键、策略评估结果或请求状态被篡改时，被控端必须拒绝执行。
- 应用层端到端加密 `reboot_request.reason` 重新计算出的 `reason_hash` 与 API 保存的 `reason_hash` 或 `api_request_hash` 输入快照不一致时，被控端必须拒绝执行。
- 被控端执行远程重启前必须在线调用 `GET /v1/reboot-requests/{reboot_request_id}` 校验 API 权威状态；无法查询、状态非 `pending/accepted`、hash 不一致或过期时必须拒绝执行。
- `api_request_hash_status` / `request_status` 必须限制为 `pending | accepted`；未知枚举必须被数据库 CHECK 或服务端校验拒绝。
- 远程重启当前 `status` 从 `pending` 流转到 `accepted/executing/device_offline/resume_ready/resumed/failed` 时，`api_request_hash_status` 和 `api_request_hash` 输入快照必须保持创建时原值不变。
- `reboot_resume_token` 必须按 `base64url(reboot_resume_token_id) "." base64url(reboot_resume_token_secret)` 解析；token ID 不存在、secret hash 常量时间比较失败、绑定账号/设备/旧会话/`permissions_digest` 不匹配、过期、失效或 `reboot_resume_token_consumed_at_epoch_millis` 非空时必须拒绝，并不得扫描全表查找 token。
- `reboot_resume_token_invalidation_reason` 必须限制为 `expired/cancelled/resume_failed/policy_changed/permissions_changed/device_key_revoked/manual_revoked`，自由文本或未知枚举必须被数据库 CHECK 或服务端校验拒绝。
- 被控端解密 E2EE `reboot_request.reason` 后重新计算 `reason_hash`，与 API 创建时 `api_request_hash` 输入中的 `reason_hash` 不一致时必须拒绝执行，并写安全日志。
- `reboot_request.mode` 必须限制为 `normal | safe_mode_reserved`，`safe_mode_reserved` 首版必须返回 unsupported 或保持不执行；未知枚举必须拒绝。
- 自动恢复一次同意撤销必须写 `consent_revoked_at_epoch_millis`、`consent_revoked_by_actor_type`、`consent_revoked_reason` 和 `remote_reboot_auto_resume_consent_revoked` 审计；撤销后自动恢复必须拒绝。
- `auto_resume_consent = none` 时，即使 `reboot_resume_token` 有效、恢复窗口未过且绑定字段一致，也必须拒绝自动恢复并进入新的被控端确认流程。
- Redis `reboot:resume:*` 只作为短期缓存；Redis 缺失、过期或与 PostgreSQL `remote_reboot_requests` 不一致时，必须以 PostgreSQL 事实源拒绝或重建缓存，不得跳过 token 消费/失效校验。
- `reboot_resume_hint` 必须携带被控设备签名，主控端解密业务消息后必须校验 `controlled_device_signature = Sign(controlled_device_private_key, SHA256(canonical("rctl-reboot-resume-hint-v1", old_session_id, reboot_request_id, controlled_device_id, resume_expires_at_epoch_millis)))`；缺失签名、签名无效、设备不匹配或过期时必须拒绝发起 `/resume`。
- `/resume` 请求体或 query 携带 `reconnect_after_reboot` 时必须拒绝；服务端不得把它解释成跳过授权、被控端确认或无人值守 proof 的信号。
- 链路切换后未重新完成 signed key exchange 时，必须拒绝业务数据。
- 无人值守 proof 跨 session、跨设备、跨挑战或过期重放必须失败。
- 临时验证码和无人值守凭据设置必须走 OPAQUE registration start/finish；跳过 finish、重放 `registration_id`、篡改 registration transcript 或把明文凭据提交给 API 都必须失败。
- 验证码明文、无人值守明文凭据不得出现在 API、Signal、Relay 请求、响应、日志或审计上下文中。
- 临时验证码和无人值守 `proof_scheme` 不是 `opaque_ristretto255_sha512_v1` 时必须拒绝。
- update manifest 签名错误、manifest 过期、artifact hash 不匹配或安装包签名无效时，客户端必须拒绝更新。
- 未知平台或非 `x86_64 | aarch64` 架构的更新检查必须拒绝并写审计；`client_update_checks.platform/arch` 必须落入固定集合，未知值不得写入。
- release private key 不得出现在仓库、构建日志和发布证据包中。
- 反诈日志和审计不得包含远控画面、剪贴板内容、文件内容、输入文本或 IME 组合内容。
- 反诈要求二次提示时，剪贴板开启必须有被控端确认状态和裁剪审计；文件传输 `ack.accepted=true` 必须代表被控端本地显式确认，且 `confirmed_by_device_id` 等于会话被控端设备。
- M8 端点侧录制若启用，必须验证录制加密 key 不落客户端日志、诊断导出或审计 metadata。
- V1 Core 产品功能中不得存在默认开启的生产会话录制；QA 录屏证据必须与生产录制功能区分。

## 6. 功能正向验收

剪贴板：

- 剪贴板开启时，文本必须可从主控端同步到被控端。
- 剪贴板开启时，文本必须可从被控端同步到主控端。
- 剪贴板关闭时，双向都不得同步。
- 日志不得记录剪贴板内容。

文件传输：

- 100MB 文件传输完成后 `sha256` 必须一致。
- 文件传输失败或取消时必须有明确状态。
- 文件传输关闭时不得创建传输任务。
- 文件名、大小、hash 和状态可审计，不记录文件内容。
- V1 只验收单文件双向传输，不验收目录传输和断点续传。
- 被控端文件传输确认弹窗必须显示文件名、大小、`sha256` 短哈希、来源主控账号和设备；拒绝时可选择理由分类并写审计。
- 文件传输请求、确认、拒绝、取消、失败和完成必须分别可审计，确认必须记录被控端设备归因。
- 端侧安全矩阵必须覆盖路径穿越、绝对路径、空文件名、Windows 保留设备名、非法字符、同名文件冲突、覆盖确认、符号链接或硬链接拒绝、接收目录无权限、磁盘空间不足、写入中断、hash 不匹配、取消后临时文件清理和失败后临时文件清理。
- 接收端必须先写同目录临时文件，`sha256` 校验通过后原子落盘；任何失败路径不得留下可误用的目标文件或未清理的大临时文件。

多显示器：

- 被控端必须能枚举显示器 ID、名称、分辨率、缩放和主屏状态。
- 主控端必须能选择显示器并切换显示器。
- 切换显示器后画面分辨率和输入映射必须正确。
- 显示器热插拔或枚举失败时必须给出明确错误并保持当前会话可断开。

无人值守：

- 开启无人值守后，授权账号必须能发起无人值守会话，未授权账号必须被拒绝。
- `require_prompt = true` 时，无人值守 proof 成功后必须进入 `waiting_approval`，被控端接受前不得交换候选、Relay token 或密钥。
- `require_prompt = true` 时，被控端接受后才允许交换候选、Relay token 和密钥。
- `require_prompt = false` 时，无人值守 proof 成功后必须进入 `unattended_verified`，并允许开始候选交换、Relay token 分配和密钥交换。
- 关闭无人值守后，新会话和旧凭据 proof 都必须失败。
- 轮换无人值守凭据后，旧版本立即失效，新版本可连接。
- 无人值守成功、失败、轮换和关闭必须写审计事件。

隐私屏和本地输入保护：

- 默认关闭。
- 被控端本地允许且会话权限允许时，主控端可以请求启用。
- 被控端本地关闭时，主控端请求必须失败并显示原因。
- 临时协助默认不能启用隐私屏和本地输入保护。
- 启用、关闭、失败和恢复必须写审计。
- 运行时状态必须通过设备签名的 `capability-events` 写裁剪审计，不得上报 E2EE 明文。
- 会话断开、主控端崩溃、被控端崩溃恢复、网络超时后必须恢复显示和本地输入。
- Windows UAC、安全桌面、锁屏和登录界面不得被绕过。
- Ubuntu Wayland portal 授权取消后不得继续锁输入或遮蔽屏幕。

iOS 主控：

- 虚拟键盘可以输入文本和常用功能键。
- 快捷键面板可以发送常用组合键。
- 触控手势可完成移动、点击、右键、滚动和缩放。
- 外接键盘和鼠标可用于基础控制。
- 横竖屏切换后画面比例和输入映射正确。

键盘、IME 和快捷键：

- 英文文本、中文 IME 文本、符号和换行可以输入。
- 常用组合键可以通过快捷键面板发送。
- 长按重复键行为符合平台预期。
- 焦点切换、断线、会话关闭和主控端崩溃后必须释放所有按键。
- Wayland 不支持能力必须明确报错。
- 日志不得记录文本、按键内容和 IME 组合内容。

Ubuntu Wayland portal 失效矩阵：

- `portal_screen_cast_denied`：用户拒绝屏幕采集授权时，不得继续采集或创建可用画面通道，客户端必须显示授权被拒绝并写审计。
- `portal_remote_desktop_denied`：用户拒绝远程控制授权时，画面可按平台允许降级为只看模式，输入必须明确 unsupported 或 disabled，不得静默丢输入。
- `portal_token_expired`：portal 授权过期或 portal 实现重启后，客户端必须停止对应能力、提示重新授权或断开会话，并恢复本地输入状态。
- `compositor_unsupported`：GNOME/KDE 或其他 compositor 不支持所需 portal 能力时，必须显示平台不支持原因；如 X11 fallback 可用则按用户确认后切换，否则保持可断开状态。
- 以上用例必须覆盖 Wayland 被控端采集、输入、断开后资源释放和敏感日志扫描，证据保存到 `docs/report/visual/ubuntu/portal-failure/**`。

媒体质量控制：

- 双方 H.264 能力协商成功。
- 能力不匹配时拒绝媒体通道并显示原因。
- 硬编不可用时降级软件编码或降低质量。
- 弱网时动态降帧、降码率或降分辨率，输入通道不持续排队。
- `keyframe_request` 可以恢复丢关键帧后的画面。
- H.265、AV1、4:4:4 和 HDR 不作为 V1 Core 验收。
- 系统音频采集、传输和远端播放不作为 V1 Core 验收。

远程重启：

- 无 `allow_remote_reboot` 时拒绝请求。
- 未完成 step-up 时拒绝请求。
- 被控端倒计时可见且可以取消。
- 重启前释放隐私屏、本地输入保护、采集和输入状态。
- 重启后被控端重新上线。
- 恢复必须创建新会话并重新完成 signed key exchange。
- 恢复窗口过期或无人值守关闭后恢复失败。
- 临时协助未选择自动恢复一次时，重启后必须重新弹出被控端确认。
- 自动恢复一次只能被原主控账号、原主控设备和原被控设备在恢复窗口内消费一次；重复消费、设备不匹配或 `local_consent_token_hash` 不匹配必须拒绝。
- API、审计和日志只允许保存 `reason_hash`，不得保存远程重启 reason 自由文本。
- 请求创建、被控端接受、开始执行和取消必须分别写入 `requested_at_epoch_millis`、`accepted_at_epoch_millis`、`executed_at_epoch_millis`、`cancelled_at_epoch_millis`，且与当前 `status` 流转一致。
- 被控端接受重启必须写 `remote_reboot_accepted`；step-up 过期、`allow_remote_reboot` 变化、策略重评估晚于 step-up 或 `permissions_digest` 变化时必须拒绝创建或执行重启请求。

反诈与滥用：

- 陌生账号临时协助展示风险提示。
- 被控端可以举报、拒绝和拉黑。
- 同一主控设备短时间连接大量陌生设备触发风控。
- Relay token 高频失败触发 Relay 限制。
- 误报解除后必须重新按权限模型评估。

会话录制边界：

- V1 Core 不提供生产会话录制入口。
- QA 截图或录屏证据必须由测试人员显式采集，并按 `docs/report/**` 证据规则保存。

M8 区域驻留：

- 企业区域策略启用时，禁止跨区 Relay。
- 区域不可用且 fail-closed 时拒绝分配。
- UDP observe 诊断 `region` 不能影响合规决策。

## 7. 性能测试

第一版基线：

- 1080p 办公画面。
- LAN Direct 不低于 30fps。
- Relay 不低于 20fps。
- LAN Direct 输入延迟目标小于 120ms。
- Relay 输入延迟目标小于 220ms。
- 断线重连目标小于 5 秒。
- 鼠标移动连续输入。
- 文本编辑。
- 浏览器滚动。
- 多显示器切换。
- 100MB 文件传输时控制通道不得出现持续 500ms 以上输入排队。
- 隐私屏或本地输入保护开启时，控制通道延迟不得持续超过同网络路径基线 20%。
- 媒体降级期间，输入事件不得持续排队超过 500ms。
- 输入排队按媒体设计定义采集：主控端发送输入事件 timestamp 到被控端注入或明确 unsupported timestamp 的差值；连续 5 秒滑动窗口内超过 500ms 的样本占比不得大于 20%，且不得出现无降级动作的单段连续排队超过 500ms。
- 帧 age 按被控端采集 timestamp 到主控端渲染 timestamp 采集，LAN Direct 目标不超过 200ms，Relay 目标不超过 350ms；超过目标时必须看到丢旧帧、降帧、降码率或降分辨率动作。

采集指标：

- RTT。
- 丢包。
- 抖动。
- 码率。
- 帧率。
- 输入排队时延。
- 帧 age。
- 编码耗时。
- 解码耗时。
- CPU。
- 内存。
- Relay 流量。

## 8. 稳定性测试

必须覆盖：

- 会话 1 小时稳定运行。
- 主控端崩溃。
- 被控端崩溃。
- Signal Server 重启。
- Relay Server 重启。
- 网络短断。
- 系统睡眠和唤醒。
- 被控端注销或锁屏。
- 远程重启。

平台降级期望：

- Windows UAC、锁屏和登录界面不承诺绕过系统安全边界；无法控制时必须显示明确错误或降级提示，并允许用户断开会话。
- Ubuntu Wayland 必须尊重 xdg-desktop-portal 授权；授权取消或桌面环境不支持时必须明确报错，不得静默绕过。
- Ubuntu X11 可使用 XTest/uinput，但断开后必须释放输入状态。
- 系统睡眠后允许会话进入 `reconnecting` 或 `closed`，不得继续注入输入事件。
- 这里的系统唤醒只指用户本地或操作系统自身唤醒后的会话状态恢复检查；V1 Core 不测试也不承诺远程开机、WOL、智能插座或带外管理唤醒。
- 远程重启后旧会话必须关闭，恢复只能走新会话。
- iOS 主控会话中 App 进入后台 60 秒、回到前台、锁屏 30 秒、解锁或来电中断 30 秒后，必须保持会话状态或正确进入 `reconnecting/closed`，不得继续发送失效输入。

## 9. 回归门禁

每次合入核心代码前必须通过：

```bash
make fmt-check
make lint
make test
make check
```

账号身份与安全专项门禁（T002P/T005A）必须额外执行：

```bash
CARGO_TARGET_DIR=/tmp/remote-integration-target cargo test -p api-server login_finish
CARGO_TARGET_DIR=/tmp/remote-integration-target cargo test -p api-server store::tests::memory_
API_TEST_DATABASE_URL=<isolated-migrated-postgresql> \
  CARGO_TARGET_DIR=/tmp/remote-integration-target \
  cargo test -p api-server -- --ignored
```

账号安全版本快照必须覆盖同毫秒、时钟回拨、改密/MFA 变化后旧 login challenge、challenge 创建与安全变化并发；`required_methods` 必须覆盖 MFA active、无 MFA password reauthentication、无 MFA 其他高风险拒绝及账号锁串行化。login finish 的 Memory/PostgreSQL grant、trust、session MFA 快照和审计集合必须使用同一契约；每个实际撤销 session/trust 必须有一条对象审计，logout 的 session 撤销与对象审计也必须原子。审计故障注入、状态故障注入和 PostgreSQL 提交后 Redis 失败均必须证明全量回滚或保持已提交终态。

真实 PostgreSQL 命令未成功执行时，不能标记 T002P/T005A 或 M2 完成；不得用 Memory、SQL 形状单测或未迁移数据库替代实库结果。
