# 里程碑计划

## 1. 原则

先冻结文档，再继续开发。开发时按阶段交付，每阶段都必须可运行、可验证、可回滚。

## 2. M0 文档定稿

目标：

- 产品规格定稿。
- 架构设计定稿。
- 协议设计定稿。
- 数据库设计定稿。
- 客户端设计定稿。
- 服务端设计定稿。
- 测试方案定稿。
- AI 开发任务清单定稿。
- 账号 MFA、条件访问、隐私屏、本地输入保护、客户端防伪、反诈与滥用、远程重启、键盘/IME、媒体协商、会话录制边界和企业区域驻留专项文档定稿。
- 登录设备身份与受信任主控设备 ADR 已接受并同步到权威文档。

退出标准：

- README 有完整文档入口。
- AGENTS 有开发前阅读规则。
- 后续开发不得绕过这些文档。
- 首版应用层端到端加密、签名密钥交换、WebSocket 鉴权握手、NAT 外部观测地址来源已经明确。
- MFA/risk、反诈与滥用、条件访问、隐私屏、本地输入保护、远程重启、键盘/IME、媒体协商、包签名、manifest 签名、SBOM、会话录制边界和企业区域驻留已经写入设计、测试和任务清单。
- 用户已确认 `0001_initial_schema.sql` 未进入共享环境；账号身份 Schema 修订固定重写 `0001`。

## 3. M1 工程基础

目标：

- Rust workspace 可构建。
- 协议、核心、传输、加密、采集、渲染抽象就绪。
- API/Signal/Relay 服务可启动。
- Docker Compose 初版。
- Schema Freeze 已完成，迁移策略已经落盘。
- 已接受账号身份 ADR 的 Schema 修订已进入最终 `0001`。

退出标准：

- `make fmt-check`
- `make lint`
- `make test`
- `make check`
- 三个服务健康检查通过。
- T002E 基础 Schema Freeze 已完成；T002P 必须按已确认路径重写未共享 `0001`，补齐 `device_enrollment_grants`、`mfa_recovery_code_deliveries`、`account_sessions.revoked_reason` 和登录 challenge/trust 约束。
- 已输出 `0001_initial_schema.sql` 与最终逻辑模型的 delta 清单。
- 已完成修订后 `0001` 的迁移 dry-run，并验证迁移 runner、Docker Compose 或部署脚本不会执行旧 Schema 或额外 `0002_account_identity_contract.sql`。

## 4. M2 账号和设备

目标：

- 两段式账号登录和设备私钥证明。
- TOTP MFA、恢复码和高风险操作 step-up。
- 一次性 enrollment grant 设备注册。
- 设备绑定。
- 在线状态。
- 设备 ID 展示和在线设备发现。

退出标准：

- 主控端、CLI 或测试客户端可看到被控端在线。
- 登录第一段不签发 token；finish 完成设备签名和所需 MFA 后才签发 account session。
- 任意 access token 不具备新增设备权限；设备、grant 消费、审计和可选 trust 原子提交。
- 无 MFA 账号自动注册设备但不建立 trust；TOTP/recovery trust 按固定 TTL 且普通登录/refresh 不滑动续期。
- TOTP 恢复码以客户端可解密 ciphertext 幂等交付；启用/禁用 MFA 和修改密码后全部旧 session/trust 失效。
- 主控端、CLI 或测试客户端可配置官方/私有服务地址，并清楚显示当前环境。
- WebSocket 账号 token + 设备签名握手有效。
- 审计日志写入。
- 新主控设备和高风险操作风险验证可用。
- 基础反诈限流、风险提示、举报和拉黑可用。

## 5. M3 信令和会话

目标：

- 主控端创建会话。
- 临时验证码 verifier/proof。
- 无人值守 proof。
- 被控端收到邀请。
- 被控端接受或拒绝。
- 会话状态可追踪。
- 会话创建前条件访问和有效权限评估。

退出标准：

- Windows/Ubuntu 两台测试设备能完成会话协商。
- 验证码过期和重试限制有效。
- `require_prompt=false` 无人值守 proof 成功后进入允许建链状态，但不要求 M3 完成真实 P2P/Relay/key exchange。
- 拒绝、超时、离线都有明确错误。
- 黑名单、`require_prompt`、`allow_relay`、MFA step-up 和条件访问拒绝可审计。
- 反诈 cooldown、deny、suspend 决策可审计。

## 6. M4 传输和 Relay

目标：

- LAN Direct。
- UDP P2P。
- QUIC Relay。
- TLS 443 Relay。
- 应用层 signed key exchange、HKDF、业务帧加密和 key_confirm。
- 链路选择。
- 断线重连。

退出标准：

- 六条 OS 家族平台链路都通过 client-core、CLI 或测试桩验证 LAN Direct over QUIC、UDP P2P over QUIC、QUIC Relay、TLS 443 Relay 的建链、业务密文消息往返和断线恢复。
- M4 必须完成 signed key exchange、HKDF 绑定字段、业务帧加密、`key_confirm`、Signal 替换临时公钥拒绝和权限变化旧 key 失效测试；未完成应用层端到端加密时不得把真实远控链路标记为通过。
- M4 是核心传输矩阵；iOS 真机网络栈、Rust FFI 和系统约束必须在 M5/M7 继续验收，不能只凭核心测试桩代表 iOS 真机通过。
- 必须输出 M4 网络矩阵证据包，至少包含 24 组证据：6 条 OS 家族链路 x 4 条网络路径，包含命令、日志、指标和结论；Windows 10/11 与 Ubuntu Wayland/X11 变体在 M5-M7 的 20 个发布真实远控组合中展开。
- TLS 443 Relay 路径未完成 T016 业务密文往返证据前，M4 不得标记通过。
- M4 不作为真实远控画面和输入验收；画面和输入必须在 M5 重新验收。
- Relay 流量可统计。

## 7. M5 远控画面和输入

目标：

- Windows 采集和输入。
- Ubuntu 采集和输入。
- Windows/Ubuntu 主控显示。
- iOS 主控显示和触控映射。
- 键盘、IME 和组合键输入。
- 媒体能力协商和质量控制。

退出标准：

- 六条 OS 家族平台链路全部能看到画面和输入控制。
- 发布真实远控矩阵在 M5 启动，至少完成 6 条 OS 家族平台链路的真实画面、输入、断开和资源释放闭环；20 个具体组合的完整通过、失败或阻断结论由 M6/T022V 补证据，并由 M7/T026 作为发布门禁汇总。
- iOS 主控完成触控、虚拟键盘、快捷键面板、外接键盘鼠标和横竖屏验证。
- 中文 IME、文本提交、组合键和断开释放按键状态通过验收。
- H.264 能力协商、弱网降级、关键帧请求和硬编失败 fallback 通过验收。
- M5 验收链路方向固定为被控端 Windows/Ubuntu -> 主控端 Windows/Ubuntu/iOS，iOS 不作为被控端。
- 断开后资源释放。

## 8. M6 可用功能

目标：

- 多显示器。
- 剪贴板。
- 基础文件传输。
- 无人值守。
- 隐私屏。
- 本地输入保护。
- 远程重启和重启后新会话恢复。
- 会话日志。

退出标准：

- 每项功能有独立权限。
- 多显示器必须支持枚举、选择、切换，并保持画面分辨率和输入映射正确。
- 剪贴板开启时双向文本同步成功，关闭时双向阻断。
- 文件传输完成后 hash 一致，失败和取消状态明确。
- 隐私屏和本地输入保护默认关闭、独立授权、平台不支持时明确失败，断开或崩溃后恢复。
- 远程重启默认关闭，必须 step-up、被控端提示、可取消；重启后旧会话关闭，新会话重新完成密钥交换。
- 无人值守开启后，`require_prompt=false` 可完成端到端连接，`require_prompt=true` 必须等待被控端接受后才能连接；轮换后旧凭据失效，关闭后不能再用旧 proof 连接。
- 审计记录完整。

## 9. M7 稳定性和性能

目标：

- 弱网优化。
- 高 CPU/低带宽场景优化。
- Relay 调度。
- 诊断日志。
- 安装包签名、更新 manifest 签名、SBOM 和发布检查。

退出标准：

- 1 小时会话稳定。
- 100MB 文件传输时控制通道不得出现持续 500ms 以上输入排队，采集口径以测试方案和媒体质量控制设计为准。
- 网络切换后可恢复。
- 媒体降级期间输入优先，不出现持续输入排队。
- 远程重启、客户端异常退出和普通网络恢复边界可解释；不承诺远程开机、WOL、智能插座唤醒或带外管理唤醒。
- 未签名、hash 不匹配、manifest 过期或被撤销的更新包不得安装。
- M7 退出前必须汇总 20 个发布真实远控组合的通过、失败或阻断结论，不能只用 M4 的 OS 家族网络矩阵代表发布验收。

## 10. M8 V1 Commercial 企业化增强

目标：

- 管理后台。
- 组织/成员/角色。
- 策略下发。
- 条件访问管理后台。
- 企业反滥用后台。
- 区域路由和数据驻留策略。
- 会话录制边界或端点侧录制预研。
- 私有化部署。

范围：

- M8 是首版个人/小团队远控闭环之后的企业化增强。
- M8 对应 `V1 Commercial`，不是 `V1 Core` 的发布门禁。
- 数据表和接口预留不阻塞 M1-M7。
- 如果首版商业发布需要私有化管理后台，必须把 M8 提前并拆成正式发布门禁。
- M8 最终发布门禁必须由 `T027Q` 汇总，依赖企业基础 `T027`、区域驻留 `T027A` 和录制决策/实现 `T027B0/T027B`，不得让 `T027` 单独代表 V1 Commercial 发布完成。

退出标准：

- Docker Compose 可部署完整服务：api-server、signal-server、relay-server、admin-web、postgres、redis；object-storage 和 metrics 只有被对应功能启用时才是门禁。
- 管理后台可查看设备、会话和审计。
- 管理后台可配置组织、成员、角色和策略，并能看到策略变更审计。
- 管理后台可配置区域策略并验证禁止跨区 Relay。
- 如 M8 提前实现生产录制，必须先完成录制二次冻结决策，再采用端点侧录制、可见提示、加密保存、访问审计、留存删除和失败策略；否则发布报告必须明确录制为 disabled，保持 V1 Core 不做生产录制。
- V1 Commercial 发布验收必须覆盖后台 RBAC、策略下发、私有化部署、私有化 release channel、客户端服务地址环境标识、区域策略、官方 SaaS 隔离、审计和回滚。
